一、iOS / SwiftUI 原生（1—10）

1SwiftUI 的“声明式 UI”到底声明了什么？它与 UIKit 的命令式更新有什么本质差异？
为什么重要

关键在于确认是否只会写 View，还是理解状态驱动、值语义、diff 与视图身份。

要点
  • SwiftUI 声明的是“当前状态应映射成什么 UI”，开发者不直接维护控件树的逐步变更；状态变化后，body 会重新求值，框架比较新旧视图描述并把必要更新提交给底层渲染系统。
  • View 通常是轻量值类型，body 重算不等于屏幕整棵树被销毁重建。性能关键在稳定 identity、合理拆分视图、避免在 body 做重计算，而不是机械地减少 body 调用次数。
  • UIKit 更偏命令式：创建对象、持有引用、在事件后手工改 label、约束和层级。SwiftUI 降低了“状态与界面不同步”的概率，但复杂导航、系统能力桥接仍可能需要 UIKit。
  • 数据流需区分：@State 管本地值状态，@Binding 向下传可写引用语义，@StateObject（旧式 ObservableObject 体系）由当前视图拥有对象生命周期，@ObservedObject 观察外部对象，@EnvironmentObject 做环境注入；新 Observation 框架则常用 @Observable。
  • 项目引用：AI医疗辅助App采用 SwiftUI + MVVM，回答时只说“用状态驱动诊断录入、OCR 结果和图表展示等界面”，不要虚构具体页面或属性包装器用法。
延伸联想

补一句：“我会先确认团队最低 iOS 版本，因为 Observation、导航和并发模型的选型都受 deployment target 影响。”把语法题拉到工程决策。

边界与常见误区

“我对 SwiftUI 的核心理解是状态到 UI 的纯映射、稳定身份和最小化更新；具体某个版本内部 diff 实现我不会假装掌握，但我能从 Instruments 和实际重绘行为验证性能问题。”

2SwiftUI 中状态失效、列表错位或页面重复初始化，通常从哪里排查？
为什么重要

关键在于理解对视图 identity、生命周期与状态归属的工程理解。

要点
  • 先检查 identity：ForEach 的 id 是否稳定且唯一，是否误用数组下标或每次生成 UUID；条件分支是否改变视图结构；显式 .id() 是否导致状态被重置。
  • 再检查所有权：需要由页面持有的引用对象不能每次重算都重新创建；外部传入对象不应被当前视图错误“拥有”。状态应尽量靠近唯一事实源，派生状态通过计算得到。
  • 异步任务要与视图生命周期绑定：.task(id:) 可随依赖变化取消和重启；需要处理取消，避免旧请求回写新页面。
  • 列表性能看稳定 id、昂贵格式化/图片解码是否在主线程、是否有过大的 ObservableObject 导致全页失效。
延伸联想

主动区分“body 重算频繁”和“真实布局/渲染昂贵”，说明会用 Instruments、signpost 或最小复现定位，而不是凭感觉优化。

边界与常见误区

“我会按 identity、状态所有权、异步任务、主线程耗时四层排查。具体到实际代码，我会先做最小复现，而不是直接加缓存掩盖问题。”

3Combine 的核心模型是什么？在 AI 流式响应或 OCR 流程里如何使用？
为什么重要

关键在于确认是否理解 Publisher、Subscriber、Operator、取消与线程调度，而不只是会 sink。

要点
  • Publisher 发出一串值并以完成或失败结束；Subscriber 订阅；Operator 组合转换、过滤、合并、节流和错误恢复；AnyCancellable 管订阅生命周期。
  • subscribe(on:) 主要影响上游订阅/工作从哪里开始，receive(on:) 决定下游在哪个调度器接收。更新 UI 要回主线程，并避免把 CPU 密集 OCR 放在主线程。
  • 搜索输入可 debounce + removeDuplicates + flatMap/switchToLatest；OCR 可把图片输入、识别、结果清洗、持久化串成 pipeline；AI token 流可增量聚合、处理取消和错误状态。
  • Combine 有 demand/backpressure 概念，但并非所有自定义 publisher 都天然解决网络端拥塞；对 SSE / WebSocket 仍需做缓冲上限、消费节奏与取消策略。
  • 项目引用：AI医疗辅助App真实技术栈包含 Combine 与 Vision Framework，可说明二者适合组织“输入—识别—状态更新”链路；不要声称项目一定使用了某个未核实的 operator。
延伸联想

可比较 Combine 与 async/await：“一次性异步请求优先结构化并发；多值事件流、组合状态或兼容既有响应式架构时 Combine 仍有价值，二者可以桥接。”

边界与常见误区

“我能讲清发布、转换、线程切换、取消这条主链；某个冷门 operator 的精确签名我会查文档，不会实践中猜。”

4Combine 中最容易出现哪些内存泄漏和竞态？
为什么重要

把响应式语法进一步讨论到生产可靠性。

要点
  • 常见环：对象强持有 cancellables，订阅闭包又强捕获对象。根据生命周期使用 [weak self]、让订阅结束、或明确由更上层持有；不能把所有问题简单粗暴地改成 weak。
  • 页面消失、搜索词变化、任务切换时取消旧订阅，防止过期结果覆盖最新状态；用 switchToLatest 或请求序号保证 last-write-wins。
  • UI 状态统一在主执行上下文更新；对共享可变状态做串行化。错误不能在链中被无声吞掉，要映射成业务可观测状态。
  • share / multicast 影响订阅是否重复触发上游，要根据副作用语义决定，不能为了“省请求”随便共享。
延伸联想

主动提出把加载态建模成 idle/loading/success/failure，而不是分散的多个 Bool，可显著减少非法状态组合。

边界与常见误区

“我先保证三个底线：订阅可取消、闭包捕获关系可解释、旧结果不能覆盖新状态；更细的 operator 行为会通过单测验证。”

5Core Data 是数据库吗？如何设计并发、迁移与性能？
为什么重要

关键在于判断是否理解对象图管理而不是把 Core Data 当 SQLite ORM。

要点
  • Core Data 是对象图管理与持久化框架，提供 identity、关系、变更跟踪、撤销、验证和持久化；SQLite 只是常见 persistent store，并不等同于 Core Data 本身。
  • NSManagedObjectContext 可看作工作区，不能跨队列随意传 NSManagedObject；跨上下文传 NSManagedObjectID，在各自队列中解析。UI 用 viewContext，导入/OCR 批处理用后台 context。
  • 批量导入控制 save 频率与 autorelease，设置 fetch limit、batch size、predicate、sort；必要字段建索引，避免循环访问关系造成 N+1。
  • 轻量迁移适合兼容的模型变化；复杂拆分/合并需 mapping 或分阶段迁移。上线前必须用旧版本真实 store 做迁移测试，并准备失败恢复和备份策略。
  • 若接 CloudKit 还要处理冲突、离线、账号切换和隐私，但没有项目证据时不要声称AI医疗辅助App用了 CloudKit。
  • 项目引用：AI医疗辅助App采用 Core Data，可记录为“承担本地结构化数据管理”；未核实的数据实体、同步方式与加密方案不能自创。
延伸联想

把医疗场景的隐私拉进来：最小化存储、敏感字段保护、日志脱敏、删除语义和备份边界往往比 ORM 语法更重要。

边界与常见误区

“我做过 Core Data 的真实落地，核心原则是 context 队列隔离、对象 ID 跨上下文、迁移先拿旧库验证；复杂自定义迁移细节我会结合模型变更再给方案。”

6MVVM 在 SwiftUI 中怎样划分才不会变成 Massive ViewModel？
为什么重要

关键在于理解架构是否服务于边界、测试与演进。

要点
  • View 负责呈现和转发意图；ViewModel 管页面状态、业务动作与异步协调；领域规则、数据访问、OCR/网络等能力下沉到 use case/service/repository。
  • ViewModel 不应直接囊括所有 SDK 细节、导航、缓存、埋点和格式化；按 feature 切分，依赖协议注入，保证核心逻辑可用 fake 测试。
  • 页面状态显式建模，单向数据流：用户意图 → action → 状态变化 → UI。导航可由 router/coordinator 或可测试的路由状态承载，按项目复杂度取舍。
  • SwiftUI 已经提供绑定和状态机制，MVVM 不是强制模板；极简单视图没必要为“架构纯洁”创建空 ViewModel。
  • 项目引用：AI医疗辅助App真实采用 SwiftUI + MVVM，可说这是为了把 UI、状态协调和 Core Data / Vision 等能力解耦；不要虚构具体分层文件数量。
延伸联想

强调架构评判标准：“是否可测试、依赖方向是否稳定、改需求时影响面是否可控”，而不是层数多少。

边界与常见误区

“我不会把 MVVM 当固定目录模板。我的底线是 UI 不直接承载业务副作用、能力可替换、关键状态可测试。”

7iOS App 生命周期在 SwiftUI 下如何理解？进入后台后哪些任务不能想当然地继续？
为什么重要

关键在于理解前后台切换、资源释放与系统约束。

要点
  • SwiftUI App 是入口，场景生命周期常通过 scenePhase 观察 active/inactive/background；多 scene 环境不能继续假设应用只有一个窗口状态。
  • 进入后台后普通代码只有有限执行时间，系统可挂起或终止进程。要保存必要状态、停止摄像头/定时器、取消非必要流、保护敏感界面。
  • 合法后台能力需匹配业务并声明对应 mode；短任务可申请 background task，调度型任务看 BGTaskScheduler，但运行时机由系统决定，不可当常驻服务。
  • 推送只是触达/唤醒机制之一，不能保证任意后台计算。恢复时要处理数据陈旧、任务中断、幂等和重试。
延伸联想

结合 AI 场景说明：长时推理更适合服务端任务化，客户端保存 task id，恢复后查询或接续流，不把生成过程绑死在前台页面。

边界与常见误区

“我不会承诺 iOS 后台常驻。设计上会把长任务做成服务端可恢复任务，客户端只维护状态和合法的系统后台能力。”

8Vision Framework OCR 的完整工程链路怎么做？准确率和性能如何权衡？
为什么重要

关键在于确认做过系统框架集成，并能处理图片方向、质量、并发和隐私。

要点
  • 典型链路：获取图片 → 修正 EXIF/CGImage 方向 → 裁剪、缩放或增强 → VNRecognizeTextRequest → 选择 recognition level、语言与纠错 → 解析 observation / candidate → 业务校验与人工确认。
  • .accurate 通常更准但更慢，.fast 适合实时预览；用 region of interest、合理分辨率和串行/受控并发降低耗时与内存峰值。
  • OCR 结果不是事实：保留置信度、原图定位框和人工校正入口；医疗文本需做字段级规则验证，不能直接进入诊断结论。
  • 请求放后台执行，UI 更新回主线程；相机连续帧要丢弃过期帧，不能无界排队。敏感图像优先端侧处理并明确生命周期。
  • 项目引用：AI医疗辅助App集成 Vision Framework OCR，这是端侧能力的真实证据；只能说使用了 OCR，不能臆造识别了哪类票据或准确率数字。
延伸联想

可进一步确认目标是“扫描一次求准确”还是“实时取景求流畅”，因为二者决定 request 配置、帧策略和交互设计。

边界与常见误区

“具体 API 参数我可能需要看当前 iOS 版本文档，但工程底线明确：方向校正、后台识别、置信度与人工确认、敏感图片最小留存。”

9ARC 如何工作？Swift 中最典型的循环引用和内存峰值从哪里来？
为什么重要

关键在于确认原生内存管理基本功。

要点
  • ARC 在编译期插入引用计数管理，强引用数归零后释放实例；只管理引用类型生命周期，不是追踪式 GC，也不保证没有循环引用。
  • weak 不增加计数、自动置 nil，必须是可选；unowned 不增加计数且假设引用始终有效，判断错误会崩溃。
  • 常见环：delegate 未设 weak、闭包/定时器/订阅/Task 强捕获 self、父子对象互持。用 Xcode Memory Graph、Instruments Allocations / Leaks 定位。
  • 峰值不一定是泄漏：大图解码后的内存远大于压缩文件、连续 OCR 帧堆积、缓存无上限、临时对象未及时释放都可能造成 jetsam。
  • 项目引用：AI医疗辅助App涉及 OCR 与图表，回答可说明会特别关注图像处理内存峰值；不能声称处理过某个未记录的 OOM 事故。
延伸联想

指出“用了 [weak self]”不是完整答案，还要解释任务是否应该因 owner 消失而取消，以及 nil 后业务如何收尾。

边界与常见误区

“我能保证引用关系和任务生命周期说得清；若实践中是疑难泄漏，我会用 Memory Graph 与 Allocations 看对象保留链，不靠猜。”

10App Store 审核机制、发布流程和常见驳回项有哪些？你如何降低审核风险？
为什么重要

关键在于理解是否有真实上架闭环，而不是只完成编码。

要点
  • 流程包括证书/签名与 provisioning、Archive、上传构建、App Store Connect 元数据与隐私信息、TestFlight 验证、提交审核、分阶段或手动发布；具体界面会更新，但审核核心围绕功能完整、合规、隐私和商业规则。
  • 常见驳回：崩溃/占位/登录不可用；用途描述与实际权限不符；收集数据但隐私清单、标签、SDK 声明不一致；账号体系无删除入口；数字内容绕过 IAP；误导性医疗声明；UGC 缺举报/屏蔽；复制 App、最低功能、截图元数据不实。
  • 审核前用 release 构建和干净账号走完整路径，提供可用审核账号、复现步骤和必要说明；权限按需触发；第三方 SDK 做隐私审计；医疗产品避免把辅助能力宣传成未经证明的诊断结论。
  • 被拒后先逐条对应 guideline、复现并修复，Resolution Center 用证据沟通；若判断错误可解释或申诉，但不对抗式回复。
  • 项目引用：AI医疗辅助App 由本人独立完成，v1.2.0→v1.2.1 多轮通过审核，提交记录包含“修复 App Store 审核问题”“iPad 布局适配”“年龄分级设置”。这些是可直接说的事实；具体被拒条款未核实，不要编造。
延伸联想

把“上架”提升为发布工程：版本可追溯、审核素材检查表、隐私与 SDK 清单、灰度与回滚预案。

边界与常见误区

“我有AI医疗辅助App从开发到多轮审核上架的完整经历，但不会凭记忆编某次驳回条款编号。能确认的是我实际处理过审核整改、iPad 适配和年龄分级，并完成 v1.2.0 到 v1.2.1 发布闭环。”

二、Android 原生基础与架构实践（11—15）

11Android Activity / Fragment 生命周期怎么理解？配置变化与进程死亡有什么区别？
为什么重要

关键在于确认最基础的平台模型与状态恢复意识。

要点
  • 经历锚点：我早年独立主导过 Android 项目架构，因此生命周期不是孤立背回调，而是状态恢复、资源释放和异常重建的架构边界。
  • Activity 常见阶段是 create/start/resume 与 pause/stop/destroy；Fragment 还要区分自身生命周期和 view lifecycle，view 销毁后继续持有 binding 容易泄漏。
  • 旋转等配置变化通常会重建 Activity；ViewModel 可跨配置变化保留内存态，但不能跨进程死亡。可恢复的小状态用 savedInstanceState / SavedStateHandle，持久数据放数据库或服务端。
  • 进程可能在后台被系统回收，恢复时不能假设单例、静态变量或内存任务仍在；入口要能从持久状态重建。
  • Compose 同样受宿主生命周期约束；副作用要用与组合和生命周期匹配的 API，不能在 composable 每次重组时裸启动任务。
延伸联想

类比 iOS 场景/后台恢复，但马上指出平台回调与约束不同，类比用于建模而不是代替 Android 事实。

边界与常见误区

“我独立主导 Android 项目时形成的底线是守住配置重建、进程死亡、状态持久化和任务取消四个边界；涉及目标系统版本的冷门回调差异，我会直接用生命周期测试验证。”

12Jetpack Compose 与 SwiftUI 有哪些相似和不同？重组为什么不等于重绘？
为什么重要

看实践者能否迁移声明式 UI 知识，同时尊重平台差异。

要点
  • 经历锚点：我有 Android 原生架构经历，也有近期 SwiftUI 实战；回答 Compose 时会从 Android 自身的 composition、状态读取和副作用机制出发，而不是简单套用 SwiftUI。
  • 二者都是状态驱动的声明式 UI：描述当前 UI，状态变化触发框架重新评估；都要求副作用与 UI 描述分离。
  • Compose 通过 composition/recomposition、slot table、state read tracking 跳过未受影响部分；重组是执行 composable 更新组合，不等于所有节点都重新 layout/draw。
  • 状态提升、单向数据流、稳定 key、列表惰性加载和避免重组内重计算是共通原则。Compose 常见 remember 只跨重组，rememberSaveable 才借助保存机制应对可保存状态重建。
  • 差异包括语言/runtime、底层 UI 系统、生命周期、导航、可观察状态和工具链，不能把 SwiftUI property wrapper 名字一一硬套。
延伸联想

用“同源模型 + 平台专项验证”定位自己，提出性能要用 Layout Inspector / Compose tracing 或基准测试验证。

边界与常见误区

“我能从 Android 原生架构和 SwiftUI 实战两侧讲清声明式 UI 的状态、identity、单向流与副作用；Compose 最新版本的 stability 推断细节，我会结合 compiler report、tracing 和基准测试确认。”

13Android 线程、协程与 ANR 的关系是什么？
为什么重要

关键在于理解并发、生命周期和稳定性底线。

要点
  • 经历锚点：独立主导 Android 项目时，主线程边界、异步任务生命周期和线上问题定位就是架构稳定性的核心；协程是今天实现这些原则的主要工具。
  • UI 线程负责输入、布局和绘制，不能做网络、长 IO 或重 CPU 工作。ANR 是主线程长期无法响应等场景触发的系统问题，不等于普通异常崩溃。
  • Kotlin coroutine 是结构化并发抽象，不等于自动切到后台；dispatcher 决定执行上下文，suspend 也不天然代表非阻塞。UI 层任务应绑定 lifecycleScope / viewModelScope 等明确作用域。
  • 取消是协作式的；阻塞 API 和 CPU 循环要主动支持取消或放到适合执行器。共享状态优先不可变与单向流，错误需要纳入状态而不是静默丢失。
  • 诊断看 ANR trace、Perfetto、StrictMode、线上监控；先识别主线程在等锁、Binder、IO 还是计算。
延伸联想

联系 AI 流式交互：网络 token 流不阻塞 UI，解析与 Markdown 渲染节流，页面退出取消消费，长任务服务端化。

边界与常见误区

“基于我的 Android 架构经验，可以明确 suspend 不等于后台线程、任务必须有作用域和取消、ANR 要从主线程 trace 找阻塞源；某个 dispatcher 的版本级内部实现则以源码和目标版本验证为准。”

14Android 本地存储怎么选：SharedPreferences / DataStore / Room / 文件？
为什么重要

关键在于理解数据形态、安全、迁移与离线能力的决策。

要点
  • 经历锚点：我主导 Android 项目技术选型时，会先按数据形态、访问模式、生命周期和安全等级划分存储职责，再决定具体组件。
  • 少量设置项优先 DataStore；复杂结构化、可查询、有关联和事务的数据用 Room；大文件走文件系统并在数据库保存元数据。SharedPreferences 是历史方案，新项目通常不作为首选。
  • Room 是 SQLite 之上的抽象，提供编译期 SQL 校验、DAO、迁移等；要设计 schema migration、索引、事务、分页和线程策略。
  • token / 密钥不能因“存在本地”就视为安全，需结合 Android Keystore、加密、权限、备份策略和威胁模型；医疗数据坚持最小留存和日志脱敏。
  • 跨端产品要明确本地数据是 cache 还是 source of truth；同步需版本号、幂等、冲突策略和离线队列。
延伸联想

以 Core Data 的迁移经验类比“旧版本真实数据升级测试”，但说明 Room 与 Core Data 的模型和 API 不同。

边界与常见误区

“我的选型顺序是先按设置、结构化数据和大文件分类，再确定一致性、安全与迁移策略；DataStore / Room 的版本级实现会用旧数据迁移测试和目标版本文档确认。”

15Android 模块化、构建与发布治理，技术负责人至少应抓什么？
为什么重要

关键在于判断能否把既有 Android 架构主导经验升级为现代工程治理能力。

要点
  • 经历锚点：早期 Android 项目中我不仅写业务，还主导整体项目设计和架构、技术调研与难题攻坚；后续多团队负责人经历进一步补齐了模块 owner、质量门和发布治理视角。
  • 模块边界按业务 feature 与稳定基础能力划分，依赖单向，避免“公共模块”成为垃圾桶；接口与实现分离要有实际编译或组织收益，不能过度模块化。
  • Gradle 治理关注版本目录/约束、插件统一、构建缓存、增量构建、CI 可复现、签名密钥隔离、依赖与许可证安全、release/debug 环境隔离。
  • 质量门包括 lint、单测、关键 UI / 集成测试、性能基线、崩溃与 ANR 指标、灰度发布、mapping 文件保留和回滚机制。
  • Play Console 侧关注 target API、权限政策、Data safety、签名与 app bundle；规则持续变化，发布前以当期官方要求为准。
  • 项目引用：可引用 AI医疗助手产品的真实发布治理：审计 5 个仓库，发现默认分支空壳、真实代码在 dev、tag 缺失，并推动 tag、分支清理和改动映射文档化。它证明治理能力，但不要说这些就是 Android 仓库。
延伸联想

直说负责人价值是建立指标、边界、质量闸门和主程授权机制，而不是抢主程写所有平台细节。

边界与常见误区

“我既有 Android 项目整体架构主导经历，也有多仓发布审计和团队治理实战。现代 Android 工程中，我会明确平台 owner，同时对模块边界、质量门、发布可追溯和风险闭环负责。”

三、Flutter、跨端与桌面端（16—22）

16Flutter 的渲染链路是什么？为什么它能跨平台保持一致？
为什么重要

关键在于判断是否理解框架底层而非只会 Widget。

要点
  • 项目引用：某金融科技公司和某到家服务平台两次 Flutter 转型都要求团队理解框架渲染边界与原生集成成本；可用“指导落地并重构 App”“领导原生团队转型”作为工程背景，不虚构具体引擎指标。
  • Dart Widget 是不可变配置，框架维护 Element 树承载实例与状态，再生成/更新 RenderObject 树完成 layout、paint、compositing，最终由 Flutter 引擎栅格化并提交平台表面。
  • Flutter 多数 UI 自己绘制而非把每个控件映射成平台原生控件，因此视觉与行为更一致；文本输入、无障碍、系统窗口和插件仍需平台集成。
  • 新版本 iOS 主要推进 Impeller 等渲染后端以改善 shader 编译卡顿；具体后端与版本要按目标平台核实，不宜说成所有版本都固定使用某一种引擎。
  • platform channel 用于 Dart 与原生能力通信；频繁细粒度跨边界、超大数据拷贝会有成本，应批处理或将重活留在一侧。
延伸联想

强调“自绘的一致性”也意味着要自己承担原生质感、无障碍和新系统特性的跟进成本。

边界与常见误区

“我能讲清 Widget—Element—RenderObject—Engine 这条链路；某一 Flutter 版本的引擎默认开关我会查 release note，不会用过期结论作答。”

17Flutter 与原生的性能差距在哪里？如何避免空泛地说“接近原生”？
为什么重要

关键在于理解是否会按场景和指标谈性能。

要点
  • 普通表单、列表和动画通常可达到良好体验；差距更容易出现在首包/启动与包体、平台视图混合、超长复杂列表、频繁 channel 调用、极致相机/音视频/图形、内存敏感和新系统能力适配。
  • 性能必须量化：启动时延、帧时间与掉帧、CPU/GPU、内存峰值、耗电、包体、平台通道耗时；在 release/profile 模式和真实低端设备测，debug 结论无效。
  • 优化包括缩小 rebuild 范围、稳定 key、图片尺寸与缓存、隔离 CPU 重活、减少透明叠层与昂贵裁剪、控制 platform view 数量、按需加载。
  • 原生也会写慢，Flutter 也可能足够快；选型看目标场景是否触及框架边界，以及团队能否维护原生插件。
  • 项目引用：某金融科技公司时期指导团队完成 Flutter 落地并重构公司移动端 App；某到家服务平台时期再次领导团队从原生转向 Flutter。可以从两次转型讲 POC、框架边界与团队落地；没有可核实 benchmark，不报具体性能百分比。
延伸联想

先明确关键用户路径，再给基准测试方案，而不是争论框架宗教。

边界与常见误区

“我不会笼统承诺‘媲美原生’。我会先锁定设备档位和关键路径，用帧、启动、内存、包体四组指标做 POC，再决定是否跨端。”

18Flutter 中状态管理怎么选？Bloc、Riverpod、Provider 是否越统一越好？
为什么重要

关键在于理解团队级状态与依赖治理。

要点
  • 先区分短暂 UI 状态、页面业务状态、跨页面领域状态、服务端缓存，再选工具；不要把所有字段塞进全局 store。
  • 评价维度：单向数据流、可测试性、异步与错误表达、作用域与释放、调试能力、团队认知、代码生成和升级成本。
  • 技术负责人应统一原则与主方案，允许少量局部状态使用框架原生能力；多套全局方案并存会增加心智与迁移成本。
  • Repository 隔离网络/数据库，状态对象显式表达 loading/data/error，避免 UI 直接调用 SDK。
  • 项目引用：可结合某金融科技公司 App 重构与某到家服务平台三款 App 团队转型，说明统一主方案的目的在于降低多人、多项目协作成本；不编造当时具体使用了 Bloc、Riverpod 或 Provider 中的哪一种。
延伸联想

表态不参与框架站队：“我更关心状态所有权和依赖方向，库只是实现。”

边界与常见误区

“我不会只凭流行度拍板。会用一个真实 feature 做 POC，对比测试、调试、异步错误和团队上手成本后统一主方案。”

19原生、Flutter、React Native、WebView 混合方案怎么选？
为什么重要

关键在于理解全局选型而非单框架偏好。

要点
  • 原生：系统能力深、体验/性能上限高、平台差异大或合规敏感；代价是双端团队与重复实现。
  • Flutter：品牌 UI 一致、双端快速交付、团队能维护 Dart 与少量原生插件；代价是包体、平台跟进、插件与混合视图边界。
  • React Native：团队 React/TS 强、业务 UI 较多且希望共享生态；仍需原生能力、版本升级和 bridge/新架构治理。
  • WebView/H5：高频运营、内容和低风险流程更新快；不适合把重交互、强离线和深系统能力全塞进去。混合方案要有路由、登录态、桥协议、版本兼容与监控。
  • 还要看人员、既有资产、交付期限、可访问性、热更新合规、长期维护总成本，而非只看首版速度。
  • 项目引用：某金融科技公司的 Flutter 落地与 App 重构、某到家服务平台从原生向 Flutter 的团队转型，是两次不同组织阶段的真实选型证据；可重点讲为何转、如何控制迁移边界和如何让团队具备原生兜底能力。
延伸联想

提出可逆决策：先把领域/API 契约稳定，UI 容器可替换；对最不确定的相机、音视频、复杂动画先做 POC。

边界与常见误区

“我不会先选框架再找场景。我会先列关键体验、系统能力、迭代频率和团队结构，再对高风险路径做两周以内的验证。”

20Taro / 微信小程序跨端方案的原理与选型边界是什么？
为什么重要

关键在于理解是否理解“编译到多端”并不意味着一次编写零差异。

要点
  • Taro 用统一 DSL / React 风格开发，经编译和运行时适配到小程序、H5 等目标；目标端仍有各自组件、API、生命周期、包体和审核约束。
  • 适合页面结构与业务流程相近、需要多小程序/H5 复用、团队前端能力强的产品；重原生交互、复杂 canvas、强性能、平台特有能力多时，适配成本可能超过收益。
  • 选型看共享率而不是端数量：业务模型、API client、校验和埋点较容易共享；UI 与平台能力要允许端侧差异化。
  • 工程上需维护能力矩阵、条件编译边界、端到端测试、分包与首屏、登录支付分享差异、目标端版本回归。
  • 项目引用：经历记录确认有 Taro、微信小程序经验；没有资产材料支持某个具体小程序指标，因此回答选型逻辑，不编项目数字。
延伸联想

指出小程序性能瓶颈常涉及逻辑层与视图层通信、setData 体量/频率和包体，跨端框架不能替平台约束消失。

边界与常见误区

“我会明确区分可共享业务层与必须端适配的能力。若某个目标平台 API 差异不确定，先做能力矩阵和关键链路 POC，不承诺百分百复用。”

21Electron 与 Tauri 的架构、安全和成本有什么差异？
为什么重要

关键在于确认桌面端选型能否超越“包体大小”。

要点
  • Electron 打包 Chromium + Node.js，主进程管理窗口与系统能力，renderer 承载 Web UI，通过 IPC 通信；生态成熟、一致性高，但包体和基线内存通常较大。
  • Tauri 通常使用系统 WebView，Rust 后端提供原生命令与能力，包体更小、攻击面可细粒度收敛；代价是不同 OS WebView 差异、Rust/插件能力和调试门槛。
  • Electron 安全底线：contextIsolation: true、关闭 renderer 的 Node integration、sandbox、preload 只暴露白名单 API、校验 IPC sender/参数、限制导航与新窗口、CSP、依赖与自动更新签名。
  • Tauri 也不是天然安全：命令白名单、capability/permission、输入验证、更新签名、Web 内容来源同样重要。
  • 项目引用：桌面端医疗助手采用 Electron，本人仅参与协同，不能说自己独立开发；更合适的表述是“在 AI医疗助手产品多端交付中参与桌面端协同，并主导企微/Web/接口/部署链路”。个人作品小哒 Coda 也有 Electron 跨平台客户端，可按经历记录事实引用。
延伸联想

主动纠正贡献边界会增加可信度：“我对桌面端医疗助手的价值主要在跨端产品线与交付治理，不把团队仓库算成个人独立作品。”

边界与常见误区

“我能从运行时、IPC、系统 WebView、包体和安全边界做选型；Tauri 某一版本的 capability 配置细节我会按官方文档验证，不实践中猜。”

22Electron 主进程、渲染进程和 IPC 应如何设计，才能避免安全问题与架构失控？
为什么重要

进一步讨论桌面端生产工程能力。

要点
  • renderer 视为不可信 Web 环境，只通过 preload 暴露窄接口；IPC 使用明确 channel、schema 校验、鉴权和错误码，避免万能 execute 或任意文件路径接口。
  • 主进程管理窗口、菜单、系统托盘、文件和更新；业务领域逻辑尽量放可测试模块，不让 main.ts 变成巨型控制器。
  • 长任务异步化并可取消，IPC 不传超大对象；流式数据用有界通道或批量传输。窗口销毁时清监听，防止重复订阅与泄漏。
  • 自动更新需要签名、来源校验、灰度、失败恢复；日志脱敏，崩溃分别覆盖 main/renderer。
  • 项目引用：可联系企业微信医疗助手的并发守卫、乐观锁，以及独立完成的本地 HID 边界方案，说明跨进程/跨设备动作需要幂等和权限边界；不要说 HID 方案一定通过 Electron 实现。
延伸联想

把 IPC 当内部 API 治理：契约、版本、权限、观测和兼容，而不是随手事件总线。

边界与常见误区

“我先守住 renderer 不可信、preload 最小授权、IPC schema 校验和更新签名四条。具体库选择可以按现有工程再定。”

四、多端协同与技术治理（23—27）

23什么场景坚定选原生，什么场景优先跨端？
为什么重要

关键在于理解负责人是否能把技术、业务与组织成本统一起来。

要点
  • 原生优先：核心体验就是相机/音视频/传感器/低延迟交互；离线与后台复杂；无障碍和平台最新能力关键；性能、功耗、隐私或审核风险高。
  • 跨端优先：多端流程高度同构、上线周期紧、UI 以标准业务组件为主、团队资源有限、品牌一致性价值高，且平台特有能力可由少量插件覆盖。
  • Web/H5 优先：内容、运营、管理后台和高频发布；桌面壳适合复用 Web 资产并补系统能力。
  • 决策表至少包含体验上限、系统能力、交付时间、团队技能、复用率、包体/性能、发布机制、长期 TCO 和退出成本。
  • 项目引用：AI医疗辅助App选择 iOS 原生可证明 SwiftUI、Vision OCR、Core Data 的端侧闭环；AI医疗助手产品用企微 Web + Electron + 本地边界方案，体现按宿主能力拆分，而不是所有端强行同构。
延伸联想

给出原则：“共享业务规则和协议，不追求 UI 代码 100% 共享。”这通常比“统一技术栈”更成熟。

边界与常见误区

“我会先做关键能力清单和 TCO 表，对最危险的系统能力做 POC。没有数据时不凭个人技术偏好拍板。”

24同一产品同时有 iOS、Web、Electron、企微端，哪些应该共享，哪些不该共享？
为什么重要

关键在于理解多端架构边界。

要点
  • 共享：领域术语、OpenAPI/事件 schema、鉴权语义、错误码、权限模型、埋点字典、设计 token、AI prompt/version 与评测口径。
  • 可生成：API client、类型、mock、契约测试；生成物要有版本与兼容策略。
  • 谨慎共享：业务规则可抽无 UI 核心库或由服务端统一，但离线规则需版本化；不要为了复用把所有端拖进同一语言或超级仓库。
  • 不强求共享：导航、交互、系统权限、存储实现、可访问性和平台特有 UI。共享率不是 KPI，交付质量和变更一致性才是。
  • 项目引用：企业微信医疗助手、Electron 桌面端医疗助手和 Web 产品线适合说明“统一服务契约与发布治理、端侧适配宿主能力”；AI医疗辅助App则是独立 iOS 原生证据。
延伸联想

提出 schema-first + contract test，降低多端联调靠口头同步的风险。

边界与常见误区

“我会优先统一协议、业务语义和质量口径，不会为了代码共享牺牲平台体验。具体复用层由变更频率和团队边界决定。”

25多端版本不一致、接口演进和 AI 流式协议如何治理？
为什么重要

关键在于理解线上兼容、灰度与可观测能力。

要点
  • API 默认向后兼容：新增可选字段、避免改变既有语义；破坏性变更显式版本化。客户端上报 app/platform/build/capability，服务端按 capability 降级，而非只按版本字符串猜。
  • 流式协议把 event type、request id、sequence、delta、done、error、usage 等建模清楚；处理断线、重复、乱序、取消与最终态，不能只拼字符串。
  • 用 OpenAPI / JSON Schema、契约测试、mock server 和兼容窗口；服务端发布先兼容旧端，客户端覆盖率达标后再清理旧逻辑。
  • feature flag、灰度、指标按端/版本切片；最低版本强更只用于安全或无法兼容的情况，并设计用户路径。
  • 项目引用：某三甲医院智能代理有 SSE 流式对话；企业微信医疗助手有并发守卫和乐观锁；这些可以支撑“流式与并发治理”回答，但不要混说为同一个仓库。
延伸联想

强调 AI 返回不仅有 transport error，还要区分模型拒答、工具失败、内容安全、超时和部分完成，端上状态机必须显式。

边界与常见误区

“我的底线是先兼容旧客户端、事件可幂等、灰度可观测、清理有覆盖率依据。某个协议字段可以与后端协作确定，不靠口头约定。”

26如何治理多端团队的技术栈、质量标准与发布节奏？
为什么重要

关键在于确认 7 年管理经验能否转化为工程机制。

要点
  • 建立技术雷达与准入流程：核心/试用/观察/淘汰；新框架需业务收益、owner、POC 数据、升级与退出方案，避免团队按个人喜好扩栈。
  • 建共同质量门：lint/typecheck/test、关键 E2E、性能预算、安全扫描、隐私清单、release checklist；平台专项指标由对应 owner 负责。
  • 统一 release train、语义化版本/tag、changelog、环境与分支策略、制品可追溯、灰度/回滚；保留端侧必要自主性。
  • 通过 RFC/ADR 记录关键决策；用组件库与 design token 提升一致性，但平台交互规范优先；轮值、复盘和知识库消除单点。
  • 项目引用：AI医疗助手产品审计 5 个仓库，发现默认分支空壳、真实代码在 dev、tag 缺失，推动 tag、分支清理与“分支—文件—改动”映射；另有 30+ 验收/排障文档。这是最适合本题的负责人证据。
  • 移动端治理证据：某金融科技公司指导团队完成 Flutter 落地并重构 App，某到家服务平台领导 3 个团队从原生转向 Flutter，证明技术栈治理不仅是制定规范，也包括选型、迁移、团队赋能和多项目落地。
延伸联想

用真实治理问题开场，而不是背框架：“我遇到过代码在 dev、默认分支空壳、tag 缺失，先解决可追溯性，再谈高级平台化。”

边界与常见误区

“我不会追求所有端工具完全统一。我会统一质量底线、协议和发布证据，把平台实现权交给主程，并用指标验收。”

27医疗 AI 多端产品如何处理隐私、安全、离线与可观测性？
为什么重要

关键在于理解行业意识和端到端风险控制。

要点
  • 数据最小化：只采必要字段，端侧与传输加密，密钥进系统安全存储，日志/埋点/崩溃信息脱敏，截图与剪贴板按风险控制，明确缓存与删除周期。
  • 权限按需、临时、可解释；相机/相册/OCR 失败有替代流程。端侧 OCR 可减少原图上传，但仍需明确产物是否敏感。
  • AI 输出标注辅助性质，关键医疗结论保留人工确认、来源与审计；prompt、模型、知识库和规则版本可追踪。
  • 离线要区分只读缓存、可编辑草稿和待同步队列；用 idempotency key、版本号、冲突策略，恢复后可重放。不要把“离线可用”泛化成所有功能都可用。
  • 可观测性按端/版本/网络/模型切片，覆盖崩溃、ANR、卡顿、流式首 token、完成率、取消率、OCR 失败和同步冲突；不记录原始敏感内容。
  • 项目引用：AI医疗辅助App的端侧 Vision OCR、Core Data可作为端侧能力案例；某三甲医院项目有数据安全合规 9 阶段整改证据；回答时区分项目，不说AI医疗辅助App已实现所有上述措施。
延伸联想

指出医疗 AI 的“正确率”不只是模型指标，还包括数据来源、人工复核、失败降级和审计可追溯。

边界与常见误区

“我不会声称单靠端侧加密就合规。会与安全、法务和业务共同做数据流图、分类分级和威胁建模，我负责把结论落成权限、存储、日志、审核和测试清单。”

五、系统设计题（28）

28如果要为同一个 AI 医疗产品同时建设 iOS 原生 App 和 Web 端，你怎么做技术选型、架构与团队分工？
为什么重要

综合考察需求澄清、端云边界、AI 流式架构、数据安全、多端协作和负责人决策。

要点
  1. 先澄清约束，不急着画框架
  • 用户是谁：医生、患者还是运营人员；核心路径是拍摄/OCR、AI 问诊、病历查阅还是后台配置。
  • 是否需要弱网/离线、推送、相机与端侧识别；iPad 是否为主设备；Web 是否覆盖移动浏览器；合规边界、上线时间、团队规模和目标 DAU。
  1. 技术选型
  • iOS 采用 SwiftUI；相机、Vision OCR、本地安全存储和系统生命周期走原生能力。最低系统版本决定 Observation、Navigation 与并发 API 选择。
  • Web 采用团队成熟的 React + TypeScript，负责跨设备访问、内容/管理和快速迭代。若患者核心链路只是标准表单，应重新评估是否所有功能都需要双端原生实现。
  • 不共享 UI 源码，统一设计 token、领域模型、OpenAPI / 事件 schema、错误码、权限和埋点字典。
  1. 端云架构与数据流
  • API Gateway / BFF 之后分认证授权、患者/病历领域服务、文件服务、AI Orchestrator、审计与通知；是否真的拆微服务取决于规模，小团队可先模块化单体。
  • AI 请求返回 task/request id；SSE 提供 typed events，支持取消、超时、重连、幂等和最终结果查询。长任务不依赖客户端持续在线。
  • 图片可在 iOS 端先做方向修正、压缩和 OCR；是否上传原图由诊疗与合规需要决定。服务端保存 AI 模型/prompt/知识来源版本和人工确认记录。
  • 本地 Core Data 只保存必要缓存、草稿与同步队列；服务端作为跨端事实源。冲突按数据类型选择 server wins、字段合并或人工处理。
  1. 安全、审核与可靠性
  • OIDC/OAuth 类认证、短期 token 与安全存储、TLS、服务端细粒度授权；日志脱敏、数据留存/删除、审计、SDK 隐私清单。
  • AI 输出有免责声明、证据来源、人工确认和失败降级。App Store 提前准备隐私标签、权限用途、审核账号、年龄分级与医疗声明。
  • 指标覆盖首屏、OCR、SSE 首 token/完成率、崩溃、同步冲突和 AI 质量；按端/版本灰度，服务端保持旧客户端兼容。
  1. 团队分工
  • 一个业务/架构 owner 对端到端结果负责；iOS owner 负责原生体验、系统能力与上架；Web owner 负责 Web 体验和前端工程；后端/AI owner 负责领域 API、Agent 编排、评测与稳定性；QA/安全从需求阶段参与。
  • 以 feature squad 交付纵向业务，同时保留 iOS/Web/后端 chapter 维护平台规范。先用 walking skeleton 打通登录—请求—流式返回—审计—发布，再并行扩功能。
  • 契约先行、mock 并行、每日自动契约测试；ADR 记录关键决策。平台细节由主程负责，负责人把控边界、指标、风险和交付。
  1. 真实经历落点
  • 移动端能力是一条连续演进线：2014 年以 iOS 原生入行，2015—2018 年独立主导 Android 项目整体架构，此后在某金融科技公司和某到家服务平台两次领导 Flutter 落地/转型；最近两年职责重心转向前端、AI 应用研发和团队管理。
  • AI医疗辅助App证明可以独立完成 SwiftUI + MVVM + Core Data + Vision OCR + Combine + Swift Charts，并完成 v1.2.0→v1.2.1 多轮审核上架。
  • 企业微信医疗助手 / AI医疗助手产品证明了 Web、企业微信、桌面端、接口与部署协同，以及并发守卫、乐观锁和多仓发布治理。
  • 桌面端医疗助手 Electron 仓库中本人仅参与协同，应表述为产品线协同经历，不能包装成独立桌面端研发。
  • 某三甲医院智能代理的 SSE 流式对话可作为 AI 流式协议实践证据；不要与AI医疗辅助App混成同一项目。
延伸联想

先确认三个决定架构的问题：“核心用户与关键路径是什么？原图是否允许上云？离线要求和上线时间是什么？”然后给出“首版模块化单体 + schema-first + 双端原生适配”的可落地方案，并说明何时才拆服务。

边界与常见误区

“我不会在需求未知时直接报框架名。我的确定性是：iOS 系统能力原生化、Web 发挥快速迭代、服务端统一事实源和 AI 任务、协议契约共享、敏感数据最小化；团队规模、离线和合规要求明确后，我再把缓存、服务拆分和人员配置量化。”
