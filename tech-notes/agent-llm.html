一、Agent 架构与编排（1—8）

1ReAct、Plan-and-Execute 和固定工作流分别适合什么场景？
为什么重要

关键在于判断是否理解 Agent 的自主性与确定性之间的取舍，而非只会背模式名。

要点
  • ReAct 让模型在“思考—行动—观察”循环中动态选工具，适合开放式探索、步骤事先未知的任务；代价是调用次数、延迟和行为不确定性更高。生产中不应暴露完整思维链，可记录结构化的决策摘要与工具轨迹。
  • Plan-and-Execute 先形成显式计划，再逐步执行并按结果重规划，适合长任务、步骤可审计、可并行的场景；关键是计划版本、步骤依赖、完成条件和重规划上限。
  • 固定 DAG/工作流适合医疗表单、审批、内容生产等路径基本确定且需强审计的业务。并不是“越 Agent 越先进”，确定性流程应尽量代码化。
  • 实际系统常为混合架构：外层状态机约束阶段，阶段内部让模型做有限决策。NovelReel 可作为真实例子：小说资产拆解→分镜→多模态生成→ffmpeg 是明确三层编排，模型负责语义工作，状态持久化、失败降级和断点续跑由工程控制。
延伸联想

可进一步确认：“这个业务更看重探索能力，还是合规、时延与可回放？不同答案会直接改变编排模式。”

边界与常见误区

我不会仅凭模式名称做选型。我会先把任务是否可枚举、错误成本、审计要求和预算量化，再决定用固定工作流、受限 Agent 还是二者混合；具体框架 API 我可以快速补齐。

2多 Agent 是否一定优于单 Agent？如何划分 Agent 边界？
为什么重要

关键在于识别是否有“为了多 Agent 而多 Agent”的过度设计倾向。

要点
  • 多 Agent 的价值来自上下文隔离、专业角色、权限隔离和任务并行，不来自角色数量。若只是多个不同 system prompt 串行互聊，往往增加 token、延迟和误差传播。
  • 边界优先按能力与责任划分：输入输出契约清晰、可独立评测、权限不同、失败可局部恢复，才值得拆分。共享数据库不等于共享全部上下文。
  • 编排者应负责路由、依赖、预算、超时和终止；执行 Agent 只获得完成当前任务所需的最小上下文和工具权限。
  • 需要定义冲突解决方式：规则优先、裁判模型、置信度或人工审核；裁判不能成为无监控的单点真相。
  • NovelReel 的“三层”重点不是模拟人格，而是把资产、分镜、生成执行拆成可验证阶段，适合说明工程型多 Agent 的边界。
延伸联想

指出“我通常先证明单 Agent + 工具不够，再拆多 Agent”，并给出拆分后的独立成功率、时延和成本指标。

边界与常见误区

我对具体多 Agent 协议不会假装有大规模生产数据，但我能先用契约、权限和可评测性控制复杂度，并通过灰度数据验证拆分是否真的带来收益。

3如何用状态机管理一个长生命周期 Agent？
为什么重要

关键在于理解能否把概率模型纳入确定性软件工程。

要点
  • 状态应显式建模，如 PENDING/RUNNING/WAITING_RETRY/WAITING_HUMAN/SUCCEEDED/FAILED/CANCELLED，业务阶段另用 stage 表示，避免一个字段承载两套语义。
  • 每次转移记录 run_id、step_id、state_version、input_hash、output_ref、attempt、model/tool_version、timestamp，使用乐观锁或条件更新避免并发重复推进。
  • 转移必须有守卫条件、超时、最大重试次数和终止状态；副作用通过幂等键、事务消息或 outbox 保证“至少一次执行但业务效果一次”。
  • 暂停点保存的是可恢复状态和产物引用，不只是聊天记录。恢复时校验依赖产物和版本，必要时从最近安全检查点重跑。
  • NovelReel 已真实支持状态持久化与断点续跑，可如实讲设计目标和 44 tests；不要声称使用了材料里未确认的特定队列或数据库。
延伸联想

画出“控制面状态”与“模型语义输出”两条线，强调模型不能自行宣布任务成功，成功必须由程序化验收条件确认。

边界与常见误区

我未必能实践中给出当前团队现有中间件的最佳写法，但长任务的核心原则明确：状态显式化、转移可审计、副作用幂等、检查点可恢复。

4Agent 的短期记忆、长期记忆和业务状态有什么区别？
为什么重要

关键在于判断是否把“把历史全塞进上下文”误当记忆管理。

要点
  • 短期记忆服务当前会话，可用最近消息、摘要和关键事实组合；长期记忆是跨会话可复用的用户偏好或事实；业务状态是订单、任务、筛查进度等权威数据，应在业务库中，不应依赖模型记住。
  • 写入长期记忆必须有提取、去重、置信度、来源、有效期和用户可更正机制。敏感医疗信息默认不因“可能有用”就长期保存。
  • 读取用相关性、时效性和权限过滤，并限制注入条数；摘要需要保留来源，防止摘要错误不断累积。
  • 记忆污染比遗忘更危险。重要事实应回查权威系统，模型记忆只作辅助线索。
延伸联想

用企微家医场景说明：会话上下文、居民档案、待办状态必须三层分离，并进一步讨论对方是否已有数据授权与删除机制。

边界与常见误区

我会把“记忆”拆成会话上下文、可检索事实和权威业务状态分别设计；具体向量记忆实现可以由后端同事深入，但数据边界和一致性由负责人先定清楚。

5Function Calling 的工具 Schema 应怎样设计？
为什么重要

关键在于理解工具调用的可靠性、可维护性与模型友好度。

要点
  • 工具应职责单一、名称和描述无歧义，参数尽量使用枚举、格式、范围、必填项和示例；不要设计一个万能 execute(action, payload)。
  • 返回结构区分 data、error_code、retryable、message_for_model、trace_id，业务错误不能伪装成 HTTP 200 的自然语言。
  • 查询与变更工具分开；高风险变更使用 dry-run、确认 token 或二阶段提交。模型提出意图，服务端重新鉴权和校验，绝不信任模型传来的 user_id、金额或权限。
  • Schema 版本化并做契约测试；对参数校验失败可有限次让模型修正，超过阈值转人工或降级。
  • 对模型只返回完成下一步所需字段，避免工具原始响应挤占上下文或泄露敏感数据。
延伸联想

实践中给出“查询居民历史”和“发送健康建议”两个分离工具，并指出后者需要明确收件人确认与审计。

边界与常见误区

我没有必要背某一家模型的 JSON 方言，但工具设计原则不会变：窄接口、强校验、最小权限、结构化错误和可审计副作用。

6如何防止 Agent 工具调用越权或造成不可逆后果？
为什么重要

关键在于确认生产安全意识。

要点
  • 模型不是安全边界。每次工具调用都由网关基于真实用户身份、租户、资源和操作重新授权。
  • 工具按风险分级：只读可自动执行；低风险写操作可撤销；高风险操作需人工确认、双人审批或根本不开放给模型。
  • 参数白名单、资源作用域、速率限制、预算上限、超时、沙箱和网络出口控制缺一不可；禁止任意 SQL、Shell 和任意 URL 抓取。
  • 将来自网页、知识库、邮件的内容视为不可信数据，不能让其中的指令提升权限。
  • 全链路保留谁发起、模型为何路由、调用参数摘要、结果和审批证据，支持追责和回放。
延伸联想

提出 capability token：只对某次运行、某个资源、某种动作、短时有效，比给 Agent 长期高权限凭证更安全。

边界与常见误区

安全实现细节需要结合当前团队 IAM，但我的底线是模型永不直接持有泛化权限，所有写操作都要在确定性服务端再次鉴权和验证。

7Agent 失败时如何设计重试、降级和人工接管？
为什么重要

关键在于理解异常分类，而非简单“失败就重试”。

要点
  • 先分类：瞬时基础设施错误可指数退避加抖动；限流按 Retry-After；参数/权限错误重试无意义；内容安全拒绝不可换模型绕过；低置信度应转人工或保守回答。
  • 重试必须有次数、总时长和成本预算，并以幂等键避免重复写入。不同模型重试前判断格式、能力和上下文是否兼容。
  • 降级维度包括模型、工具、功能和体验：强模型→轻模型、实时→异步、自动执行→建议草稿、个性化→通用安全回复。
  • 人工接管时提供问题摘要、已执行步骤、证据、失败原因和建议动作，而不是丢给人工一段完整日志。
  • NovelReel 的模型失败降级与断点续跑，以及某三甲医院语音引擎从多供应商降级到后续收敛掉 Azure，都是可引用的真实实践。
延伸联想

强调“降级不是偷偷降低质量”，面向用户要显示状态并保护核心业务承诺。

边界与常见误区

具体阈值要通过线上数据校准；我能先建立错误分类、重试预算、幂等与人工接管四个基本机制，再逐步调参。

8如何观测和调试 Agent，而不是只看最终回答？
为什么重要

关键在于判断是否具备 LLMOps 思维。

要点
  • 一次运行用统一 trace_id 串起用户请求、计划、模型调用、工具调用、检索、状态转移和最终响应；记录版本、耗时、token、成本、错误码与脱敏后的输入输出引用。
  • 指标分层：系统指标（可用性、P95、错误率）、Agent 指标（任务成功率、步骤数、重试率、工具成功率）、质量指标（事实性、引用命中、人工接管率）和业务指标（任务完成、医生采纳等）。
  • 支持按版本重放，但外部副作用默认 mock/dry-run；建立失败轨迹聚类，优先修复高频系统性失败。
  • 日志与评测样本之间建立闭环：生产失败脱敏后进入回归集，发布前进行版本对比。
延伸联想

可进一步确认“现在能否回答某次错误是模型、检索、工具还是业务状态导致的？”这能迅速暴露观测体系成熟度。

边界与常见误区

我没有绑定某个 tracing 产品，重点是先统一运行标识和事件模型；产品选型可以再结合现有 OpenTelemetry 或平台能力落地。

二、RAG 全流程（9—16）

9请完整讲一遍生产级 RAG 链路。
为什么重要

关键在于检查是否只懂“向量库 + Prompt”。

要点
  • 离线链路：数据源接入→解析/OCR→清洗去重→结构识别→切片→元数据与权限标注→embedding→索引→质量校验与版本发布。
  • 在线链路：问题理解/改写→权限和元数据过滤→稀疏与稠密召回→融合→rerank→上下文组装→带引用生成→答案校验/拒答→反馈记录。
  • 横向能力：多租户权限、版本与删除传播、监控、离线评测、线上实验、成本和时延预算。
  • 质量定位要分层：解析是否丢信息、召回是否找到证据、排序是否把证据放前面、生成是否忠于证据。只看最终答案无法定位瓶颈。
  • 边界要如实说：某三甲医院知识库/RAG 后端同事深度参与更多，自己主要负责知识库交互设计；可以讲完整设计判断，但不虚构亲手实现过的索引参数。
延伸联想

先问文档类型、更新频率、权限模型、答案是否必须有出处；这四项往往比先选向量库更决定架构。

边界与常见误区

RAG 的底层检索实现不是我在某三甲医院项目里贡献最深的部分，后端同事参与更多；但作为负责人，我能把摄取、召回、排序、生成、评测与权限的一整条链路拆清楚，并组织专项验证。

10Chunk 应如何切？固定长度、递归切分和语义切分怎么选？
为什么重要

关键在于理解是否理解切片对召回和上下文完整性的影响。

要点
  • 固定 token 切分简单稳定，适合作基线，但可能切断表格、条款和医学结论；递归切分按标题、段落、句子逐级保结构；语义切分按语义突变划界，质量可能更好但成本和稳定性更难控。
  • 先尊重文档结构，再限制 token。说明书可按章节/条款，FAQ 按问答对，病历按字段与时间，表格需保留表头和行关系；没有通用最优 chunk size。
  • chunk 太小语义不完整，太大则召回不精准、上下文昂贵。可用 parent-child：小块召回，大块返回；适度 overlap 只解决边界问题，不能替代结构切分。
  • 元数据至少保留来源、章节、版本、时间、权限、父子关系和定位信息；用目标问题集对不同策略做召回率和最终答案对比。
延伸联想

建议拿 50—100 个真实问题做切片实验，而不是争论 512 还是 800 token。

边界与常见误区

我不会声称有一个万能尺寸。我的做法是以文档结构为主、token 上限为约束，并用真实问答集测 Recall@K 和上下文完整率后定参数。

11Embedding 模型如何选型，如何迁移？
为什么重要

关键在于判断是否考虑领域、语言、成本和版本治理。

要点
  • 评价维度包括中文与医疗语义表现、长文本上限、向量维度、吞吐/成本、部署方式、数据出境、模型稳定性及与检索任务的匹配。
  • 不以公开榜单直接替代业务评测；用真实 query-document 标注集测 Recall@K、MRR/nDCG，并关注缩写、同义词、否定、药名和数值条件。
  • 查询与文档按模型要求加 instruction；向量归一化和相似度度量需匹配。embedding 版本、切片版本和索引版本应可追踪。
  • 迁移通常双写/回填新索引，离线对比后灰度切读；新旧 embedding 不能直接混在同一空间比较，回滚保留旧索引。
延伸联想

把“国产化/私有化与医疗数据不出域”作为选型的一等约束，而非事后补丁。

边界与常见误区

具体型号我会根据当前可用模型做小规模 benchmark，不凭记忆报榜单；我能保证选型指标、版本隔离和灰度迁移方法正确。

12向量检索、BM25 和混合检索各自解决什么问题？
为什么重要

关键在于理解召回层基本功。

要点
  • 向量检索擅长语义相似和同义表达，但对精确编码、罕见药名、数字和专有名词可能不稳；BM25 擅长关键词精确匹配，可解释性强，但不理解改写和语义近似。
  • 混合检索并行召回后融合，常用 RRF 按排名融合，避免直接比较不同体系的原始分数；也可根据问题类型动态调权。
  • 先做权限/租户过滤，或使用支持过滤的 ANN，避免先召回无权文档再“希望后面过滤干净”。
  • Query rewriting、多路查询能提高召回，但会增加延迟和噪声，需要去重和预算控制。
延伸联想

举“药品商品名/疾病别名”和“检查指标编号”两类问题，说明为什么医疗知识库更需要混合检索。

边界与常见误区

我不会编造项目里的具体融合权重；原则上会以 BM25 + dense 建基线，用 RRF 融合，再按真实问题集调权和做消融实验。

13Rerank 为什么有效，应该放在哪里？
为什么重要

关键在于判断是否理解“高召回、精排序”的两阶段检索。

要点
  • 初召回为了速度，用 BM25/向量从大库取几十到上百候选；cross-encoder reranker 联合阅读 query 与 chunk，相关性判断更准但计算更贵，再选少量上下文。
  • 可先融合去重，再 rerank；候选太少会错过答案，太多增加时延。需要根据延迟预算测 top-N 和最终 top-K。
  • 领域 reranker 要用医疗问题验证；相关不等于可信，还要结合来源权威性、版本时效、权限和多样性。
  • 评测不能只看最终生成，应分别看 Recall@N、nDCG/MRR、rerank 后证据覆盖率和端到端事实性。
延伸联想

提出按问题复杂度动态启用 rerank：明确编号查询走快速通道，复杂自然语言问题走完整链路。

边界与常见误区

我没有亲自在某三甲医院项目里调过 reranker 的生产参数；但我清楚它位于高召回之后、上下文组装之前，具体 N/K 会通过离线评测和 P95 延迟共同决定。

14如何抑制 RAG 幻觉并实现“无证据就不回答”？
为什么重要

关键在于检查是否错误地认为接入知识库就不会幻觉。

要点
  • 幻觉可能来自错误解析、漏召回、错排序、冲突资料和生成越界，要分层治理。
  • Prompt 明确仅基于证据回答、逐项引用、证据不足则说明不足；但 Prompt 不是硬保证，还需检索阈值、来源白名单、时效规则和输出校验。
  • 让模型先提取可支持的 claim 与证据，再生成；对关键结论做 citation entailment/事实一致性检查。医疗高风险建议可强制人工审核或只提供信息导航。
  • 置信度不要只用模型自报，可综合召回分数、来源数量/一致性、问题覆盖度和校验结果；校准后才可用于拒答阈值。
  • UI 展示可点击出处、版本和原文高亮，帮助医生核验。
延伸联想

强调“正确拒答率”也是产品指标，不能只追求回答率。

边界与常见误区

我不会承诺技术上消灭幻觉；我会通过权威证据、引用校验、风险分级和人工兜底，把不可控生成变成可观测、可拒绝、可追溯的风险。

15知识库更新、删除与索引一致性如何保证？
为什么重要

关键在于理解生产数据管道与一致性意识。

要点
  • 每份文档使用稳定 document_id，每次内容变化生成版本；chunk ID 可由文档版本、位置和内容 hash 派生，支持去重和差量更新。
  • 业务元数据与索引更新用任务状态机/outbox 协调，不能假设数据库和向量库能天然分布式事务。索引先构建和校验，再原子切换 alias/version。
  • 删除需传播到对象存储、关键词索引、向量索引、缓存和备份策略；敏感数据可先 tombstone 阻断在线读取，再异步物理清除并留合规审计。
  • 处理乱序和重复事件：版本比较、幂等消费、失败重试、死信队列和对账任务。定期比对源数据与索引的数量、hash、版本和权限。
  • 对强时效内容设置 effective_at/expires_at，回答中标注文档版本。
延伸联想

提出“可见性 SLA”：业务更新后多久可检索、撤回后多久不可见，应由产品和合规共同确认。

边界与常见误区

具体中间件要看现有架构，但我会用版本化索引、幂等事件、别名切换和定期对账保证最终一致，并为紧急撤回保留强制阻断通道。

16RAG 质量下降时，你如何系统排查？
为什么重要

关键在于理解分层诊断能力。

要点
  • 固定失败问题与期望证据，依次查看原文解析、chunk、metadata/ACL、query 改写、各路召回、融合、rerank、上下文截断、Prompt 和最终输出。
  • 若正确证据不在候选集，是摄取/召回问题；在候选集但排名低，是排序问题；已进入上下文仍答错，是生成或冲突处理问题。
  • 对近期变更做版本对比：解析器、切片、embedding、索引、reranker、Prompt、模型任何一项都可能引发回归。
  • 建立 golden set 和逐层指标，做消融实验而非同时改多个参数；线上按文档类型、问题类型、租户分桶观察。
延伸联想

排查时先要求一条完整 trace，而不是直接建议“换更大的模型”。

边界与常见误区

我的 RAG 实现深度不如长期专做检索的后端同事，但我能以证据是否在各阶段丢失为主线定位，并组织 embedding、检索和业务专家共同完成专项优化。

三、Dify 与自研框架选型（17—20）

17Dify 与自研 Agent 框架，你的选型标准是什么？
为什么重要

关键在于确认两类经验是否真实，并考察负责人判断力。

要点
  • Dify 优势是可视化编排、模型/知识库快速接入、运营与业务可共同查看流程，适合需求变化快、场景较标准、先验证价值的 0→1 阶段。
  • 自研适合复杂状态机、强事务/低延迟、深度业务集成、特殊多模态流水线、精细成本控制、可测试可回放或平台锁定风险不可接受的场景。
  • 判断维度：交付速度、流程复杂度、扩展性、可观测性、测试能力、权限合规、团队技能、吞吐时延、单位成本、可迁移性和总拥有成本。
  • 不是二选一：Dify 可做编排控制台，自研服务承载企业微信、会话存档解密、素材推送、看板和核心业务；高复杂链路再逐步下沉。
  • 真实案例：AI医疗助手产品（基于Dify打通20+医疗场景智能体）中，Dify 是编排层的一部分；NovelReel 是个人项目的自研三层 Agent 编排。必须明确二者项目属性。
延伸联想

一句话定调：“低代码买的是验证速度，自研买的是关键链路控制权；最终看业务生命周期内的 TCO。”

边界与常见误区

我不会先站队框架。我会选一个代表场景做 spike，用交付周期、P95、失败恢复、测试覆盖和单位任务成本做同口径比较。

18如何证明在全科助手中不是“只用了 Dify 现成功能”？
为什么重要

核实实践者的实际贡献边界。

要点
  • 先准确划界：Dify 提供工作流、模型和知识库编排；企业微信接入、会话存档解密、图文语音消息、素材推送、看板统计等由自建服务和多端产品承载。
  • 自己真实负责从需求、设计还原、React 开发、接口联调、ChatSim 群聊模拟、企微/桌面端集成到部署运维；企微助手前端由本人承担核心开发工作，在团队中贡献突出。
  • 可讲生产边界：键盘连发可能触发 AI 重复回复，因此做并发守卫；用乐观锁防止状态覆盖。这些是低代码平台外的真实工程问题。
  • 不把团队成果全部据为己有；涉及 Dify 工作流内部节点和后端实现时，说明自己掌握整体链路，具体模块按实际贡献回答。
延伸联想

把系统画成“渠道层—业务服务层—Dify 编排层—模型/知识库层”，自然呈现自己的端到端职责。

边界与常见误区

某个具体 Dify 节点若不是我亲手配置，我会明确说明；我的核心贡献是把编排能力接入真实企微业务并解决多端、并发、状态、发布和运维问题。

19低代码平台在生产环境最常见的技术债是什么？
为什么重要

关键在于理解是否经历过平台规模化后的问题。

要点
  • 工作流复制膨胀、节点配置漂移、Prompt 隐式依赖、缺少代码评审与自动化测试、环境差异和密钥散落。
  • 平台日志可能不足以定位跨服务链路；复杂分支导致可读性急剧下降；升级、插件和模型适配带来锁定风险。
  • 治理方式：工作流导出进 Git、版本/tag、配置与密钥分离、模板复用、命名规范、发布审批、回归集、灰度和回滚；关键逻辑下沉为可测试服务。
  • 结合真实发布治理经验可讲：曾审计 5 个仓库，发现默认分支空壳、真实代码在 dev、tag 缺失，并推动 tag、分支清理和映射文档化。不要说这些问题全都发生在 Dify 本身。
延伸联想

提出“工作流也应像代码一样有 owner、版本、测试、发布和退役流程”。

边界与常见误区

我没有把所有平台坑都踩遍，但会把工作流纳入软件交付治理；无法版本化、测试和回滚的关键逻辑，不会长期留在平台黑盒里。

20什么信号说明一个 Dify 工作流该下沉为自研服务？
为什么重要

关键在于理解演进式架构能力。

要点
  • 信号包括：分支/节点复杂到难以理解；需要事务、幂等、长任务恢复；P95 或并发不达标；测试与回放不足；细粒度权限/审计无法满足；平台成本显著；核心能力需跨场景复用。
  • 先抽取纯函数或高复用能力为 API/tool，不一次性重写；建立旧新链路的契约测试和影子流量比较。
  • 编排可继续留在 Dify，核心领域逻辑、状态和副作用归自研服务；只有控制面也成为瓶颈时再迁移。
  • 迁移完成标准不是代码重写，而是质量、时延、成本、可恢复性不退化且可回滚。
延伸联想

说明“平台边界应由可逆性决定”：先把最不可控、最关键的部分收回控制权。

边界与常见误区

我会用数据而不是个人偏好触发迁移：复杂度、故障、延迟、成本和合规中至少出现明确痛点，再按 strangler pattern 渐进替换。

四、多模型网关与降级容错（21—24）

21设计一个统一的 LLM 多模型网关，需要哪些能力？
为什么重要

关键在于理解模型抽象、路由、治理与可观测性。

要点
  • 统一请求/响应协议，但保留 capability registry：上下文长度、Function Calling、JSON、视觉、区域、价格、速率限制等；不能用最低公分母抹平模型差异。
  • 路由输入包括任务类型、风险等级、质量目标、时延 SLO、预算、租户策略和数据地域；输出为主模型与允许的 fallback 链。
  • 提供鉴权、配额、限流、缓存、重试、熔断、并发控制、内容安全、脱敏、审计和成本归集。
  • 模板与模型解耦并版本化；记录首 token、总耗时、token、成本、成功率、工具调用正确率和质量评测。
  • 回退前检查上下文长度、工具 schema、输出格式和安全策略兼容，避免“接口成功但语义失败”。
延伸联想

强调“网关不是简单反向代理，而是策略执行点和可观测控制面”。

边界与常见误区

我真实做得更深的是 TTS/ASR 多引擎统一与降级；LLM 网关可复用健康检查、路由、熔断和观测思想，但还要补上下文、能力与质量兼容层。

22成本、延迟、效果三者如何动态权衡？
为什么重要

关键在于判断是否会把模型选择转化为业务策略。

要点
  • 先按任务风险分层：医疗关键解释、高价值复杂任务优先质量；意图分类、改写、摘要等可用轻模型；不能全站默认最强或最便宜模型。
  • 建立质量底线与 SLO，在满足底线的候选模型中优化成本；路由可基于规则起步，再用历史数据训练/校准分类器。
  • 复杂度升级：轻模型先做，低置信或校验失败再升级强模型；同时注意两次调用可能增加尾延迟和总成本。
  • 缓存、Prompt 压缩、上下文裁剪、批处理和异步化通常比盲目换小模型更稳。
  • 用每个“成功任务”的成本，而不是每百万 token 单价作最终指标。
延伸联想

给出策略句：“质量是约束，成本是目标，延迟是 SLO；三者由场景风险分层，不用一个全局权重硬算。”

边界与常见误区

我不会实践中拍一个权重；会先定义各类任务的最低质量和延迟门槛，再用离线评测与真实流量测每成功任务成本。

23健康检查、熔断、重试和故障转移怎样配合？
为什么重要

关键在于理解分布式韧性设计。

要点
  • 健康分被动指标与主动探针组成：网络可达不等于模型可用，还要检测鉴权、首 token 延迟、限流和最小能力响应；探针需控频，防止放大故障。
  • 熔断按供应商、区域、模型和错误类型隔离，采用 closed/open/half-open；连续失败率、慢调用比例达到阈值后短路，半开少量探测恢复。
  • 重试只针对幂等、瞬时错误，指数退避加抖动并受总 deadline 限制；全链路共用 retry budget，防止各层叠加重试风暴。
  • 故障转移必须遵守数据地域、模型能力和成本上限；fallback 也失败时快速失败或异步排队，不无限级联。
  • 真实经历可讲某三甲医院讯飞/百炼/Azure 多 TTS/ASR 引擎降级，以及后续发现 Azure 维护成本与收益不匹配后下掉，体现“韧性不等于供应商越多越好”。
延伸联想

主动提出演练供应商超时、429、鉴权失效和局部质量退化四类故障，后者往往不能靠 HTTP 健康检查发现。

边界与常见误区

实际阈值要结合流量分布和供应商 SLA 调整；我能先把错误分类、熔断隔离维度、总超时与重试预算设计正确。

24为什么后来移除 Azure？如何判断“架构收敛”而不是能力退化？
为什么重要

核实真实项目并观察技术取舍能力。

要点
  • 如实回答：某三甲医院项目最初接入讯飞、阿里云百炼、Azure 多引擎做容错，后续因 Azure 的维护成本高、效果冗余而移除，简化架构。不要编造具体故障率或价格数字。
  • 多供应商会带来 SDK、音色/格式、鉴权、监控、合规、回归测试和团队认知成本；每增加一家都应证明边际韧性收益。
  • 下线前比较真实语料效果、可用性、覆盖能力和故障相关性；验证剩余供应商能覆盖核心场景，并准备灰度、回滚和观测。
  • 收敛的衡量是用户可用性和质量不下降，同时维护面、故障面和认知负担降低，而不是单看接口数量。
延伸联想

把这个案例上升为负责人原则：“冗余只有在故障不高度相关、且团队能持续验证时才有价值。”

边界与常见误区

当时可确认的判断是维护成本与实际收益不匹配，所以做了收敛；没有留存的精确指标我不会补造，但我会讲清评估维度和灰度验证方法。

五、LLM 评测与质量保证（25—29）

25如何建设一套面向医疗场景的 LLM 评测集？
为什么重要

核实真实评测经验及数据方法论。

要点
  • 先从业务任务和风险出发建立 taxonomy：医学知识、临床推理、信息抽取、遵循指令、拒答、安全等，并按科室、难度、问题类型和人群分层。
  • 公开集用于通用能力和行业可比性，业务自建集覆盖真实分布与失败边界；训练/调参/最终测试严格隔离，去重并防止公开集污染。
  • 每题保留来源、标准答案/评分 rubric、可接受变体、风险等级和版本；由专业人员复核高风险内容。
  • 真实案例：自建医疗LLM评测体系整合 MedQA 48,876 题、CMB 280,913 题，以及 HealthBench、PubMedQA，并制作全科、皮肤科等 100 题子集；完成 26 项细化指标设计与 10 项核心指标确认。可说“近 33 万题”，不要夸成全部人工标注。
  • 评测集不是一次性文件：生产失败脱敏入库、定期重采样、版本化，持续监控覆盖与陈旧度。
延伸联想

先区分“模型学科能力 benchmark”和“产品任务成功评测”，说明两者不能互相替代。

边界与常见误区

医学专业结论必须由临床专家把关；我的强项是评测工程、数据组织、指标体系和版本流程，不越界替代医生制定金标准。

2626 项指标为什么最终只确认 10 项核心指标？指标如何取舍？
为什么重要

关键在于判断是否能从完整性走向可运营性。

要点
  • 指标多不等于体系好。核心指标要与业务风险和决策绑定，能稳定测量、可解释、彼此不过度重复，并且团队有成本持续运行。
  • 建议用分层 scorecard：少量北极星/门禁指标负责版本决策，诊断指标负责定位原因，探索指标暂不进入发布门禁。
  • 医疗场景优先安全性、事实正确性、证据一致性、完整性、拒答恰当性等；流畅性不能抵消事实错误。高风险项可设“一票否决”，不简单加权平均。
  • 真实事实是“设计 26 项、确认 10 项核心指标”；若材料没有保存具体十项名称，应诚实说明，不实践中编造名单，可讲取舍原则。
延伸联想

主动说明指标要测 inter-rater agreement、方差和与人工结论的相关性，否则数字精确但没有决策价值。

边界与常见误区

我能确认当时完成了 26 项设计与 10 项核心指标确认；具体十项名称若实践中记不全我不硬背，但取舍依据是业务风险、可重复性、解释性和运行成本。

27LLM-as-a-Judge 有哪些偏差，如何控制？
为什么重要

关键在于理解对自动评测局限的认识。

要点
  • 常见偏差：位置偏差、偏爱长答案/特定文风、自我偏好、提示敏感、领域事实不足、评分漂移和被被评答案 prompt injection。
  • 使用清晰 rubric 和锚点样例，要求逐项结构化评分并引用证据；成对比较时交换顺序，多次采样或多 judge 处理边界样本。
  • judge 与被评模型尽量隔离；将候选答案当不可信数据，禁止其改写评分指令；固定 judge、Prompt、温度与版本。
  • 用专家标注集校准相关性、准确率和阈值，定期抽样人工复核；安全/医学关键结论不能仅靠 judge 自动放行。
  • 评测成本也要管理，可用规则/小模型初筛，复杂争议样本交强模型或人工。
延伸联想

说出“Judge 是测量仪器，也需要被评测”，并询问其与专家一致率而非只问模型名称。

边界与常见误区

LLM Judge 适合规模化筛查，不等于金标准；我会用小规模高质量人工集校准，并把低一致性、高风险样本转人工。

28自动评测、人工评测和线上业务指标如何结合？
为什么重要

关键在于理解完整质量闭环。

要点
  • 发布前：单元/契约测试保证工程正确，固定离线集做版本回归，规则与 LLM Judge 扩大覆盖，专家评审高风险样本。
  • 发布中：影子流量或小比例灰度，监控延迟、错误、成本、安全和质量代理指标；设置自动回滚门槛。
  • 发布后：任务完成、采纳/纠正、转人工、投诉等业务指标验证真实价值；用户点赞只能作为弱信号，不能直接等同医学正确。
  • 把线上失败按隐私要求脱敏、聚类和专家复核，进入新的回归集；防止只优化固定 benchmark。
  • 指标冲突时按风险优先级判断，不能用点击率提升掩盖事实性下降。
延伸联想

提出质量金字塔：“大量便宜自动测、少量高质量专家测、最终用真实业务效果验证。”

边界与常见误区

我会先建立一个小而可信的人工 golden set，再逐步引入自动评测扩规模；在没有校准前，不用自动分数独立决定医疗场景上线。

29如何判断一次 Prompt、模型或 RAG 升级真的更好？
为什么重要

关键在于理解实验设计与回归意识。

要点
  • 冻结评测集、评分规则和除被测变量外的配置，保存模型/Prompt/检索版本；多因素变化需消融实验，否则无法归因。
  • 同时看总体和分桶表现，报告均值、置信区间/显著性与失败类型；防止总体提升但某高风险科室退化。
  • 质量之外要比较 P95、首 token、成本、拒答率、工具成功率和稳定性；形成 Pareto 前沿而非单一总分。
  • 对随机模型做多次运行或固定策略，失败样本盲评；达到门禁后再灰度线上 A/B，保留快速回滚。
延伸联想

可进一步确认“这次升级的预注册成功标准是什么？”避免看到结果后临时挑有利指标。

边界与常见误区

统计方法可由数据同事协作细化，但我会确保版本可复现、单变量对比、风险分桶和线上灰度这四条基本纪律。

六、Prompt / Context Engineering（30—33）

30Prompt Engineering 与 Context Engineering 有什么区别？
为什么重要

关键在于理解是否从“写咒语”上升到系统工程。

要点
  • Prompt Engineering 关注如何表达任务、约束、示例和输出格式；Context Engineering 关注在每一步把哪些信息、以何种结构、在何时提供给模型。
  • Context 来源包括 system policy、用户请求、业务状态、检索证据、工具定义/结果、记忆和中间产物；关键是选择、排序、压缩、隔离和溯源。
  • 上下文越长不必然越好，会出现注意力稀释、冲突、成本和延迟。权威指令与不可信数据应明确分区，重要信息靠近相关任务。
  • 复杂 Agent 的瓶颈常不是 Prompt 文案，而是错误数据进入上下文、关键状态缺失或工具结果过载。
  • 可结合本人 AI Engineering 课程体系：53 个专题、51 份可演讲 HTML 课件覆盖 Prompt、Context、Harness 与 Agent；它证明方法论沉淀，不等同于某项线上指标。
延伸联想

用一句话总结：“Prompt 是上下文中的一部分，Context Engineering 是围绕模型建立信息供应链。”

边界与常见误区

具体术语边界行业里并非完全统一；我的实践重点是让上下文可选择、可追溯、可评测，而不是无限堆历史文本。

31如何设计一个稳定、可维护的生产 Prompt？
为什么重要

关键在于理解 Prompt 软件工程化能力。

要点
  • 分区组织：角色/目标、权威规则、输入数据、任务步骤、工具约束、输出 schema、拒答与异常策略；明确优先级和冲突处理。
  • 少写空泛人格，多写可验证规则；few-shot 覆盖典型、边界和错误例，而不是只给完美示例。
  • 变量类型化并转义，不把用户文本直接拼进指令；结构化输出由 schema 校验，失败有限次修复。
  • Prompt 进 Git，包含 owner、版本、变更原因、适用模型和回归结果；发布走离线评测、灰度、观测和回滚。
  • 模型能力变化后重新验证，不假设同一 Prompt 跨模型行为一致。
延伸联想

主动展示 Prompt 的验收标准，而非只展示文本本身。

边界与常见误区

我不会靠个人语感宣布 Prompt 好；会把输出契约、失败样本和回归集一起交付，使其像代码一样可维护。

32长上下文如何压缩，且尽量不丢关键信息？
为什么重要

关键在于理解 token 管理与信息保真。

要点
  • 先分信息类型：硬约束、当前业务状态和待办原样保留；历史对话可分段摘要；大文档按当前问题检索；工具原始响应提取所需字段。
  • 用滑动窗口 + 分层摘要 + 事实表/状态表组合；摘要应附来源和时间，重要事实可回查原文。
  • 每一步只给最小充分上下文，不让所有 Agent 继承全部历史；缓存稳定前缀，减少成本与延迟。
  • 监控压缩前后任务成功率、事实保留率和矛盾率；当摘要不确定时保留原文引用或请求澄清。
延伸联想

指出“业务状态不能被摘要”，例如企微待办是否完成必须读数据库，而非依赖对话总结。

边界与常见误区

我会把不可丢的状态先结构化，再对自然语言历史做摘要和检索；这样即便摘要质量波动，也不影响权威业务状态。

33如何处理 Prompt 版本、模型版本和工具版本之间的耦合？
为什么重要

关键在于理解可复现性和变更治理。

要点
  • 一次运行保存完整 manifest：模型及参数、system/prompt 版本、tool schema 版本、检索/embedding/index 版本、feature flag 和代码版本。
  • 建立兼容矩阵和契约测试；工具 schema 变更用新增字段向后兼容，破坏性变更升 major version，并允许旧新并行。
  • Prompt 不硬编码供应商特有行为；通过 adapter 处理消息格式、工具调用和结构化输出差异，但保留能力差异。
  • 发布以“配置包”灰度，出现问题按 manifest 回滚；历史轨迹重放时冻结外部副作用。
延伸联想

把版本组合当成“AI 应用制品”，而不是只给模型名打标签。

边界与常见误区

我未必使用过当前团队的 Prompt 管理平台，但会先保证每个线上答案能还原到一组确定的模型、Prompt、工具和知识索引版本。

七、安全与合规（34—36）

34如何防御 Prompt Injection，尤其是间接注入？
为什么重要

关键在于判断是否理解 LLM 应用特有攻击面。

要点
  • 直接注入来自用户，间接注入藏在网页、文档、知识库或工具结果中。核心原则是把外部内容标记为不可信数据，不能让它改变 system policy 或权限。
  • 指令与数据结构隔离；工具最小权限；敏感操作二次确认；URL/文件/参数白名单；输出到下游前做编码与校验。
  • 检索内容先做恶意指令检测可降低风险，但检测器不是唯一防线；即便模型被诱导，服务端授权也应阻止越权。
  • 建红队集：泄密、越权工具、跨租户读取、编码绕过、多轮诱导和知识库投毒；持续监控异常工具序列与数据外传。
  • 不声称“Prompt 写得好即可彻底防住”，以零信任和纵深防御为主。
延伸联想

说出“注入成功不应等于系统失守”，把安全责任从模型提示词移回服务端控制。

边界与常见误区

Prompt Injection 无法仅靠一句防御提示根治；我的方案是最小权限、服务端鉴权、数据隔离、风险操作确认和持续红队的组合防线。

35医疗敏感数据如何脱敏、授权和审计？
为什么重要

核实医疗合规经验和数据治理意识。

要点
  • 先做数据分类分级和数据流图：采集、传输、存储、模型调用、日志、备份与删除；遵循最小必要、目的限定和保存期限。
  • 直接标识符删除/掩码/令牌化，准标识符结合风险泛化；训练、评测、日志尽量使用去标识数据。脱敏不是简单正则，需处理自由文本、图片、音频和关联重识别风险。
  • 传输与静态加密、密钥轮换、租户隔离、RBAC/ABAC、按字段授权、审批与全量访问审计；第三方模型需明确数据地域、留存和训练使用条款。
  • 展示层防越权与误分享，日志不落完整 Prompt/病历；支持患者相关数据更正、撤回与删除传播。
  • 真实经历：某三甲医院项目完成 9 阶段 42 条任务的数据安全合规改造清单，配套 Playwright 回归与 Nginx 安全响应头；若涉及具体法规条款或全部任务，应按真实材料回答，不扩写未确认细节。
延伸联想

强调“脱敏是数据生命周期能力，不是上线前跑一次脚本”。

边界与常见误区

我能负责工程侧分类、最小化、访问控制、审计和回归；具体法律适用与医学数据出境结论会与法务/合规共同确认，不越权给法律结论。

36AI 输出内容安全如何做分层审核？
为什么重要

关键在于理解高风险行业输出治理。

要点
  • 输入侧检测违法、攻击、隐私与自伤等风险；生成侧结合供应商安全策略、自建规则/分类器和事实/引用校验；输出侧按场景决定阻断、改写、警示或人工审核。
  • 风险分级：一般科普可自动回答并展示来源；个体化诊疗、用药变化、危急症状等高风险内容应限制模型角色、触发就医建议或专业人员审核。
  • 规则擅长明确红线，分类模型覆盖语义变体，人工处理高风险与不确定项；任何单层都有漏报和误杀。
  • 保留策略版本、命中原因、处置和申诉/复核记录；用红队集测召回率、误杀率及绕过率，安全版本也需灰度。
  • 产品文案不能用免责声明替代真正控制。
延伸联想

可进一步确认“AI 是直接给患者决策，还是给医生草稿？”角色不同会改变整个风险控制等级。

边界与常见误区

医疗内容的最终责任边界需产品、医生与合规共同确定；工程上我会先做风险分级、自动检测、证据展示、人工闸门和全链路审计。

八、系统设计题（37—38）

37系统设计：设计一个支持 20+ 医疗场景智能体、并在企业微信稳定运行的 Agent 中台。
为什么重要

综合考察架构拆分、渠道接入、多租户状态、模型治理、可靠性、合规与团队落地。

要点
  • 先澄清：服务对象是医生还是居民；20+ 场景的流量、SLO、响应时限；是否自动发消息；知识与患者数据范围；多租户与合规要求；人工接管流程。
  • 分层架构：企微渠道适配层负责回调验签、消息解密/标准化、去重和限流；会话/身份层映射租户、医生、居民和会话；路由层识别意图与场景；编排层可先用 Dify 承载工作流；自研业务服务承载会话存档、待办、素材、看板和核心事务；模型网关统一 LLM/TTS/ASR；知识层负责 RAG 与 ACL；观测审计层贯穿全链路。
  • 稳定性：消息 event_id 幂等、顺序键/会话锁、并发守卫避免连续按键触发重复回复；同步快速确认、异步任务处理；超时/重试/死信、熔断和人工兜底；外发消息用 outbox 防止业务成功但发送丢失。
  • Agent 治理：场景注册表记录 owner、版本、Prompt、工具权限、知识库、模型策略、预算和发布状态；外层状态机限制 Agent；高风险写操作确认，医疗建议按风险分级。
  • 数据与安全：租户/患者权限前置过滤，敏感数据最小化和脱敏，第三方模型地域策略，审计与删除传播；知识回答带引用。
  • 质量与发布：每场景 golden set、工具契约测试、影子流量、灰度和回滚；监控任务成功率、重复消息率、P95、转人工率、成本与安全命中。
  • 真实案例落点：AI医疗助手产品（基于Dify打通20+医疗场景智能体）覆盖体检预警、随访整理、合理用药、病历质控、医保拒付风险等场景；本人主导企微/多端交付，做过并发守卫与乐观锁。Dify 只是编排层，不把自建服务说成 Dify 原生能力。
延伸联想

白板先画消息生命周期：“收到一次企微事件→唯一化→鉴权→路由→编排→人工/模型→幂等发送→审计”，再补平台横切能力，显得架构围绕真实故障设计。

边界与常见误区

具体到 Dify 某个节点或企微某个 SDK 参数我可以会后核对；但系统的职责边界、消息幂等、状态一致性、模型降级、安全审计和灰度发布，我能作为负责人完整设计并推动落地。

38系统设计：如果把现有 Dify 方案迁移到自研 Agent 框架，你如何规划路径？
为什么重要

综合考察迁移决策、风险控制、兼容性、组织协同和渐进式演进。

要点
  • 先证明迁移必要性：列出 Dify 在复杂状态、测试、可观测、性能、成本、合规或锁定上的实测瓶颈；明确目标 SLO 与 TCO。不为“技术先进”全量重写。
  • 资产盘点：逐个工作流统计调用量、业务重要性、节点/Prompt、知识库、工具、变量、外部副作用、owner、失败率和依赖；按价值、复杂度和风险分层。
  • 先建兼容层：定义统一 Agent Run、Message、Tool、State、Trace 与 Model Gateway 协议；把 Prompt、工具 schema、评测集和知识数据从平台配置中导出并版本化。
  • Strangler 迁移：先迁无副作用、低风险、可验证的场景或共用工具；入口路由支持按租户/场景/比例切换旧新引擎。复杂核心流程最后迁，不做“大爆炸”。
  • 状态与数据：新框架采用显式状态机、检查点、幂等和审计；迁移会话时定义兼容映射，不强求搬运无价值的历史思维过程；知识索引可先共享服务，避免同时迁两套高风险系统。
  • 同口径验证：用历史脱敏轨迹做离线回放和差分测试；影子流量禁止真实副作用；比较质量、P95、成本、工具成功、恢复能力与安全。达到门禁后小流量灰度，保留快速回切。
  • 组织和退役：双跑期限定时间，明确 owner、值班、培训、文档和预算；迁完一条就冻结旧配置，最终撤销密钥、归档审计并下线，避免永久双维护。
  • 结合真实经历：可对比全科助手的 Dify 编排与个人项目 NovelReel 的自研三层 Agent、状态持久化、失败降级、断点续跑和 44 tests，说明自己理解两端；不能声称 NovelReel 已承载 20+ 医疗场景生产流量。
延伸联想

先给迁移成功定义：“不是功能搬完，而是每个场景质量不降、可回滚、旧系统能真正退役，并且单位成功任务成本可解释。”

边界与常见误区

我没有做过把全科助手从 Dify 全量迁出的既成事实，因此不会包装成真实业绩；但我同时做过 Dify 生产集成和自研 Agent，可以用兼容层、影子流量、差分评测与 strangler pattern 给出低风险迁移方案。

## 实际使用总提醒

  • 回答负责人级问题时用“四段式”：业务约束 → 架构判断 → 关键机制 → 指标与回滚。
  • 可重点引用的真实项目：AI医疗助手产品（基于Dify打通20+医疗场景智能体）、某三甲医院认知筛查（讯飞/百炼/Azure 多语音引擎，后移除 Azure；9 阶段 42 条合规改造）、自建医疗LLM评测体系（公开集 + 专科子集，26 项指标/10 项核心）、个人项目 NovelReel（三层 Agent、失败降级、状态持久化、断点续跑、44 tests）。
  • 必须守住的边界：NovelReel 是个人项目；某三甲医院 RAG/知识库后端同事深度参与更多，自己主要负责知识库交互设计；没有材料佐证的模型参数、阈值、故障率、成本数字和具体十项指标名称不要实践中补造。
