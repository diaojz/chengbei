一、后端服务与 API 设计基础（1～6）

1RESTful API 应该如何设计资源、状态码和版本策略？
为什么重要

判断是否有独立设计过后端接口，而不是只消费别人给的接口。

要点
  • 资源用名词复数、层级表达从属关系，动作优先映射到 HTTP 方法而非塞进 URL；列表接口统一分页、排序、过滤参数命名规则。
  • 状态码分层：2xx 明确区分创建/无内容，4xx 区分客户端错误类型（校验失败、未授权、冲突），5xx 只在服务端确实异常时使用，不能用 200 包裹错误码掩盖真实状态。
  • 版本策略优先 URL 前缀或 header，明确废弃周期和迁移文档；破坏性变更走新版本而非原地修改字段语义。
  • 响应体统一错误结构（code/message/traceId），便于前端统一拦截处理；我在 Ponder 里设计过 55 条 API 路由，坚持路由按领域聚合、错误结构统一，前端联调成本明显更低。
延伸联想

“Ponder 的 55 条路由不是随手加的，我可以讲权限模型和路由聚合是怎么一起设计的。”

边界与常见误区

“复杂的超媒体/HATEOAS 流派我不会现场展开，但资源建模、状态码语义和版本兼容这三条我会坚持先讲清楚。”

2GraphQL 相比 REST 解决了什么问题？什么场景反而不该用？
为什么重要

看是否只会站队，还是理解取舍。

要点
  • GraphQL 解决过取数/欠取数问题，客户端按需声明字段，减少多端定制接口的维护成本；对聚合多个来源的复杂详情页收益明显。
  • 代价是查询复杂度不可控（需 depth/complexity limit）、缓存策略比 REST 更难（不能简单靠 URL 做 HTTP 缓存）、N+1 查询需要 DataLoader 之类的批处理方案兜底。
  • 简单 CRUD、强缓存需求、团队对 schema 治理经验不足的场景，REST 往往更省心；两者也可以在同一系统里分层共存，网关层 GraphQL 聚合、内部服务 REST/RPC。
  • 权限模型在 GraphQL 里要下沉到字段级，不能只在网关做一次性鉴权，否则细粒度越权很容易被忽略。
延伸联想

“我目前的项目里网关层聚合场景不算复杂，都是判断后主动选了 REST，我可以讲这个判断依据。”

边界与常见误区

“大规模 GraphQL 网关的性能调优我没有一线经验，会先用 complexity 限制和 DataLoader 打底，再按压测结果调整。”

3Node.js 后端和 Python（FastAPI）后端，你会按什么标准选型？
为什么重要

判断技术选型是否基于业务约束，而不是"我熟哪个用哪个"。

要点
  • 团队认知和前后端复用是现实因素：Node/TS 能和前端共享类型定义、协议 schema，适合前端主导的全栈团队；Python 生态在数据处理、AI/ML 集成、科学计算库上更成熟。
  • I/O 密集型场景两者都能用异步模型撑住并发；CPU 密集型任务两边都需要额外的进程池/Worker 方案，不能指望单进程事件循环硬扛。
  • FastAPI 的类型系统（Pydantic）和自动生成的 OpenAPI 文档，对需要频繁联调、多端消费的 API 团队很友好，这也是我在 Lollipop 项目选它的直接原因，配合 Next.js/React 前端做类型闭环。
  • 最终选型要看团队人力、现有基础设施、对接的 AI/模型 SDK 语言生态是否成熟，而不是抽象地比性能跑分。
延伸联想

“Lollipop 用 FastAPI + PostgreSQL + Redis，我可以讲当时权衡的具体依据，包括为什么没有选 Node 全栈。”

边界与常见误区

“两个生态的极限性能优化我不会现场比数字，会先按团队认知成本和生态成熟度做第一轮筛选，再用压测验证。”

4如何设计一个可维护的分层后端架构（controller/service/repository）？
为什么重要

看是否理解职责分离，而不是把所有逻辑堆进路由处理函数。

要点
  • controller 只做协议转换（解析请求、校验入参、调用 service、格式化响应），不写业务逻辑；service 承载业务规则和编排，repository 只负责数据访问，隔离 ORM/SQL 细节。
  • 跨领域的复用逻辑下沉到独立的领域服务或工具层，避免 service 之间互相直接调用形成隐式耦合；依赖关系单向，不允许 repository 反向依赖 service。
  • 校验分两层：接口层做格式/类型校验（拒绝明显非法输入），业务层做规则校验（余额是否够、状态是否允许流转），两者不能混为一谈。
  • 独立交付的小项目（如AI皮肤病采集平台）容易图快把逻辑全堆在路由里，我会用这三层强制自己在一周交付周期内也保持基本的可维护结构，方便后续加需求不推倒重来。
延伸联想

“AI皮肤病采集平台那个项目是我一个人在一周内独立完成的前后端，我可以讲当时怎么在赶工期和保持结构清晰之间取舍。”

边界与常见误区

“更复杂的六边形架构/DDD 分层我了解原理但没有大规模实践，会先用清晰的三层结构打底，按团队规模决定要不要进一步拆分。”

5接口幂等性应该怎么设计？前端已经做了防抖，为什么后端还要做？
为什么重要

判断是否理解前端防护不能替代后端保证。

要点
  • 前端 debounce/按钮 disable 只能防"正常用户误触"，防不住网络重试、多端同时操作、爬虫或恶意重放；后端幂等是唯一可信边界。
  • 常见方案：客户端生成幂等键（如 UUID）随请求携带，服务端用该键做去重（写入前查询/唯一索引冲突处理）；对状态机类操作用"目标状态 + 前置状态校验"代替"无条件执行"。
  • 支付、AI 任务提交、消息发送这类有副作用的操作必须幂等；纯查询接口天然幂等，不需要额外设计。
  • 我在企微家医助手项目里处理过键盘连发触发 AI 重复回复的真实问题，当时前端做了并发守卫，但如果后端没有幂等键兜底，多端同时操作或重试仍会重复触发，这是我从真实故障里理解幂等价值的来源。
延伸联想

“企微助手那次重复回复问题，我可以讲前端并发守卫和后端幂等键分别解决了什么、为什么两层都要有。”

边界与常见误区

“分布式场景下幂等键的存储选型（Redis/唯一索引/分布式锁）要看具体一致性要求，我会先明确操作的副作用类型再选方案，不会不假思索上分布式锁。”

6BFF（Backend for Frontend）层解决了什么问题？什么时候不需要 BFF？
为什么重要

考察多端协作场景下的后端分层判断，贴合读者前端出身背景。

要点
  • BFF 承接"多端消费同一批后端服务，但各端需要的数据形状、鉴权方式、聚合逻辑不同"的问题，把端特定的裁剪、聚合、协议转换放到 BFF，后端服务保持通用。
  • 我在某三甲医院智能代理项目里做的 SSE 会话代理本质就是 BFF 的一种：前端不直接连 Dify，而是经过我方 BFF 层统一处理鉴权、流式协议转换和多环境路由。
  • 只有单一端、接口形状和后端服务基本一致、团队规模小到没必要多一层维护成本时，BFF 反而是过度设计，直接消费后端服务更省心。
  • BFF 层要避免变成"业务逻辑的第二个后端"，核心业务规则应留在后端服务里，BFF 只做端适配、聚合和协议网关的工作。
延伸联想

“SSE 会话代理是我在真实项目里落地的 BFF，我可以展开讲它怎么处理鉴权透传和多环境路由。”

边界与常见误区

“大规模多 BFF 治理（比如按业务线拆分多个 BFF 团队）的组织问题我没有一线经验，会先从职责边界和协议契约讲起。”

二、数据库建模与选型（7～12）

7什么情况下选关系型数据库，什么情况下选文档型/KV？不要只说"看场景"。
为什么重要

检查数据库选型是否有具体判断标准。

要点
  • 数据结构稳定、字段间存在强关联和事务约束（如订单-明细-库存）优先关系型；数据结构多变、层级嵌套深、读写模式以整体存取为主（如内容型 JSON 文档、日志）适合文档型。
  • KV 存储（Redis 等）适合高频读写、结构简单、对延迟极度敏感的场景，如会话状态、限流计数、缓存层，不适合承载需要复杂查询和事务的核心业务数据。
  • 判断标准具体化为三问：数据之间的关系是否需要联表查询和外键约束？写入后是否需要强一致读取？查询模式是点查为主还是复杂条件筛选为主？答案决定选型而不是团队偏好。
  • Lollipop 项目用 PostgreSQL 承载用户、订阅、计费等强关联数据，Redis 承载会话缓存和限流计数，两者分工明确，不会把缓存当主存储用。
延伸联想

“Lollipop 里 PostgreSQL 和 Redis 的分工，我可以具体讲哪些数据放哪边、为什么。”

边界与常见误区

“NewSQL/分布式数据库的选型我了解但没有生产实践，会先按一致性和查询模式的判断标准出发，再评估是否需要引入更复杂的存储。”

8数据库表结构设计时，范式化和反范式化怎么取舍？
为什么重要

看是否理解范式不是教条。

要点
  • 范式化减少数据冗余和更新异常，适合写多读少、数据一致性要求高的核心业务表；反范式化通过冗余字段减少联表查询，适合读多写少、对查询性能敏感的展示层数据。
  • 常见做法是核心事务表保持范式化，配合物化视图、宽表或缓存层做反范式化的读优化，而不是直接在事务表里堆冗余字段。
  • 反范式化必须配套明确的数据同步策略（触发器、应用层双写、异步任务），否则冗余字段会悄悄和源数据不一致，这类 bug 很难在测试阶段发现。
  • 医疗数据场景（如AI皮肤病采集平台的病历资料）我倾向保守：核心诊断数据严格范式化并加约束，避免因为省一次联表查询而引入数据不一致的合规风险。
延伸联想

“AI皮肤病采集平台项目涉及病历资料，我在范式化取舍上会明显偏保守，可以讲当时具体的表结构考虑。”

边界与常见误区

“大规模数据仓库的宽表设计我经验有限，日常业务库的范式取舍我可以讲清楚判断逻辑。”

9数据库索引是怎么生效的？为什么加了索引查询有时反而不走索引？
为什么重要

检查是否真的用过 EXPLAIN 排查过慢查询，而不是背"加索引就变快"。

要点
  • B+ 树索引让等值/范围查询避免全表扫描，但索引本身有维护成本（写入变慢、占用空间），不是越多越好；联合索引要遵守最左前缀原则，字段顺序错了索引可能用不上。
  • 常见不走索引的场景：对索引列做函数运算或隐式类型转换、LIKE '%xxx' 前缀通配、优化器估算全表扫描比走索引更便宜（数据分布倾斜、统计信息过期）。
  • 排查方式是用 EXPLAIN/EXPLAIN ANALYZE 看执行计划，确认扫描类型、预估行数和实际行数是否偏差过大，而不是凭直觉加索引。
  • 索引设计要结合真实查询模式：高频过滤字段、排序字段、联表关联字段优先建索引；低选择性字段（如布尔值）单独建索引往往收益很低。
延伸联想

“这类问题我更愿意用具体案例讲，比如某个查询从全表扫描优化到走索引的完整排查过程。”

边界与常见误区

“特定数据库引擎（如 PostgreSQL 的 GiST/GIN 索引）的高级索引类型我了解概念但没有深度实践，B+ 树索引的基础排查方法论我能讲扎实。”

10数据库读写分离和分库分表分别解决什么问题？什么阶段不该提前引入？
为什么重要

判断对数据库扩展性方案的边界认知。

要点
  • 读写分离解决"读多写少场景下单机读吞吐不够"的问题，代价是主从延迟带来的读己之写不一致，需要业务层容忍或做强制走主库的策略。
  • 分库分表解决"单表数据量/写入量超过单机承载能力"的问题，但会带来跨库事务、跨分片查询、扩容迁移的复杂度，是最后的手段而不是默认选项。
  • 大多数中小规模业务（包括我做过的AI皮肤病采集平台、AI合理用药系统、Lollipop 这类项目）数据量远没到需要分库分表的量级，提前引入只会徒增复杂度、拖慢迭代速度。
  • 正确顺序是先做好索引、慢查询优化、合理缓存、必要的读写分离，真正遇到单表数据量/写入瓶颈且优化已经打满时，再评估分片方案。
延伸联想

“我做的项目目前都没到需要分库分表的量级，我可以讲我怎么判断'还没到那个阶段'而不是过度设计。”

边界与常见误区

“真实分库分表落地（尤其是跨分片事务和数据迁移）我没有一线经验，会诚实说明并讲清楚我知道该往哪个方向验证。”

11Redis 除了做缓存还能做什么？缓存穿透、击穿、雪崩怎么分别应对？
为什么重要

检查 Redis 使用深度，是否只会 set/get。

要点
  • 除缓存外，Redis 常用于分布式锁、限流计数器（滑动窗口/令牌桶）、会话存储、排行榜（sorted set）、消息发布订阅和轻量级队列；AI Gateway 项目里我用它做用量统计和并发限流计数。
  • 缓存穿透（查询不存在的数据导致每次都打到数据库）用布隆过滤器或缓存空值应对；缓存击穿（单个热点 key 过期瞬间大量请求打穿）用互斥锁重建或逻辑过期；缓存雪崩（大批 key 同时过期）用过期时间加随机抖动、多级缓存分散。
  • 缓存一致性策略要明确：先更新数据库再删除缓存（而不是先删缓存）能降低并发下的脏读窗口，但极端情况仍需接受短暂不一致，业务上要评估这个窗口是否可接受。
  • Redis 不是万能数据库，持久化和数据丢失风险要评估清楚，核心业务数据不能只存在 Redis 里没有落盘的强一致来源。
延伸联想

“AI Gateway 里的并发限流和用量统计是我用 Redis 落地的真实场景，可以讲具体的计数模型设计。”

边界与常见误区

“Redis Cluster 的分片和高可用切换细节我了解原理但没深度运维过，单机/主从场景下的缓存策略我能讲得很扎实。”

12向量数据库和传统数据库的定位区别是什么？RAG 场景下你会怎么选型？
为什么重要

结合读者 AI Agent/RAG 背景，检查是否理解检索基础设施的取舍。

要点
  • 向量数据库（或传统数据库的向量扩展）解决的是"语义相似度检索"，不是替代关系型数据库的事务和结构化查询能力；两者通常并存，向量库负责召回候选，关系型库负责元数据过滤和权限校验。
  • 选型看规模和团队成本：小规模场景可以直接用支持向量扩展的 PostgreSQL（pgvector）减少额外中间件；召回量级和向量维度大到一定程度，专用向量数据库在索引算法（HNSW/IVF）和水平扩展上更有优势。
  • RAG 全流程里向量检索只是一环，还要结合关键词/结构化过滤做混合检索，单纯语义相似度排序容易召回"看起来相关但实际不对"的内容，这一点我在 Ponder 项目的混合检索设计里有具体实践。
  • 检索质量要有评估基线（召回率、排序质量），不能只凭肉眼感觉"检索得还不错"就上线。
延伸联想

“Ponder 的混合检索不是单纯向量相似度，我可以讲当时为什么要叠加结构化过滤。”

边界与常见误区

“超大规模向量库的分布式索引调优我没有一线经验，中小规模场景下的选型判断和混合检索设计我能讲清楚。”

三、事务、一致性与并发写入（13～17）

13数据库事务的 ACID 分别是什么？为什么"用了事务"不代表"数据一定一致"？
为什么重要

检查是否理解事务边界和业务一致性的区别。

要点
  • 原子性保证事务内操作全部成功或全部回滚；一致性指事务前后数据库始终满足约束（这依赖正确的约束定义，不是数据库自动保证业务逻辑正确）；隔离性控制并发事务间的可见性；持久性保证提交后数据不因故障丢失。
  • 事务只保证"数据库层面"的一致，业务逻辑一致性（比如跨服务的库存和订单要同步）还需要应用层设计，尤其涉及外部调用（发消息、调第三方接口）时不能把它们塞进同一个数据库事务。
  • 长事务（事务里包含慢查询或外部 IO）会持有锁资源过久，拖累并发性能，正确做法是把外部调用移出事务边界，用最终一致性方案（补偿、重试队列）处理。
  • 事务范围应该尽量小、尽量快；"加个事务保险一点"是常见的误用，反而可能引入锁竞争和死锁风险。
延伸联想

“我更愿意讲一个具体反例：把外部 API 调用放进数据库事务里导致的长事务问题，以及怎么拆分修复。”

边界与常见误区

“分布式事务（两阶段提交/TCC/Saga）的生产实践我没有深度经验，单机事务边界设计和最终一致性思路我能讲扎实。”

14数据库隔离级别有哪几种？为什么大多数团队默认用可重复读/读已提交就够了？
为什么重要

检查是否理解隔离级别背后的并发异常类型，而不是死背名词。

要点
  • 隔离级别从低到高对应能防的并发异常：读未提交（脏读都防不住）、读已提交（防脏读，不防不可重复读）、可重复读（防不可重复读，MySQL InnoDB 下还能防大部分幻读）、串行化（完全隔离但并发性能最差）。
  • 大多数业务对幻读不敏感，且更高隔离级别意味着更多锁竞争和更差的并发吞吐，所以默认级别（PostgreSQL 读已提交、MySQL InnoDB 可重复读）在正确性和性能之间是务实的平衡点。
  • 真正需要更强隔离保证的场景（比如金融计费的关键路径），应该用显式的行锁、乐观锁版本号或应用层约束去解决具体问题，而不是笼统调高全局隔离级别。
  • 乐观锁（版本号/时间戳比对）适合冲突概率低的场景，冲突时重试或提示用户；悲观锁（SELECT FOR UPDATE）适合冲突概率高、必须严格串行处理的场景，两者的选择取决于业务的并发写入特征。
延伸联想

“企微助手项目里我用过乐观锁版本控制处理并发编辑冲突，可以具体讲那个场景为什么选乐观锁而不是行锁。”

边界与常见误区

“不同数据库引擎在幻读防护上的实现差异（比如 MVCC 具体机制）我不会背版本细节，但我能准确讲清楚每种隔离级别防住了哪类异常。”

15高并发下的库存扣减/名额抢占问题，你会怎么设计？
为什么重要

经典并发一致性场景，看是否有具体方案而不是空谈"加锁"。

要点

  • 高并发热点场景（秒杀级别）单纯依赖数据库容易被打垮，需要在前面加一层限流和排队，把压力削峰后再落库；Redis 原子操作（DECR/Lua 脚本）可以做前置的快速判断和预扣减。

  • 我目前的项目规模没有遇到过秒杀级并发，这类方案我是基于原理设计并会在面试中诚实标注"没有在真实千万级并发场景验证过"，但设计思路和常见坑我很清楚。

16分布式锁怎么实现？Redis 分布式锁有哪些常见坑？
为什么重要

检查是否理解分布式锁的正确性边界，而不是只会 SETNX。

要点
  • 基础实现是 SET key value NX PX <ttl> 保证加锁的原子性，释放锁要用 Lua 脚本判断"锁是自己加的"再删除，避免误删别人的锁。
  • 常见坑：业务执行时间超过锁的 TTL 导致锁提前释放、多个客户端同时认为自己持有锁；单机 Redis 存在主从切换时锁状态丢失的风险，Redlock 算法试图解决这个问题但业界对它的正确性一直有争议。
  • 分布式锁本质是"尽力而为"的并发控制，不能替代真正需要强一致性的场景（比如资金扣减），那种场景应该用数据库的原子操作或更严格的一致性协议兜底。
  • 很多场景其实不需要真正的分布式锁，用数据库唯一约束、乐观锁版本号或队列串行化就能达到同样的效果，且更简单可靠，我会优先考虑这些更轻量的方案。
延伸联想

“分布式锁我倾向于'能不用就不用'，可以讲我在什么场景下用唯一索引替代了原本想加锁解决的问题。”

边界与常见误区

“Redlock 的争议细节和多机房容灾场景我没有深度实践，日常场景下我会优先选更简单可靠的方案而不是炫技上分布式锁。”

17数据库死锁是怎么产生的？线上遇到死锁应该怎么排查？
为什么重要

检查是否有真实排查经验或至少清晰的方法论。

要点
  • 死锁通常源于多个事务以不同顺序请求同一批资源的锁，形成循环等待；常见诱因是同一批业务代码里对多张表的加锁顺序不一致。
  • 排查思路：数据库通常会记录死锁日志（如 MySQL 的 SHOW ENGINE INNODB STATUS），能看到涉及的 SQL 语句和锁等待链路，先定位具体是哪几条 SQL 互相等待。
  • 修复方向是统一加锁顺序（比如始终按主键从小到大加锁）、缩短事务持有锁的时间、必要时把大事务拆小；应用层要对死锁异常做重试处理，因为数据库会自动回滚其中一个事务。
  • 我目前项目规模较小，还没有真实遇到过生产死锁，但我清楚它的成因和排查工具链，会在这类问题上诚实说明经验边界。
延伸联想

“我可以换个角度讲：我在设计并发场景（比如企微助手的并发守卫）时，是怎么从源头上避免多资源加锁顺序不一致的。”

边界与常见误区

“我没有真实排查过生产死锁事故，这里我会诚实说明，并给出基于日志分析和加锁顺序统一的标准排查思路。”

18消息队列解决了什么问题？什么场景不需要引入队列？
为什么重要

检查是否理解队列是取舍而非"高级架构标配"。

要点

19后端如何设计一个可靠的异步任务系统（比如 AI 生成任务、批处理任务）？

20限流算法有哪几种？滑动窗口和令牌桶分别适合什么场景？
为什么重要

检查限流设计的具体理解，贴合读者做过的 AI Gateway 并发限流经验。

要点
  • 固定窗口计数实现最简单，但存在窗口边界的突刺问题（前后两个窗口临界点可能瞬间通过双倍流量）；滑动窗口通过更细粒度的时间片统计，能更平滑地限制速率。

  • 限流策略要分层：网关层做粗粒度保护，业务层可以按用户等级/场景做更精细的配额管理；限流触发后要给客户端明确的重试提示（如 Retry-After），而不是简单丢弃请求。

21如何设计一个 Web 应用的多级缓存策略？
为什么重要

要点

五、后端安全、鉴权与合规（23～27）

23JWT 和传统 Session 鉴权分别适合什么场景？JWT 怎么处理"注销"这个天然难题？
为什么重要

检查鉴权机制的理解深度，而不是只会说"JWT 无状态更快"。

要点
  • Session 依赖服务端存储会话状态，天然支持主动注销和精细的会话管理，但要处理多实例间的会话共享（集中式 session store）；JWT 把状态编码进 token，服务端无需查库即可校验，适合分布式、跨服务的场景，但注销和权限即时收回是天然弱项。
  • JWT 常见的注销方案：短 TTL + refresh token 轮换、维护一个黑名单/撤销列表（本质上又引入了状态存储，只是换了个地方）、或者在关键权限变更时靠客户端主动清除+服务端拒绝旧签发时间之前的 token。
  • token 存储位置直接影响安全模型：放 localStorage 容易被 XSS 窃取，放 httpOnly cookie 又要考虑 CSRF 防护，这是我在处理前端安全问题时反复权衡过的组合。
  • 医疗/敏感系统我倾向短期 token + 服务端可控的会话状态结合，而不是纯无状态 JWT，因为合规场景往往需要能立即吊销某个用户的所有会话。
延伸联想

“这个问题正好连接我前端安全那部分的经验，我可以从 token 存储位置讲到 XSS/CSRF 组合防护的完整链路。”

边界与常见误区

“OAuth2/OIDC 复杂授权流程的所有细节我不会现场背，但 JWT 和 Session 各自的权衡与注销难题的应对我能讲清楚。”

24RBAC 权限模型怎么设计？多租户场景下权限和数据隔离要注意什么？
为什么重要

结合读者在 Ponder 项目里做过权限模型的真实经历。

要点
  • RBAC 核心是用户—角色—权限的多对多映射，角色作为权限的聚合单元便于批量授权；更细粒度场景需要资源级权限（某个具体文档/记录级别的可见性），这时候单纯角色粒度不够，需要叠加 ACL 或策略引擎。
  • Ponder 项目里我从"需求矛盾审查"开始设计权限模型，核心是先理清楚业务角色之间的真实边界冲突（谁能看什么、谁能改什么、谁能导入什么），再落到数据结构，而不是先写代码再补权限。
  • 多租户场景下，权限校验必须下沉到数据访问层（每条查询都带租户过滤），不能只在接口层做一次性校验就假设后续查询天然隔离；行级安全（Row-Level Security）或统一的查询中间件是常见落地方式。
  • 权限变更要可审计：谁在什么时候给谁授予/收回了什么权限，这在医疗/企业场景的合规要求里往往是硬性的，不是可选项。

25后端如何防范 SQL 注入？ORM 是不是就天然安全？
为什么重要

检查基础安全意识，不能因为用了 ORM 就掉以轻心。

要点
  • 参数化查询/预编译语句是根本防护手段，让用户输入始终作为数据而非 SQL 语法的一部分；拼接字符串构造 SQL 是绝对红线，无论前端做了多少校验都不能信任。
  • ORM 默认的查询方法通常是参数化的，相对安全，但如果用了 ORM 提供的"原始 SQL"逃生舱（raw query）又手动拼接字符串，同样会引入注入风险，ORM 本身不是安全的护身符。
  • 权限最小化原则同样适用于数据库账号：应用连接数据库的账号不应该有 DROP/ALTER 这类高危权限，即使代码层出现漏洞，也能限制攻击面。
  • 我处理过 SSRF 和路径遍历这类安全问题的两轮整改，形成过完整的分析/复核/复测/验证报告闭环，SQL 注入的防护思路和这些问题共享同一套"不信任任何外部输入"的底层原则。
延伸联想

“我可以从 SSRF/路径遍历那次真实的安全整改闭环讲起，说明我怎么把'不信任外部输入'这条原则贯穿到不同类型的漏洞防护里。”

边界与常见误区

“二阶注入、盲注这类更隐蔽的攻击手法我不会现场展开变种细节，但参数化查询+最小权限这两条底线我会坚持说清楚。”

26医疗/敏感数据场景下，后端应该如何设计数据脱敏和访问审计？
为什么重要

结合读者多个医疗项目背景，检查合规意识是否具体可落地。

要点
  • 脱敏要分场景：日志和普通监控里病历、身份信息等 PII 一律不能明文出现，需要在写日志前做字段级脱敏；管理后台展示可以按角色显示部分脱敏（如手机号中间四位打星），只有特定审批角色能看到完整信息。
  • AI皮肤病数据采集平台在设计上就要求匿名脱敏和医院品牌定制，我在独立完成前后端时把脱敏规则实现在数据落库前的处理层，而不是指望前端展示时才脱敏——脱敏必须尽早发生，越靠近数据源越安全。
  • 访问审计要记录"谁在什么时间访问/导出了哪些敏感数据"，审计日志本身也要做好权限隔离，防止审计记录被篡改或被无关角色查看。
  • 数据最小化原则：能不采集的字段不采集，能不长期保留的数据设置合理的留存期限并到期清理，这比"采集了再加固权限"更从根源上降低风险。
延伸联想

“AI皮肤病采集平台项目的匿名脱敏是我独立设计并落地的，可以具体讲脱敏规则在数据链路里的位置和留存策略。”

边界与常见误区

“严格意义上的医疗合规认证（比如等保测评的具体条款）我不是合规专家，但数据脱敏、访问审计、最小化采集这几条工程侧的红线我很清楚也有真实落地经验。”

27后端如何应对第三方 API/模型接口的密钥泄露风险？
为什么重要

结合读者 AI Gateway 项目背景，考察密钥和凭证管理意识。

要点
  • 密钥绝不能出现在前端代码、客户端存储或版本库里；服务端集中管理密钥，业务代码通过内部服务调用而不是直接持有密钥，这也是 AI Gateway 项目本身要解决的核心问题之一。
  • 密钥要支持轮换和按账号/用途细分，一旦某个密钥疑似泄露可以单独吊销而不影响其他调用方；日志和错误信息里要主动过滤密钥字段，避免异常堆栈把密钥打印到日志系统里。
  • AI Gateway 项目里我设计了 Key/账号/用量管理体系，并限制了公网暴露面，核心思路是让业务方拿到的是受限的、可审计、可撤销的凭证，而不是直接持有上游服务商的原始密钥。
  • 监控告警要覆盖异常用量突增，这往往是密钥被盗用最早的信号，比人工发现密钥泄露快得多。
延伸联想

“AI Gateway 的 Key/账号/用量管理正是围绕这个问题设计的，可以具体讲密钥分发和撤销的完整链路。”

边界与常见误区

“企业级密钥管理服务（如专用 KMS/HSM）的深度集成我没有实践过，中小团队场景下的密钥集中管理和轮换设计我能讲得很具体。”

29遇到一个后端性能问题，你会怎么定位？没有专职 DBA/SRE 支持时怎么办？
为什么重要

检查独立排障能力和资源有限时的应对策略。

要点
  • 先分层定位：是应用层慢（业务逻辑本身耗时、串行调用过多）、数据库层慢（慢查询、锁等待、索引缺失）、还是外部依赖慢（第三方 API、模型接口延迟）；用日志耗时打点和数据库自带的慢查询日志快速缩小范围。
  • 没有专职 DBA 时，我会依赖数据库自带的诊断工具（EXPLAIN、慢查询日志、连接数/锁等待监控）先自己排查到"大概是哪类问题"，再决定是否需要引入更专业的工具或求助。
  • 独立交付的项目里，我倾向于把监控和日志在上线第一天就配好（而不是出问题了才加），AI Gateway 里的监控告警设计就是基于这个习惯——问题发生时能第一时间看到是哪个环节异常，而不是两眼一抹黑地猜。
  • 遇到超出自己判断能力的复杂问题（比如怀疑是数据库引擎底层的 bug），我会明确承认边界，选择查阅官方文档、复现最小案例、或者寻求社区/专业支持，而不是凭感觉试错到上线环境。
延伸联想

“AI Gateway 的监控告警体系是我为了应对'没有专职团队支持'这个现实约束主动设计的，可以讲具体覆盖了哪些指标。”

边界与常见误区

“复杂数据库引擎内部机制的排查我能力有限，但'先分层定位、再针对性深入'这套方法论适用于我目前遇到的所有性能问题。”

30AI 全栈负责人和专职后端团队协作时，你的角色边界应该怎么定？

七、系统设计题（31～32）

31设计"AI皮肤病数据采集平台"这类医疗数据采集系统的后端架构：采集端、管理后台、公网访问、匿名脱敏、医院品牌定制，且要求一周内独立交付上线。
为什么重要

综合考察在极短交付周期下，独立完成的后端架构设计与合规意识，直接对应真实项目。

要点
  • 范围裁剪： 一周交付的前提是先砍掉一切非必要的通用能力（不做复杂权限系统、不做多租户框架），专注采集、脱敏、审核、导出这条主链路；技术选型优先熟悉且能快速上手的成熟框架，不引入需要额外学习成本的新工具。
  • 数据模型： 核心表围绕"采集记录"（皮损照片 + 病历资料 + 诊断标注 + 采集时间/操作人）设计，脱敏字段和敏感字段分离存储，导出时按角色决定是否携带敏感字段；照片等大文件走对象存储或独立文件服务，数据库只存元数据和路径。
  • 公网访问与安全： 部署在具备公网访问能力的服务器，用 Nginx 做反向代理和 HTTPS 终止；采集端和管理后台按角色区分访问入口，管理后台加登录鉴权，采集端根据实际场景决定是否需要院内网络限制或简单的访问码机制。
  • 脱敏与合规： 数据落库前做匿名化处理（去标识化关键字段），审计记录谁在什么时候访问/导出了数据；医院品牌定制通过配置化的主题/文案层实现，不为单个客户 fork 代码库。
  • 交付节奏： 一周内的关键路径是"核心采集流程先跑通并可用" → "管理后台补齐审核/导出" → "部署上线 + 公网验证" → "补文档和使用说明"；每天有可演示的进展，而不是憋到最后一天才集成。
  • 真实项目连接： 这不是纸面设计，是我独立完成需求文档、产品设计、前端、后端、部署上线和使用说明的真实项目，一周内完成全链路交付，支持采集端、管理后台、公网访问、匿名脱敏和医院品牌定制。
延伸联想

“这道题我可以直接讲真实交付过程中的取舍，包括哪些功能是主动砍掉、为什么砍。”

边界与常见误区

“如果要求支持更大规模并发采集或更复杂的多院区权限体系，我会先明确这已经超出一周独立交付的合理范围，需要重新评估团队规模和周期。”

32设计一个面向小团队的 AI 网关后端：Key/账号/用量管理、并发限流、多环境部署、监控告警与备份恢复，同时要应对国内访问不稳定的网络环境。
为什么重要

综合检验后端服务设计、数据库选型、安全治理和生产运维协作意识，直接对应 AI Gateway 真实项目。

要点
  • 核心数据模型： PostgreSQL 存储账号、Key、用量流水这类需要强一致和关联查询的数据；Redis 承载并发计数、限流令牌桶和短期缓存，两者职责分离，不用 Redis 当主存储。
  • 请求路径： 网关接收业务方请求后，先做 Key 校验和限流判断（Redis 原子操作，低延迟），通过后转发到上游模型服务，回包前记录用量到异步队列/延迟写入，避免用量记录拖慢主路径延迟。
  • 网络与部署： 服务部署在境外 VPS，针对国内 SSE 长连接不稳定的问题设计两条访问链路——一条经 Cloudflare 做管理和过渡访问，一条走 Caddy 做 API 直连，按稳定性和延迟需求分流；同时限制公网暴露面，只开放必要端口。
  • 容器化与环境： 用 Docker 部署，配置和密钥通过环境变量/secret 注入而非硬编码；预留多环境（测试/生产）能力，镜像构建产物可追溯到具体版本。
  • 可观测性与容灾： 监控告警覆盖异常用量突增（密钥泄露信号）、限流触发频率、上游服务延迟和错误率；数据库和关键配置有定期备份和已验证过的恢复流程，而不是"配了备份从没试过恢复"。
  • 安全边界： 业务方拿到的是受限、可审计、可撤销的 Key，不直接持有上游服务商的原始密钥；异常调用模式（比如短时间内异地大量请求）触发告警甚至自动降级。
  • 真实项目连接： 这就是我在日本 VPS 上独立部署运行的 AI Gateway，面向小团队提供 Claude Code 中转能力，覆盖 Key/账号/用量管理、并发与限流、PostgreSQL/Redis、Docker 部署、监控告警和备份恢复，双访问链路已经在真实网络环境下验证过可用性。
延伸联想

“这不是假设场景，AI Gateway 现在就在真实运行，我可以直接打开监控面板讲当前的用量和告警设计。”

边界与常见误区

“如果要求支持数百个团队级别的多租户隔离和企业级 SLA，现有的单节点设计需要重新评估水平扩展方案，我会诚实说明这是下一阶段要解决的问题，而不是假装当前架构已经够用。”
