一、JavaScript / TypeScript 核心（1～9）

1浏览器事件循环中，一次点击触发的同步代码、Promise、MutationObserver、setTimeout 和渲染分别如何排序？
为什么重要

关键在于判断是否真正理解任务调度、渲染时机和卡顿根因，而非只会背“宏任务/微任务”。

要点
  • 一个 task（如点击回调）先执行完同步调用栈；随后清空 microtask queue，Promise.then 与 MutationObserver 都属于微任务，按入队顺序及规范检查点执行。
  • 微任务执行期间新增的微任务也会继续清空；无限追加会饿死渲染。浏览器在任务间获得渲染机会，但不是每轮都必然绘制；requestAnimationFrame 在下一次绘制前执行。
  • setTimeout(fn, 0) 只是把任务放到未来的 task queue，受最小延迟、后台页节流和主线程占用影响，不保证立刻执行。
  • Node.js 的 phase 与浏览器不同，不能把两套模型混讲。工程上，大量计算应切片、下沉 Web Worker，流式文本更新应批量提交，避免每个 token 都触发重渲染。
延伸联想

“我在 SSE 流式对话里更关注微任务之外的增量渲染节流，您希望我展开讲 token 批处理还是断线恢复？”

边界与常见误区

“精确到不同浏览器实现的个别时序我会以规范和 DevTools trace 验证，但主线是 task 执行完、清空微任务、浏览器择机渲染。”

2原型链、class、new 和 instanceof 的底层关系是什么？
为什么重要

关键在于检查对象模型基础，以及能否解释框架、SDK 中的继承与类型判断陷阱。

要点
  • 对象通过内部 [[Prototype]] 形成委托链；属性读取从自身向原型逐级查找。class 主要是原型机制的语法封装，并增加严格模式、不可直接调用等语义。
  • new F() 会创建对象、把其原型指向 F.prototype、以新对象为 this 调用构造函数；若构造函数显式返回对象，则返回该对象。
  • instanceof 检查右侧的 prototype 是否出现在左侧对象原型链上；跨 iframe、手工改原型、Symbol.hasInstance 都可能让结果偏离直觉。跨 realm 更适合品牌检查或 Array.isArray。
  • 业务代码优先组合而非深继承；原型污染要防守 __proto__、constructor.prototype 等不可信键。
延伸联想

“原型链本身我会控制在基础设施层，复杂前端架构里我更偏组合和显式依赖，避免继承层级成为治理成本。”

边界与常见误区

“我可以先讲确定的委托链和 new 四步；跨 realm 与 Symbol.hasInstance 的边界我会查规范确认。”

3闭包为什么既有价值又可能造成内存问题？如何定位泄漏？
为什么重要

看实践者能否把语言原理连接到长生命周期应用的稳定性。

要点
  • 闭包是函数连同其词法环境，适合数据封装、工厂函数、缓存和异步回调；不是“用了闭包就泄漏”，而是仍可达的闭包保留了不再需要的大对象。
  • 常见泄漏源：未移除的事件监听、定时器、全局 Map、游离 DOM、订阅未取消、组件卸载后仍持有响应式对象。WeakMap 只在键的生命周期应跟随对象时使用，不是通用缓存方案。
  • 用 Chrome Memory 的 heap snapshot 比较 retained size 与 retaining path；Allocation instrumentation 复现增长；先稳定复现，再定位 GC 后仍存活的对象链。
  • React effect、Vue watch、SSE/WebSocket、Electron IPC 都要设计 teardown，尤其多端助手类长会话页面。
延伸联想

“AI 对话页面通常长时间不刷新，我会把流连接、订阅和历史缓存的生命周期作为专项治理点。”

边界与常见误区

“我不会直接把内存上涨归因于闭包，会先强制 GC 后做快照对比，看对象由哪条引用链保活。”

4手写一个可靠的 debounce 和 throttle，需要考虑哪些语义？
为什么重要

不只考代码，更考 API 设计、边界条件和真实业务判断。

要点
  • debounce：连续触发只在安静窗口后执行；需明确 leading、trailing、maxWait，并保留最新参数和 this，暴露 cancel/flush。
  • throttle：时间窗口内最多执行一次；可用时间戳或“剩余时间 + timer”实现，同时处理首尾调用、系统时间变化和卸载清理。
  • 搜索联想适合 debounce；滚动采样适合 throttle；提交、支付、AI 回复等副作用不能只靠前端防抖，还要请求去重、幂等键或服务端状态约束。
  • 企微助手的真实问题是键盘连发可能触发 AI 重复回复，因此“并发守卫”比普通 UI 防抖更关键：需锁住进行中状态、拒绝/合并重复触发并在异常路径释放。
延伸联想

“我可以结合企微助手讲为什么 debounce 不是并发安全，以及前后端幂等怎么补齐。”

边界与常见误区

“完整可复用实现我会先确认 leading/trailing 语义；实践中可以写基础版，并明确生产版还需 cancel、flush 和异常释放。”

5如何实现 Promise.all？失败、空数组和 thenable 怎么处理？
为什么重要

关键在于检查 Promise 语义、并发结果排序与异常传播。

要点
  • 返回新 Promise；用 Promise.resolve(item) 吸收普通值与 thenable；按输入索引保存结果而非完成顺序；计数等于输入数时 resolve。
  • 任一项 reject 立即 reject；空 iterable 应立即 fulfilled 为 []。即使外层提前失败，已启动任务通常不会自动取消。
  • 生产环境还需并发上限、超时、重试、取消信号和 allSettled 取舍。大批上传或 AI 批量任务不应无上限 all。
  • 手写时要注意 iterable 而非仅 Array，以及迭代过程中抛错。
延伸联想

“在 AI 多模型调用里，我会进一步讨论‘首个成功’、降级和 AbortController，而不是只停在 Promise.all。”

边界与常见误区

“我能实践中写数组版核心逻辑；iterable 与 thenable 的规范细节我会明确标出并用测试补齐。”

6深拷贝应该如何设计？为什么 JSON 序列化不是通用答案？
为什么重要

看对数据结构、引用语义和工程边界是否敏感。

要点
  • JSON 会丢失 undefined、Symbol、函数、BigInt，改变 Date/Map/Set，无法处理循环引用，还可能触发 toJSON。
  • 浏览器优先评估 structuredClone，它支持循环引用、Map/Set、ArrayBuffer 和 transferable，但不克隆函数、DOM 节点等。
  • 自研需用 WeakMap 处理循环，按类型创建目标，保留属性描述符/原型是否必要要由需求决定；“深拷贝一切”往往是错误抽象。
  • 状态管理更推荐结构共享和不可变更新，避免大对象全量复制；跨 Worker 可利用 transfer 减少复制成本。
延伸联想

“大型状态树里我更愿意从状态边界和结构共享解决，而不是用深拷贝掩盖数据所有权问题。”

边界与常见误区

“我会先问清数据类型和用途；纯 JSON 数据、浏览器结构化克隆、保留原型对象是三种不同需求。”

7TypeScript 的结构类型、联合类型、泛型与条件类型如何用于 SDK 设计？
为什么重要

关键在于判断是否能用类型系统表达业务约束，而非只写接口注解。

要点
  • TS 是结构化类型系统；赋值看形状兼容。联合类型配合可辨识字段可表达有限状态机，如 idle | streaming | success | error，通过 never 做穷尽检查。
  • 泛型应表达输入输出关系，而不是把所有东西写成 <T>；约束 extends、keyof、索引访问类型可构造安全 API。
  • 条件类型和 infer 适合从 schema/函数推导结果；映射类型适合统一生成 readonly/optional 变体，但过度体操会损害错误信息和编译性能。
  • 对 SSE 事件协议可按事件名建立 discriminated union，使解析后不同 payload 在编译期收窄；运行时仍必须用 Zod 等校验，因为 TS 类型会被擦除。
延伸联想

“我在流式 Agent 前端更关注‘协议类型 + 运行时校验’，可以展开讲如何防止后端事件漂移。”

边界与常见误区

“复杂条件类型我不会凭记忆炫技；我会先把状态和协议用可辨识联合表达，再按维护性决定是否抽象。”

8any、unknown、never 分别应在什么场景使用？如何治理大型 TS 项目的类型债？
为什么重要

看类型安全意识和渐进式治理能力。

要点
  • any 同时放弃读写检查并会传播；unknown 只允许赋值，使用前必须收窄，适合外部输入；never 表示不可能发生或不返回，用于穷尽检查。
  • 边界输入统一从 unknown 进入：API、localStorage、postMessage、插件消息均做运行时 schema 校验，再转领域类型。
  • 治理顺序：开启 strict 新代码门禁；统计 any/ts-ignore；先修公共包与高变更模块；对历史代码设预算递减，不追求一次性清零。
  • API 类型最好由 OpenAPI/schema 生成，但生成类型不替代领域模型；避免后端 DTO 穿透全部 UI。
延伸联想

“我会把类型治理和发布门禁一起讲，因为只改 tsconfig 不配 CI 很快会反弹。”

边界与常见误区

“具体配置项我可以查表，但原则是外部数据先 unknown、校验后进入领域，any 必须有隔离边界和清理计划。”

9设计一个可取消、可重试、可限制并发的异步任务池。
为什么重要

关键在于理解异步抽象、资源治理和失败模型。

要点
  • 维护 pending queue、running count 和任务状态；每完成一个任务在 finally 释放槽位并调度下一项，避免异常导致“永远占槽”。
  • 每项接受 AbortSignal；取消未开始任务直接移出，运行中将信号向下传；Promise 本身不可取消，取消是协作协议。
  • 重试只针对可恢复错误，使用指数退避 + jitter；非幂等任务需幂等键。支持优先级时要防低优先级饥饿。
  • 可观测性至少包括排队时长、执行时长、失败类型、重试次数和并发水位；适用于上传、评测批任务、多模型/多媒体生成。
延伸联想

“我个人项目的视频流水线有状态持久化与断点续跑经验，但会明确说明这是个人项目，不和公司项目混淆。”

边界与常见误区

“我会先写固定并发池的核心状态机；重试策略需要结合接口幂等性和供应商限流规则再定。”

二、React / Vue 原理与状态管理（10～18）

10React Fiber 解决了什么问题？render 与 commit 阶段有什么区别？
为什么重要

关键在于判断能否解释 React 并发能力与副作用约束。

要点
  • Fiber 将组件树工作拆成可遍历、可中断的工作单元，并记录 child/sibling/return、优先级及副作用；解决旧递归协调不可中断的问题。
  • render/reconciliation 阶段计算新树与变更，可被中断、重启或丢弃，因此必须纯；commit 阶段同步应用 DOM 变更并执行布局相关 effect，不能被中断。
  • 并发渲染不是多线程；Scheduler 根据优先级让出主线程。startTransition 表示非紧急更新，不能拿来掩盖昂贵计算。
  • StrictMode 开发环境重复调用可暴露不纯 render 和 effect 清理问题，不应靠关闭它解决。
延伸联想

“SSE 高频增量更新很适合讨论 urgent/transition 的划分，我可以结合智能代理项目讲实际策略。”

边界与常见误区

“Fiber 字段级实现我不死背，但能确定 render 可重做且不能副作用，commit 才把变更同步落到宿主环境。”

11React diff 为什么强调 key？索引 key 会造成什么真实问题？
为什么重要

关键在于理解是否理解 identity、状态保留和列表性能。

要点
  • React 在同层按元素类型和 key 判断节点身份；key 不是给 DOM 用，而是帮助协调器复用 Fiber 与组件状态。
  • 插入、删除、排序时使用 index 会让“位置”冒充“业务身份”，导致输入框内容、焦点、局部 state 错配；静态且永不重排列表才相对安全。
  • key 变化会强制卸载/重建，可用于有意重置状态，但会丢失 DOM/组件状态且触发副作用清理。
  • 长消息列表还要配合虚拟化、稳定数据引用和锚点保持，不能把所有性能问题归给 diff。
延伸联想

“在企微群聊模拟和 AI 会话列表中，消息 ID、流式临时 ID 与服务端确认 ID 的映射才是关键。”

边界与常见误区

“核心是 key 定义身份；我会用可稳定复现的插入列表例子解释状态错位，而不是只说性能差。”

12useEffect 常见竞态和闭包陷阱有哪些？
为什么重要

关键在于检查真实 React 工程经验。

要点
  • 缺依赖导致读取旧闭包；依赖对象每次新建导致 effect 反复执行；在 effect 中无条件 setState 可形成循环。
  • 请求 A 后请求 B，A 晚返回可能覆盖 B；应使用 AbortController、请求序号或缓存库的去重/过期策略。卸载时清理监听、timer、SSE。
  • effect 用于与外部系统同步，不应承担可由 render 推导的状态；事件逻辑优先放事件处理器。
  • 对严格模式下 setup-cleanup-setup 要保持幂等。流式连接应把“连接身份”与“消息累积”分离，避免每次渲染重连。
延伸联想

“我可以结合 SSE 连接生命周期讲取消、重连与重复消费的处理。”

边界与常见误区

“我会先按‘依赖是否完整、清理是否对称、异步是否可取消’三项检查，具体 API 再实践中确认。”

13React Context、Zustand、Redux Toolkit、服务端缓存分别怎么选？
为什么重要

看状态分类能力，而非框架站队。

要点
  • 先分状态：局部 UI、跨组件客户端状态、服务端异步缓存、URL 状态、表单状态；不要把它们塞进同一个全局 store。
  • Context 适合低频、稳定的依赖注入或主题；频繁变化的大对象会让消费者重渲染。Zustand API 轻、selector 细粒度，适合中等复杂客户端状态；Redux Toolkit 适合强约束、审计、复杂事件流和大团队。
  • 服务端数据优先 TanStack Query/SWR 这类缓存模型，处理 stale、去重、失效和重试；URL 应承载可分享/可回退状态。
  • 某三甲医院智能代理使用 React18+TS+Zustand；选择理由应落在状态复杂度、团队认知、调试与持久化需求，而不是“代码少”。
延伸联想

“我可以用真实智能代理 Monorepo 说明 Zustand 如何和 SSE 会话状态分层。”

边界与常见误区

“我不会脱离状态类型直接选库；先画状态所有权和更新频率，再比较约束与团队成本。”

14Vue 3 响应式系统与 React 状态更新模型有何本质区别？
为什么重要

关键在于理解双栈深度及迁移/选型能力。

要点
  • Vue 3 通过 Proxy 拦截读写，在 effect 执行时 track、变更时 trigger，依赖粒度通常到属性；computed 懒计算并缓存，watch 处理副作用。
  • React 以状态快照驱动组件函数重新执行，再经协调更新宿主树；依赖追踪主要由组件边界和显式 hooks 完成。
  • Vue 常见坑：解构 reactive 丢响应性、深层 watch 成本、集合/数组边界；React 常见坑：引用不稳定、旧闭包和无效重渲染。
  • 选择不应只看跑分：还要看团队能力、生态、跨端目标、历史资产和团队建设成本。某到家服务平台时期推动 Vue、Flutter、AMIS 转型，可作为“按业务选技术”的背景，但不虚构具体指标。
延伸联想

“我更愿意谈双栈治理：同一组织如何统一协议、组件标准和质量门禁，而不是争论谁绝对更快。”

边界与常见误区

“内部 scheduler 的版本细节我会查源码，但核心差别是 Vue 自动依赖追踪，React 以组件重执行和显式依赖为主。”

15Vue 的 computed、watch、watchEffect 如何取舍？
为什么重要

关键在于判断是否会控制响应式副作用。

要点
  • computed 表达纯派生值，按依赖缓存；不应在 getter 中发请求或改状态。
  • watch 显式指定源，可获得新旧值，适合精确副作用；watchEffect 自动收集同步执行阶段读取的依赖，方便但隐式依赖多时难维护。
  • 异步 watch 要处理清理和竞态；深度监听会遍历，超大对象应监听明确字段或重构数据边界。
  • flush 时机决定回调相对组件更新的顺序；读取更新后 DOM 才需要 post，默认语义不要靠猜。
延伸联想

“技术负责人更该约束副作用写法和 lint/代码评审规则，否则响应式便利会转成隐形耦合。”

边界与常见误区

“我会先按纯派生用 computed、明确副作用用 watch；具体 flush 顺序会以当前 Vue 文档确认。”

16如何系统定位 React/Vue 页面重渲染过多，而不是盲目 memo？
为什么重要

看性能诊断方法与优化收益判断。

要点
  • 先用 Performance、React Profiler/Vue Devtools 找长任务、提交次数和热点组件，建立交互基线；区分网络慢、JS 执行慢、布局慢和渲染频繁。
  • React 检查 state 放置过高、Context 大对象、selector 不稳定、对象/函数引用；Vue 检查粗粒度 reactive、深 watch、模板中昂贵计算。
  • memo/useMemo/useCallback 有比较和认知成本，仅在热点且引用稳定时用；优先缩小状态边界、拆组件、虚拟化长列表、批量流式更新。
  • 用用户指标验证优化，避免 profiler 数字变好但交互无感。
延伸联想

“某三甲医院项目有可核实的首屏提速 50%～60%，我可以按测量—资源—加载策略拆解实际优化闭环。”

边界与常见误区

“我不会先加 memo；会先录 profile 找最贵的一次交互，再用单变量实验验证。”

17SSR、SSG、CSR、ISR、流式 SSR 与 React Server Components 怎么选？
为什么重要

关键在于理解现代 Web 架构、缓存和交互边界。

要点
  • CSR 适合登录后强交互应用；SSG 适合内容稳定页面；SSR 适合动态且首屏/SEO重要页面；ISR 在可接受短期陈旧时降低重建成本。
  • 流式 SSR 提前输出可渲染片段，配合 Suspense 改善感知速度；hydration 仍有成本和一致性要求。
  • RSC 在服务端执行、减少客户端 JS，并可直接访问服务端资源；不能使用浏览器 API，交互边界仍需 Client Component。它不是传统 SSR 的简单替代。
  • 选择还要考虑个性化、缓存键、数据敏感性、部署平台和故障降级。医疗后台通常不为 SEO 付 SSR 复杂度。
延伸联想

“AI 产品里我会把公开落地页与登录后 Agent 工作台分开决策，不用一个渲染模式覆盖所有页面。”

边界与常见误区

“RSC 具体版本行为变化快，我会讲清服务器/客户端边界，并以项目所用框架版本文档为准。”

18如何设计流式 AI 对话组件，避免卡顿、内容错乱与重复消息？
为什么重要

结合 AI 前端场景考察状态机、性能和协议设计。

要点
  • 将会话、消息、一次生成任务分层；消息有 clientId/serverId、状态、累积内容、错误与引用信息；事件按 conversationId/messageId/sequence 路由。
  • token/chunk 先入缓冲区，按动画帧或时间片批量更新；Markdown 可分阶段解析，避免每字符全量重算；长列表虚拟化并处理自动滚动与用户上翻冲突。
  • 明确 connecting/streaming/completed/failed/cancelled 状态机；支持 Abort、超时、重连、Last-Event-ID 或业务游标、重复事件去重。
  • 某三甲医院智能代理已有 SSE 流式对话和 Dify 会话代理，可据此讲实际边界；不要声称使用了材料未确认的具体重连算法。
延伸联想

“这题正好连接我的 AI 应用和前端深度，我可以继续画 SSE 协议与前端状态机。”

边界与常见误区

“具体协议字段要看后端约定，但我会坚持任务状态机、事件幂等、批量渲染和可取消四条主线。”

19Vite 为什么开发快？与 Webpack 的核心差异是什么？
为什么重要

关键在于判断是否理解构建工具的执行模型和生产约束。

要点
  • Vite 开发期利用浏览器原生 ESM，按需转换模块；依赖预构建减少大量请求并处理 CommonJS。Webpack 通常先构建完整依赖图再提供 bundle。
  • Vite 的 HMR 基于模块边界精确失效；生产通常使用 Rollup 路径，因此 dev/prod 仍可能有差异。
  • “快”不是无条件：超大依赖、插件 transform、类型检查、网络文件系统都会拖慢；需要 profile 插件耗时、缓存和依赖边界。
  • 工具选型关注生态、SSR、模块联邦、遗留 loader/plugin 和团队迁移成本，不按热度重写。
延伸联想

“企微助手采用 React18+TS+Vite7，我更愿意讲升级时如何用回归与发布门禁控制风险。”

边界与常见误区

“插件钩子的细节我不凭记忆展开，但开发期原生 ESM 按需转换与传统全量 bundling 的差异是确定的。”

20Tree Shaking 为什么有时不生效？如何设计可摇树优化的包？
为什么重要

关键在于检查模块语义、包发布和体积治理能力。

要点
  • 依赖 ESM 静态结构；CommonJS 动态 require、运行时属性访问、模块顶层副作用会阻碍分析。
  • 包应提供正确 exports/module 条目，尽量使用具名 ESM 导出；准确设置 sideEffects，CSS 或注册型模块不能误标为无副作用。
  • barrel file 可能扩大加载/转换范围；需用 bundle analyzer 看最终产物，而非只看源码 import。
  • Tree Shaking 不等于 code splitting；首屏还要路由/组件动态导入、依赖替换和缓存策略。
延伸联想

“我做首屏优化时会把资源压缩、加载时机和 bundle 结构一起量化，某三甲医院项目资源体积确实减少了 53%。”

边界与常见误区

“我会先检查产物分析图、模块格式和 sideEffects，而不是假定构建器自动完成。”

21Turborepo + PNPM Monorepo 的价值、缓存原理和风险是什么？
为什么重要

关键在于理解大型仓库架构和真实落地经验。

要点
  • PNPM workspace 管依赖与包链接，严格依赖边界减少幽灵依赖；Turborepo 根据任务图、输入、环境变量和依赖产物计算缓存，支持并行与远程缓存。
  • 包边界应按领域和复用稳定性划分，不把所有代码抽成 shared；公共 UI、协议 SDK、配置、埋点可独立包，业务页面保持内聚。
  • 缓存正确性依赖 inputs/outputs/env 声明；未纳入环境变量或生成文件会命中脏缓存。CI 应只运行 affected 任务，但关键发布仍需风险兜底。
  • 某三甲医院智能代理采用 React18+TS+Ant Design+Turborepo+PNPM+Zustand，包含 SSE 代理和无侵入埋点，可作为真实案例。
延伸联想

“这个项目由我个人主导绝大多数提交、持续 12 个月，可以进一步讲 Monorepo 在长期迭代中的收益与债务。”

边界与常见误区

“远程缓存服务的实现细节我会按所用版本确认；但任务图、内容哈希和输入声明决定正确性这点不会变。”

22如何治理 Monorepo 中的依赖边界、版本与变更发布？
为什么重要

关键在于理解是否能防止 Monorepo 退化成“大泥球”。

要点
  • 用 package/领域边界、ESLint import rule、TypeScript project references 或依赖图规则限制跨层引用，禁止业务包反向依赖基础包。
  • 内部包统一版本或独立版本取决于发布模式；Changesets 可记录变更并生成版本/changelog。应用与库需要明确 owner 和兼容策略。
  • 公共包变更要契约测试；CI 按受影响图执行 lint/typecheck/test/build。周期性检查循环依赖、重复依赖和废弃导出。
  • “共享”应有准入门槛：至少两个稳定消费者、语义一致、维护责任明确，否则复制少量代码可能更便宜。
延伸联想

“我可以把 Monorepo 依赖治理和我审计 5 个仓库发现默认分支空壳、tag 缺失的发布治理串起来讲。”

边界与常见误区

“具体选 Nx/Turbo/Changesets 可以讨论，但边界规则、owner、契约和可追踪发布是必须项。”

23大型前端项目的 CI/CD 质量门禁应如何分层？
为什么重要

关键在于判断是否有技术负责人级交付意识。

要点
  • 提交前做快速格式/lint；PR 做类型检查、单测、受影响构建、依赖与安全扫描；主干/候选版本做集成、E2E、视觉回归和产物检查。

  • 真实案例：审计 5 个仓库发现默认分支空壳、真实代码在 dev、tag 缺失，推动打 tag、清理分支及“分支—文件—改动”映射文档化。

“我不是只讲理想流水线，可以展开讲从混乱仓库迁移时怎样避免影响现网。”

边界与常见误区

“某家公司的工具链我需要适配，但产物可追溯、自动验证、渐进发布和可回滚四个目标不变。”

24前端测试金字塔如何落到 React/Vue、SSE 和多端项目？

看质量策略是否与风险匹配。

25如何建设可观测的前端埋点体系，又避免侵入业务代码？

关键在于理解数据闭环、架构抽象与隐私意识。

要点
  • 分技术指标（Web Vitals、JS error、资源失败）、行为事件和业务漏斗；统一 event schema、版本、公共上下文和 traceId。

“我可以把埋点进一步连接到 AI 应用评测：体验指标和模型质量指标必须分层观察。”

26从输入 URL 到页面可交互，浏览器经历了什么？
为什么重要

综合考察网络、解析、渲染与性能定位能力。

要点
  • URL 解析、缓存/Service Worker 检查、DNS、连接建立（TCP+TLS 或 QUIC）、HTTP 请求响应；可能经历代理、重定向和 CDN。
  • HTML 流式解析生成 DOM，CSS 生成 CSSOM；样式计算后形成 layout tree，布局、绘制、分层、栅格化与合成。同步脚本会阻塞解析，CSS 会影响渲染和脚本执行时机。
  • 可交互还取决于 JS 下载、解析、执行、框架 hydration/初始化和主线程空闲，不等于 load。
  • 用 Navigation Timing、Resource Timing、Performance trace 分段，不把所有慢都归因于网络。
延伸联想

“我可以用某三甲医院首屏优化的真实结果讲资源体积、加载优先级和渲染链路如何联动。”

27如何制定首屏性能优化方案和验收指标？
为什么重要

看能否从指标到诊断再到收益闭环。

要点

  • 网络侧：CDN、压缩、缓存、HTTP/2/3、preconnect/preload 谨慎使用；资源侧：图片格式/尺寸、字体子集、代码拆分；执行侧：减少主线程长任务、延迟非关键第三方。
  • 保证关键内容优先、占位尺寸防 CLS；性能预算进入 CI，发布后观察回归。优化必须记录基线、变更和同条件结果。
  • 某三甲医院项目可引用：图片资源压缩后体积减少 53%，图片加载策略优化使首屏加载时间减少 50%～60%；不要扩写材料未记载的具体 CDN 实施数字。
延伸联想

“这不是理论成绩，我能继续讲如何证明 50%～60% 的改善以及怎样防回退。”

“我会先拿 waterfall 和主线程 trace 建基线；没有数据时不会先承诺某个优化百分比。”

28重排、重绘、合成分别是什么？动画如何避免卡顿？
为什么重要

关键在于检查渲染流水线和交互性能基础。

要点
  • layout/reflow 重新计算几何；paint 生成绘制指令；composite 合成图层。影响范围取决于属性和布局结构，不宜背“某属性绝对只触发某阶段”。
  • 动画优先 transform/opacity，使用 requestAnimationFrame 与刷新率同步；批量读写 DOM，避免读布局后写样式反复触发强制同步布局。
  • will-change 只对明确热点短期使用，过多图层会增加显存与合成开销。高频计算可 Worker 化，但 DOM 仍在主线程。
  • DevTools Performance 查看 Layout、Paint、Compositor、long task，而不是凭肉眼判断。
延伸联想

“AI 流式文本虽不是传统动画，但同样需要按帧批量提交，避免高频 layout 与 Markdown 重解析。”

边界与常见误区

“不同浏览器的分层启发式会变，我会用 trace 验证；通用策略是减少布局抖动和主线程长任务。”

29HTTP 缓存应该如何组合使用？发布后如何避免旧 HTML 引用新旧资源错配？
为什么重要

看生产发布与网络基础是否打通。

要点
  • 强缓存由 Cache-Control: max-age/immutable 等控制；协商缓存用 ETag/If-None-Match 或 Last-Modified。浏览器缓存、CDN 和 Service Worker 是不同层。
  • 带内容哈希的静态资源可长缓存 immutable；HTML 短缓存或 no-cache，以便及时拿到新资源清单。
  • 发布采用资源先上传、HTML 后切换，旧资源保留一段时间；多版本并存和原子切换避免 HTML/资源错配。回滚也必须保留对应资源。
  • API 按数据敏感性和一致性设私有缓存，医疗数据不能进入公共 CDN 缓存。
延伸联想

“我处理过 Nginx 静态资源缓存、多环境部署和子路径代理，可以继续讲发布次序与回滚设计。”

边界与常见误区

“缓存头的细节可按场景确认，但我会确保 HTML 可更新、哈希资源长缓存、发布期间多版本可取。”

30SSE、WebSocket、长轮询如何选？SSE 经过代理时有哪些坑？
为什么重要

针对实时 AI 应用考察协议与生产运维。

要点
  • SSE 基于 HTTP、服务端到客户端单向、文本事件、浏览器 EventSource 可自动重连；适合 LLM 流式输出。WebSocket 全双工，适合高频双向实时互动；长轮询兼容性好但开销和延迟更高。
  • 原生 EventSource 通常不能方便地自定义 Authorization header，可能用 cookie、短期 token、fetch streaming 或代理；需考虑同源、连接数和鉴权续期。
  • Nginx/网关要关闭或调整响应缓冲与压缩，设置正确 Content-Type，及时 flush，延长 read timeout，防 CDN/代理把流聚合；心跳防空闲断开。
  • 某三甲医院智能代理有 SSE 流式代理；AI Gateway 个人/基础设施项目针对国内 SSE 长连接设计 Cloudflare 管理路径与 Caddy API 直连路径，引用时说明项目边界。
延伸联想

“我既做过浏览器端增量渲染，也排查过代理链路，您想听协议选型还是线上断流诊断？”

边界与常见误区

“具体网关参数按部署环境确认，但我会从缓冲、超时、心跳、鉴权、重连五项排查。”

31XSS 有哪些类型？React/Vue 是否自动解决了 XSS？
为什么重要

关键在于检查前端安全边界，尤其 AI 生成内容的风险。

要点
  • 反射型、存储型和 DOM 型 XSS；本质是不可信数据进入可执行上下文。React/Vue 默认文本插值会转义，但 dangerouslySetInnerHTML/v-html、URL、CSS、脚本拼接和第三方 Markdown 渲染仍有风险。
  • 按输出上下文编码；富文本用可靠 sanitizer 白名单；禁 javascript: URL；CSP、Trusted Types 可作为纵深防御，不能替代源头处理。
  • AI 输出是不可信输入，Markdown 中的 HTML、链接、图片 URL、代码预览都要治理；token 不放可被脚本读取的长期存储更稳妥。
  • 依赖供应链、source map、DOM clobbering 也应进入威胁模型。
延伸联想

“AI 应用把模型输出直接渲染，XSS 风险比普通 CRUD 更突出，我可以展开讲 Markdown 安全管线。”

边界与常见误区

“我不会说框架已经安全；遇到富文本会先当不可信 HTML，做白名单净化并加 CSP 验证。”

32CSRF 的原理和防护是什么？SameSite 能否完全替代 CSRF Token？
为什么重要

关键在于理解是否理解浏览器凭证自动携带与现代防护组合。

要点
  • CSRF 利用浏览器自动携带 cookie，在用户不知情时向目标站发起有副作用请求；攻击者通常不需要读取响应。
  • 防护组合：SameSite=Lax/Strict、CSRF Token、校验 Origin/Referer、敏感操作二次确认；状态变更不用 GET。
  • SameSite 受兼容性、跨站业务、子域/同站边界影响，不应成为所有场景唯一防线。CORS 不是 CSRF 的通用防护，因为简单请求仍可发出。
  • 若使用 Authorization header 且凭证不自动附带，风险模型不同，但要重新评估 XSS 与 token 存储风险。
延伸联想

“我做医疗数据合规整改时会把身份、传输、日志和浏览器侧防护放在同一张威胁模型里。”

边界与常见误区

“SameSite 细粒度规则我会按当前浏览器文档确认，但生产上不会只靠单一机制，会结合 Token 与 Origin 校验。”

33SSRF 明明是服务端漏洞，为什么前端/AI 全栈负责人也必须懂？
为什么重要

关键在于检查跨栈安全意识和边界判断。

要点
  • SSRF 是服务端替攻击者请求任意地址，可能探测内网、访问云 metadata、读取内部管理接口；前端 URL 校验不能作为安全边界。
  • 服务端采用目标 allowlist、解析后验证 scheme/host/port、DNS 与最终连接 IP 双重约束、防 DNS rebinding、禁止/限制重定向、网络层 egress policy、超时和响应大小限制。
  • AI 产品常有网页抓取、图片代理、知识库导入、Webhook、插件工具调用，SSRF 面显著扩大；还要阻止 file/gopher 等危险协议与私网/环回/链路本地地址。
  • 项目资产中确有 SSRF、路径遍历修复及两轮整改、四份分析/复核/复测/验证报告，可讲完整闭环，不虚构具体漏洞 URL。
延伸联想

“这正体现我不是只写页面：我可以从发现、修复、复测讲安全治理闭环。”

边界与常见误区

“具体绕过手法我不会实践中猜，但会坚持应用层校验与网络层出站限制双保险，并由安全复测验证。”

五、大前端架构与技术负责人视角（34～39）

34Web、Flutter、React Native、原生 iOS/Android、Tauri/Electron 如何做跨端选型？
为什么重要

看技术负责人能否用约束和总成本决策，而非技术偏好。

要点
  • 先列业务约束：设备能力、性能/包体、离线、更新频率、上架政策、桌面系统集成、既有团队与交付周期。
  • Web/H5 迭代快、分发轻；Flutter UI 一致性强但需 Dart 与原生桥接；RN 复用 React 生态但仍有原生边界；原生能力、体验与审核控制最好但双端成本高；Electron 生态成熟但资源占用较高，Tauri 更轻但插件成熟度需评估。
  • 复用重点通常是协议、领域模型、设计 token、测试规范，而非强求 UI 代码 100% 复用。
  • 真实履历覆盖 Vue/React、Flutter/Taro/小程序、Electron/Tauri、SwiftUI iOS 与 Android；AI医疗辅助App 由本人独立完成全部提交并经历 App Store v1.2.0→1.2.1 审核整改。
延伸联想

“我可以用AI医疗辅助App原生上架和企微/Electron 多端产品对比，讲一次真实选型的组织成本。”

边界与常见误区

“我不会直接报框架名，会先要设备能力、体验目标、团队结构和上线节奏四组信息，再给加权决策。”

35如何设计大型团队的前端研发规范，而不让规范变成文档摆设？
为什么重要

关键在于理解管理、治理与落地能力。

要点
  • 规范分层：必须自动执行的格式/lint/type/test/依赖边界；需评审的架构与安全；供参考的最佳实践。能机器检查的绝不只写文档。
  • 建 RFC/ADR 记录关键决策，CODEOWNERS 明确责任，模板统一 PR 风险、测试和回滚说明；指标看 review 时长、逃逸缺陷、构建时间，而非规范页数。
  • 推行要从高痛点试点，提供迁移脚本与例子，设豁免期限；定期删除过时规则。负责人也要写核心代码和处理例外，避免规则脱离现实。
  • 可引用历史上管理 3 个团队、推动 Flutter/Vue/AMIS 转型，以及当前发布流程审计经验；不要夸大当前团队规模。
延伸联想

“我的管理模式一直偏技术负责人+独立贡献者，我可以讲如何用工具门禁降低跨团队沟通成本。”

边界与常见误区

“我不会先发一份大规范；会从最近三类高频故障反推规则，并把可检查部分进入 CI。”

36多环境、多仓库、多客户部署如何治理发布与配置？
为什么重要

看能否处理企业项目规模化交付的复杂度。

要点
  • 同一制品跨环境晋级，配置与代码分离；配置 schema 校验，密钥进入 secret manager，不在前端 bundle 或仓库中。
  • 环境矩阵明确域名、API、鉴权、功能旗标、版本；客户差异优先配置/插件化，避免长期分叉。部署产物带 commit、build id、配置版本。
  • 建环境冒烟、兼容性检查、灰度和回滚；数据库/API 变更采用向后兼容的 expand-contract，避免前后端必须同秒发布。
  • AI医疗助手产品覆盖多家社区医院试点和多环境代理；智能代理支持路演多环境部署；多仓审计推动 tag 与分支治理，均可用于说明现实复杂度。
延伸联想

“我可以继续讲‘客户定制不分叉代码’的边界，以及默认分支空壳这类历史债怎么迁移。”

边界与常见误区

“具体平台可以是 GitHub/GitLab/Jenkins，但我会先确保制品不可变、配置可验证、版本可追踪、发布可回滚。”

37低代码平台应该自研还是采购？如何避免最后成为不可维护的“第二套前端框架”？
为什么重要

关键在于理解平台产品判断和架构克制。

要点
  • 先判断场景是否高重复、低差异、组件可枚举、权限和数据模型稳定；复杂交互和高性能核心链路不适合强塞低代码。
  • 采购看连接器、扩展 SDK、权限、版本迁移、私有化和锁定成本；自研只有在业务差异形成长期壁垒且有平台团队时才成立。
  • 核心是 schema 版本、组件契约、数据源/动作模型、权限、校验、发布回滚和逃生舱；生成物必须可测试、可观测、可迁移。
  • 曾在某基座大模型公司主导可视化低代码能力、在某到家服务平台推动 AMIS 技术转型，可据实讲决策方法，不编造成果数字。
延伸联想

“我可以从 AMIS 与自建可视化能力的经验讲‘什么不该低代码化’，这通常比功能清单更重要。”

边界与常见误区

“我会先做场景标准化率和五年 TCO 评估；如果 schema 与扩展边界不清，不会贸然平台化。”

38如何把 AI Coding/Agent 真正引入研发流程，同时守住代码质量和数据安全？
为什么重要

关键在于判断 AI 辅助研发是否有可执行方法论，而非追热点。

要点
  • 按风险分层：文档/测试草稿、局部重构、独立功能、核心安全代码分别设置不同的人审与验证要求；Agent 只获得最小权限和明确验收边界。
  • 上下文提供架构约束、代码规范、测试命令和完成定义；产出必须过 diff review、类型/测试/安全扫描，不能用“模型说通过了”作为证据。
  • 敏感仓库要管控上传、凭证、日志与第三方模型；记录模型/提示/变更来源以便审计。用 lead time、缺陷逃逸、review 成本评价，而非生成代码量。
  • 真实资产包括 53 个 AI Engineering 专题、51 份可演讲课件，以及共享 Skill/标准流程；表达为已验证的方法论与流程，不以 Skill 数量冒充业绩。
延伸联想

“我可以讲‘人定目标与验收边界，Agent 执行、验证并沉淀’如何落到 PR 和发布门禁。”

边界与常见误区

“某款工具能力变化快，但最小权限、可追溯 diff、自动验证和人工责任主体四条不会变。”

39遇到技术债、交付压力和业务需求同时到来，技术负责人如何排序？
为什么重要

看风险判断、沟通与长期治理能力。

要点
  • 用“发生概率 × 影响 × 暴露面 × 修复成本”评估；安全、数据不可逆、发布不可回滚类债务优先，纯洁癖式重构靠后。
  • 把债务翻译成业务风险：故障时间、交付吞吐、合规、客户影响；给出立即止血、中期治理、长期预防三层方案。
  • 预留固定容量、把债务绑定业务变更顺手清理，设 owner、期限和可验收指标；若暂不修，记录接受风险的人和触发条件。
  • 可用多分支合一、下掉冗余 Azure TTS 做架构收敛、5 仓发布整改说明“删复杂度”和“保交付”并重。
延伸联想

“我有一个典型例子：不是继续堆更多语音引擎，而是移除 Azure TTS 收敛架构，可以展开讲决策依据。”

边界与常见误区

“信息不足时我不会承诺大重构，会先做风险清单和止血方案，再和业务共同确认可接受风险。”

六、系统设计题（40～41）

40设计一个“企业微信家医助手”的多端状态同步前端架构：Web 管理台、企微侧边栏、Electron 桌面端同时处理群消息与 AI 回复。
为什么重要

综合考察多端架构、状态一致性、实时通信、并发安全、离线恢复与技术负责人决策。

要点
  • 边界与模型： 服务端是会话真相源；领域对象包括 conversation、message、AI task、draft、operator。每个命令携带 clientId、幂等键、baseVersion；事件有全局/会话 sequence 和 serverVersion。
  • 通信： 历史与命令走 HTTP，增量事件按场景用 WebSocket 或 SSE；重连携带 lastSequence，先补 gap 再恢复实时。多 tab 可用 BroadcastChannel/SharedWorker 共享连接，跨 Electron/企微端则由服务端统一广播。
  • 一致性： 本地先乐观更新，服务端用版本号/乐观锁判冲突；冲突按业务选择重放、合并或提示。AI 回复任务使用单飞/并发守卫，键盘连发只接受一次，finally 释放；服务端幂等兜底，不能只靠按钮 disabled。
  • 前端分层： shared 包放协议 schema、领域 reducer/state machine、设计 token 与埋点；各端保留适配层（企微 JS-SDK、Electron IPC/HID、浏览器 API），不强求 UI 全复用。运行时 schema 校验协议。
  • 体验与故障： 消息状态明确 pending/sent/failed/streaming；断网进入只读或离线队列；AI 超时可取消/重试；长列表虚拟化、流式内容按帧批量更新。
  • 安全与观测： 最小权限、敏感医疗内容脱敏、企微签名与 token 不落前端、traceId 串联命令和 AI task；监控重复回复率、冲突率、断线率、消息端到端延迟。
  • 真实项目连接： AI医疗助手产品覆盖多类医疗场景；企微助手已有并发守卫、乐观锁版本控制和系统性的 Figma 走查整改；本人是企微前端团队中贡献占比最高的成员。send-helper 的 HID 方案为企微 JS-SDK 无法自动回车的本地边界方案，全部提交均由本人完成。
延伸联想

“这不是纸面设计，我可以重点复盘真实的键盘连发重复回复、乐观锁以及 JS-SDK 能力边界。”

边界与常见误区

“我会先明确服务端真相源和消息一致性等级；协议细节未知时，先用幂等键、版本号、序列游标和显式状态机搭出可验证骨架。”

41设计一个面向多业务线的 AI Agent Web 平台：Monorepo、SSE 流式对话、多环境部署、埋点与灰度发布。
为什么重要

综合检验前端平台架构、AI 流式体验、工程化、可观测性和发布治理。

要点
  • 目标拆解： 区分平台共性（认证、会话、模型/Agent 协议、流式解析、组件库、埋点、配置）与业务差异（医院/金融领域页面、工具卡片、权限）；先定义 SLO、浏览器范围、租户隔离和部署拓扑。
  • 仓库架构： PNPM workspace + Turborepo；apps/* 放业务应用，packages/protocol、stream-client、ui、auth、tracing、config 放稳定能力。用依赖规则禁止业务反向污染基础包；任务 inputs/outputs/env 完整声明，CI 按 affected 图执行。
  • 流式链路： BFF/代理统一 Dify/模型供应商差异，输出版本化事件协议；前端解析为可辨识联合类型，按 taskId/sequence 去重，支持取消、心跳、超时、重连与降级到非流式结果。chunk 缓冲后批量渲染。
  • 状态与缓存： 服务端数据交给 query cache，会话生成用显式状态机，短暂 UI 状态本地化；URL 承载可分享导航。避免把所有数据塞进 Zustand；store 用 selector 控制更新。
  • 环境与发布： 同一制品、运行时配置；租户/场景 feature flag；静态资源内容哈希多版本保留，HTML 后切换；tag 对应制品，灰度指标异常自动/人工回滚。
  • 质量与安全： 协议契约测试、分片流测试、核心 E2E、性能预算；AI Markdown 白名单净化，代理防 SSRF，医疗日志脱敏，权限与租户隔离在服务端强制。
  • 观测： EventTracing 统一 schema，traceId 串联页面—BFF—Dify；看首 token 延迟、完成率、断流率、重试率、前端 INP/LCP 和业务转化，模型质量另走评测体系。
  • 真实项目连接： 某三甲医院智能代理即 React18+TS+Ant Design+Turborepo+PNPM+Zustand，具备 SSE、Dify 会话代理、EventTracing 和多环境部署；本人主导绝大多数提交、持续 12 个月。
延伸联想

“我可以实践中继续画 package 依赖图，或重点展开 SSE 代理经过 Nginx/网关时的生产问题。”

边界与常见误区

“我会先确认租户隔离、协议归一和部署拓扑三项，因为它们会决定后续包边界；具体工具可以替换，架构约束不能省。”
