一、AI Coding 工具机制与选型（1—6）

1Claude Code、Codex、Cursor 这类工具的共同核心架构是什么？
为什么重要

关键在于判断实践者是否理解 Coding Agent，而不只是熟悉 UI 和快捷键。

要点
  • 共同内核是一个受约束的 agentic loop：接收目标与上下文→形成下一步动作→调用读文件、检索、编辑、Shell、浏览器或 MCP 等工具→观察结果→修正计划→验证→在终止条件满足时交付。
  • 模型只是决策组件，真正决定工程上限的是 Harness：上下文如何装配、工具如何暴露、权限如何控制、状态如何保存、失败如何恢复、验收如何判定。
  • IDE 型产品更容易利用当前文件、选区、诊断和索引；终端型 Agent 更贴近仓库、脚本、Git 和 CI，适合跨文件长任务与自动验证。具体产品能力持续变化，应按当前版本实测，不把阶段性功能说成永久差异。
  • Coding Agent 与普通聊天助手的关键区别是它能改变外部状态。因此工具调用、副作用、工作区隔离、diff 和测试结果比“回答看起来正确”更重要。
  • 实践者可结合日常用 Claude Code、Codex、Cursor 做前端/全栈真实交付的经验，强调自己关注的是完整闭环，不是代码补全速度。
延伸联想

先画“模型—Harness—工具—工作区—验证器”五层图，再结合当前环境确认当前痛点在模型能力、上下文、工具、权限还是验收层。

边界与常见误区

各产品内部未公开的调度细节我不会臆测，但可观测的共同工程结构很明确：模型在受控循环中读取环境、执行工具、根据反馈迭代，并由外部验证决定是否完成。

2三类工具在工程形态上有哪些核心差异？如何避免做成“品牌横评”？
为什么重要

关键在于理解选型是否基于任务和治理，而不是个人偏好。

要点
  • 比较维度应包括交互入口、代码库索引、长任务自治、工具扩展、MCP/插件生态、非交互执行、权限粒度、沙箱、审计、企业数据策略、模型可选性、成本与团队学习曲线。
  • IDE-first 工具适合高频局部修改、补全和可视化审查；CLI/agent-first 工具适合仓库级任务、脚本化验证、并行工作区和 CI 接入。两者可共存，不必强制全团队只用一种。
  • 区分“模型能力”和“产品 Harness 能力”：同一模型在不同上下文装配、工具权限与验证循环下，交付质量可能明显不同。
  • 选型用代表性任务集实测：小修复、跨模块重构、陌生仓库定位、测试补齐、安全修复、前端视觉验收；记录一次通过率、人工修订时间、回滚率、成本和 P95 时长。
  • 数据安全与权限是准入项，不是加权项；不满足代码出域、密钥和审计要求的工具不能靠更高生成质量抵消。
延伸联想

给出“任务—工具”矩阵，并指出优秀方案通常是统一底线、允许多入口，而不是采购一个工具就宣布完成转型。

边界与常见误区

具体版本的功能差异会变化，我不会背产品宣传页；我会用同一仓库、同一任务、同一验收集做基准测试，再结合安全与总成本决策。

3Coding Agent 的上下文是怎样构成的？上下文窗口越大越好吗？
为什么重要

关键在于识别是否把“把整个仓库塞进去”当成 Context Engineering。

要点
  • 上下文通常包含系统/项目规则、用户目标、当前计划、相关代码与配置、工具 Schema、历史工具结果、diff、测试/编译错误和阶段性摘要。
  • 大窗口解决容量，不解决相关性、冲突和注意力稀释。无关文件、过期日志、重复输出会增加成本并诱发错误修改。
  • 应采用渐进式发现：先读目录、规则、入口和符号关系，再按假设加载最小相关切片；工具大输出落文件或摘要，只把下一步必需信息留在工作上下文。
  • 稳定规则放仓库级说明，任务事实由代码和测试提供，临时决策放计划/状态；三者分层，避免一段巨型 Prompt 同时承担所有职责。
  • 压缩时保留目标、约束、已改文件、未决风险、验证结果与证据引用，而不是只生成自然语言聊天摘要。
延伸联想

用“上下文预算表”说明每类信息为什么进入、何时淘汰、权威来源是什么。

边界与常见误区

我不会靠盲目扩大窗口解决问题；会先建立相关性检索、权威来源、摘要检查点和验证反馈，确保上下文小而可信。

4Sandbox、权限模型和人工审批在 Coding Agent 中分别解决什么问题？
为什么重要

关键在于理解对 Agent 外部副作用的安全意识。

要点
  • Sandbox 限制进程能读写的文件、网络、系统调用和资源；权限模型决定某类工具在什么作用域可用；人工审批用于风险无法完全程序化判断的高影响动作。三者互补。
  • 默认最小权限：只写任务工作区，只访问允许域名，不读取用户主目录和生产凭据；读、写、执行、联网、部署分级授权。
  • 命令审批不能只看命令名，还要解析目标路径、参数、重定向和环境变量。高风险动作使用明确目标、dry-run、短期 capability token 和二次确认。
  • Prompt injection 可能来自 README、网页、issue 或依赖输出；外部文本是数据，不得改变系统权限。服务端必须重新鉴权，不能相信模型声称“用户已同意”。
  • 变更应在 Git 分支/worktree 或容器中进行，配合 diff、快照和可逆操作；生产部署、数据迁移、密钥轮换不由 Agent 自主完成。
延伸联想

主动把工具按 L0 只读、L1 工作区写、L2 外部低风险写、L3 生产高风险分级，并给出每级审批策略。

边界与常见误区

不同产品的沙箱实现我需要查当前文档，但原则不变：模型不构成安全边界，权限由确定性系统最小化授予，高影响副作用必须可审计、可撤销或人工确认。

5如何建立 AI Coding 工具的团队级选型评测？
为什么重要

关键在于判断能否把个人体验转化为可复现的工程决策。

要点
  • 从真实历史任务抽取脱敏 benchmark，按难度和类型分层，固定仓库版本、任务说明、权限、预算和验收脚本；避免只用玩具算法题。
  • 指标包括任务成功率、首次验收通过率、人工介入分钟数、缺陷逃逸率、安全违规次数、P50/P95 时长、token/API 成本和开发者主观负荷。
  • 至少重复多次以处理模型随机性；盲审 diff，记录失败类别。只比较“最好的一次”会产生严重选择偏差。
  • 评测同时覆盖 cold start 与熟悉仓库、局部任务与长任务；还要测取消、超时、上下文污染、工具失败和恢复能力。
  • 最终不是选“最聪明模型”，而是选单位合格交付成本最低、治理边界可接受、能进入团队流程的组合。
延伸联想

建议先做两周小样本试点，输出失败分类和置信区间，再决定许可、席位与默认工具。

边界与常见误区

我没有当前团队代码上的现成结论，但可以先定义任务集和验收器，用真实交付数据替代工具口碑，逐步形成可复跑的内部榜单。

6为什么熟练使用工具仍可能导致代码质量失控？负责人如何治理？
为什么重要

关键在于确认是否把速度提升误当工程成熟度。

要点
  • Agent 会放大既有系统：清晰架构、测试和规范会被放大，混乱边界、弱测试和模糊需求也会被更快复制。生成速度提高后，审查吞吐往往成为瓶颈。
  • 治理应把目标从“生成代码”改为“交付可验证变更”：任务小批量、验收标准前置、强制 diff、自测、静态扫描、依赖审计、关键模块 owner 审核。
  • 按风险分层自治：文档和低风险测试可高自治；业务逻辑需 PR；认证、支付、医疗建议、数据迁移需要专家审核和更强证据。
  • 建立 AI 变更可追踪性，但不以“AI 写的”替代责任归属。提交者仍对设计、许可证、安全和线上结果负责。
  • 用生产缺陷、返工和交付周期监测是否失控；若速度升而返工、回滚、review wait time 同步上升，说明只是把成本后移。
延伸联想

提出 WIP 限制：Agent 并行开工数量必须受团队 review 和验证能力约束。

边界与常见误区

我不会承诺靠一份 Prompt 保证质量；负责人要把测试、审查、权限、风险分级和指标做成系统门禁，让快生成不能绕过慢判断。

二、Agent Harness 设计与执行控制（7—12）

7什么是 Agent Harness？它与模型、Agent 框架、IDE 插件有什么边界？
为什么重要

关键在于判断对 Harness 是否有可落地定义。

要点
  • Harness 是包围模型的执行与治理系统：负责输入规范化、上下文装配、计划/循环、工具调度、状态、权限、预算、观测、验收、重试和产物交付。
  • 模型负责概率性推理与生成；Agent 框架提供编排抽象；IDE/CLI 是交互入口；Harness 把这些能力组织成可重复、可验证、可运营的工程系统。
  • 一个最小 Harness 至少有 run、step、tool call、artifact、checkpoint、policy、verifier 七类对象，且模型不能自行宣布成功。
  • 自研不等于从零实现模型 SDK、终端或索引。应复用成熟组件，只在企业工作流、状态协议、权限、验收和沉淀机制上建立差异化。
  • 可引用 mini-harness（个人项目、个人时间产出） 作为对 Harness 抽象的真实探索，准确说明已实现部分，不用框架名称夸大生产规模。
延伸联想

用一句话收口：“Agent 是会做事的决策体，Harness 是让它安全、稳定、可验证地把事做完的工程外壳。”

边界与常见误区

行业对 Harness 命名尚未完全统一，我采用工程定义：凡是负责模型之外的执行控制、上下文、工具、状态、验证和治理，都属于 Harness 范畴。

8什么情况下值得自建 Harness，什么情况下不值得？
为什么重要

关键在于理解平台化冲动与 ROI 判断。

要点
  • 值得自建的信号：任务重复且跨工具、需要专有权限与审计、长任务需恢复、验收可程序化、现有产品难接内部系统，或多团队重复搭相同胶水层。
  • 不值得的情况：需求仍在探索、单人低频任务、成熟工具已满足、没有维护 owner、没有评测数据。此时 Prompt + 脚本 + CI 可能已足够。
  • 采用 build/buy/compose 分层：模型接入、协议、沙箱尽量买或复用；企业特有策略、任务模板、验证器和资产目录按需自建。
  • 先从一条高价值“黄金路径”验证：基线耗时、失败率、人工介入与风险改善达到阈值后，再抽象平台能力。
  • mini-harness（个人项目） 能证明实践者理解机制；要产品化仍需补租户、权限、观测、队列、兼容性、SLA 和运维，不能直接宣称企业就绪。
延伸联想

主动列出“不造什么”，能体现负责人控制平台边界的能力。

边界与常见误区

我会先用真实流程验证价值，不会因为 Harness 热门就造平台；只有重复性、治理要求和投入回报同时成立才进入自建。

9长任务的状态模型和检查点应该如何设计？
为什么重要

关键在于理解能否让 Agent 从对话 Demo 变成可恢复系统。

要点
  • 控制状态可设 QUEUED/RUNNING/WAITING_APPROVAL/WAITING_RETRY/PAUSED/SUCCEEDED/FAILED/CANCELLED，业务阶段独立建模，避免把“运行状态”和“做到哪一步”混为一谈。
  • 每步记录 run_id、step_id、attempt、input_hash、policy_version、model/tool_version、artifact_ref、verdict、cost、timestamp；用事件日志加物化状态支持审计和恢复。
  • 检查点应保存可重建的状态、不可重复副作用的回执和产物引用，而不是只保存聊天历史。恢复前验证代码基线、依赖版本和外部资源是否已漂移。
  • 写操作通过幂等键、乐观锁、事务边界或补偿动作避免重复；明确 cancel 与 pause 的语义。
  • 可引用 NovelReel（个人项目、个人时间产出） 的三层编排、状态持久化、断点续跑以及完整测试集，作为长任务工程化实例。
延伸联想

画出“事件日志是事实、当前状态是投影、产物存储是证据”的三层结构。

边界与常见误区

具体存储选型需结合吞吐量，但核心不会变：状态显式、步骤幂等、产物可寻址、版本可追踪、恢复前校验环境漂移。

10如何设计 Agent 的验收边界，避免模型自说自话？
为什么重要

关键在于确认是否掌握 Harness 最关键的“完成定义”。

要点
  • 人负责定义目标、禁止项、可修改范围、验收命令、风险等级和需要人工决策的节点；Agent 负责执行、收集证据、修正并交付。这就是“人定目标与验收边界，Agent 执行、验证并沉淀”。
  • 验收分层：语法/类型→单元与集成测试→安全/许可证→架构约束→行为与视觉→人工业务判断。越靠后越难完全自动化。
  • 验收器必须独立于生成声明：测试进程退出码、结构化扫描结果、快照或人工签字才是 verdict；“我已完成所有测试”不是证据。
  • 定义 hard gate 与 soft signal。认证绕过、测试失败是硬拒绝；复杂度上升可作为 review 提示，避免指标机械化。
  • 交付包包含 diff、验证命令与结果、未覆盖范围、风险和回滚方式；验收失败回到限定循环，超过预算转人工。
延伸联想

技术讨论中先问“谁有权宣布 done？”并回答“不是模型，而是策略化 verifier 与责任人”。

边界与常见误区

业务正确性未必都能自动证明，我会把可机器验证的先做硬门禁，把价值判断显式留给人，绝不让模型置信度代替验收。

11Agent 失败应怎样分类、重试、降级和回滚？
为什么重要

关键在于判断异常处理是否只是“再问模型一次”。

要点
  • 区分瞬时错误、限流、工具不可用、权限拒绝、输入不完整、代码验证失败、策略违规、模型能力不足和预算耗尽；只有可恢复错误才重试。
  • 重试采用退避、抖动、次数/时间/成本上限，并改变条件：缩小任务、补上下文、切工具或模型。原样无限重试只会重复消费。
  • 降级可从全自动改为生成方案/草稿，从强模型切备用模型，从并行改串行，从完整功能退到核心路径；安全拒绝不能换模型绕过。
  • 回滚优先依赖隔离工作区、原子提交、Git revert、产物版本和数据库补偿；开始前即判断操作是否可逆，不可逆动作必须审批。
  • NovelReel（个人项目） 可用于说明模型/媒体生成失败降级和断点续跑，但需如实限定为个人工程实践。
延伸联想

提出“失败预算”：一次 run 允许多少次调用、多少分钟、多少钱、多少次修改同一文件，耗尽就停止并呈报。

边界与常见误区

阈值要靠运行数据校准；我能先把错误可恢复性、幂等、预算、降级和人工接管建起来，避免无界循环与不可逆损失。

12人机协作中哪些决策必须由人保留？
为什么重要

关键在于理解自治边界和责任设计。

要点
  • 人保留目标优先级、需求冲突、架构重大取舍、风险接受、生产变更、合规解释和最终业务验收；Agent 适合搜索、实现、测试、证据整理和重复性修复。
  • 以不确定性×影响面划分：低影响低不确定可自动；低影响高不确定可探索但不提交；高影响低不确定需审批；高影响高不确定必须人工主导。
  • 审批点应提供选项、证据、成本和可逆性，不要让人通读全部轨迹；否则 human-in-the-loop 会退化成审批疲劳。
  • 人的修改和拒绝要结构化回流到规则、测试、Skill 或评测集，减少同类问题再次审批。
  • 实践者的个人协作方式可表述为：在个人项目与个人工程实践中，自己定目标和验收边界，让 Agent 执行验证，再把稳定做法沉淀为 Skill；不宣称已在公司全员制度化落地。
延伸联想

强调目标不是“人少点一下”，而是把人的稀缺判断力放在高杠杆节点。

边界与常见误区

我不会用固定自治比例回答；应按风险、可逆性和验收能力动态授权，并让每次越界都有明确责任人。

三、Skill、跨工具共享与 MCP（13—16）

13什么样的重复工作值得沉淀为 Skill？
为什么重要

关键在于判断能否把个人技巧变成可维护资产。

要点
  • Skill 是有触发条件、输入输出契约、步骤、工具权限、验收标准、失败处理和示例的可复用能力包，不只是一段长 Prompt。
  • 适合沉淀的任务应高频、流程相对稳定、错误可检测、收益可复用；一次性探索和强依赖隐性判断的工作先保留为 playbook。
  • 从真实成功轨迹抽取不变量，删除项目私有信息，明确前置条件、禁止项和退出条件；把可确定的操作写成脚本，把语义判断留给模型。
  • 每个 Skill 要有最小示例、反例、fixture/测试和人工 owner；用调用成功率、返工率和节省的人工时间淘汰低价值 Skill。
  • 可引用个人 Skill 与跨工具自动化（个人项目、个人时间产出）：课程制作、AI 视频、图像生成质检、飞书桥接、周报、内容发布、Git 交付、浏览器自动化等。
延伸联想

实践中把一个“发布内容”流程拆成输入契约、执行脚本、审核点、发布回执和回归样例，展示 Skill 不是提示词收藏夹。

边界与常见误区

我会先观察三到五次真实执行，确认稳定模式和失败边界后再封装；过早抽象比没有 Skill 更容易固化错误流程。

14Skill 如何做版本管理、测试、发布和退役？
为什么重要

关键在于理解 Skill 是否按软件资产治理。

要点
  • Skill 与代码一样进入 Git，采用语义化版本或明确的兼容策略；变更记录说明 Prompt、脚本、工具 Schema、权限与输出契约变化。
  • 测试分层：静态检查、脚本单测、fixture 回放、工具契约测试、模型评测集和少量端到端 canary。随机模型输出用不变量和评分规则验证，不硬比全文。
  • 发布采用 registry/catalog、owner review、签名或来源校验；运行记录 Skill 版本、模型和工具版本，便于复现。
  • 破坏性升级提供迁移说明、灰度与回滚；长期无人使用、成功率差或依赖失效的 Skill 标记 deprecated 后退役。
  • 敏感变量通过 secret manager 注入，不能写进 Skill；第三方 Skill 当供应链依赖审查，限制工具与网络权限。
延伸联想

提出“Skill SLO”：成功率、人工介入率、P95 时长和兼容矩阵，使资产有维护依据。

边界与常见误区

不同工具的 Skill 格式可能变化，但我会保留工具中立的规范、测试和版本元数据，再用薄适配层生成各端入口。

15Claude Code 与 Codex 的 Skill 如何共享，又如何处理差异？
为什么重要

关键在于确认是否真正做过跨工具工程化，而不是复制 Prompt。

要点
  • 建立单一事实源：公共说明、脚本、模板、fixture 和版本元数据放共享仓库；各工具只保留轻量 manifest/入口适配，避免双份内容漂移。
  • 抽象统一能力接口，如文件读写、Shell、浏览器、MCP、审批；适配层处理工具名称、参数 Schema、上下文约定、沙箱与触发规则差异。
  • 不能假设能力完全等价。维护 capability matrix，缺少某工具时明确降级或阻止运行；跨端契约测试验证相同输入的不变量，而非要求逐字同输出。
  • 共享目录/软链接要考虑路径、权限、循环链接和发布环境；团队场景更适合版本化包或 registry，不只依赖个人机器软链。
  • 可引用已打通的Claude Code 与 Codex 共享 Skill 体系及 MCP 委派（个人项目、个人时间产出），并清楚说明这是个人工程资产，不是公司平台成果。
延伸联想

画“共享内核 80% + 工具适配 20%”，并举一个权限语义不同导致不能直接复用的例子。

边界与常见误区

我不会宣称两个产品零差异兼容；共享的是意图、流程、脚本和验收契约，工具调用及权限由适配层负责。

16MCP 在 AI Coding 工具链中解决什么问题？服务端应如何设计？
为什么重要

关键在于理解对 MCP 的价值、边界和安全设计是否具体。

要点
  • MCP 为 Agent 暴露标准化的 tools、resources、prompts 等能力，降低每个客户端分别对接内部系统的成本；它是上下文/工具协议，不自动解决业务正确性和权限治理。
  • 工具应窄接口、强类型、语义明确，读写分离；返回结构包含 data、error code、retryable、trace id 和对模型友好的精简信息。
  • 身份不能只靠模型参数传入。服务端基于调用主体、租户、资源重新鉴权，采用最小权限、短期令牌、审计、限流、超时和幂等。
  • 高风险写工具支持 dry-run、计划预览、确认 token 或二阶段提交；资源内容视为不可信数据，防止 Prompt injection 借 MCP 提权。
  • 协议版本与业务工具版本分开治理，做契约测试、向后兼容和可观测；不要用一个万能 execute(action,payload) 掩盖权限边界。
延伸联想

区分“MCP 让能力可发现可调用”和“Harness 决定何时调用、能否调用、如何验收”。

边界与常见误区

具体 SDK API 我可以按版本查文档；设计底线是接口窄、服务端鉴权、写操作幂等可审计，不能因为接入 MCP 就把内部系统裸露给模型。

四、Coding Agent 的 Prompt / Context Engineering（17—20）

17AI Coding 的 Prompt 与通用聊天 Prompt 有什么本质不同？
为什么重要

关键在于判断 Prompt 能力是否落到可执行工程任务。

要点
  • Coding Prompt 不是追求漂亮回答，而是定义一次有副作用的变更：目标、现状、允许范围、禁止项、接口约束、验收命令、证据和交付格式。
  • 高质量任务说明类似轻量工程合同：说明 why/what，不必微操每个 how；给 Agent 探索空间，同时用测试和边界收口。
  • 把不稳定自然语言转成机器可验收条件，例如“接口更快”改为基准阈值，“页面一致”改为指定 viewport 的截图与交互检查。
  • 明确先调查再修改、读取项目规则、保留既有行为、不得跳过测试；遇到冲突或高风险动作暂停呈报。
  • Prompt 不应塞入可从仓库查到的大段代码；引用路径、符号、issue 和验收脚本更易维护。
延伸联想

把模糊需求实践中改写成“范围—约束—验收—非目标—升级条件”五段任务卡。

边界与常见误区

我不依赖某个万能 Prompt；Coding 场景真正稳定的是明确边界和外部验证，措辞会随仓库和工具调整。

18面对大型陌生代码库，怎样给 Agent 构造有效上下文？
为什么重要

关键在于理解仓库理解与上下文检索策略。

要点
  • 先读取仓库规则、目录、构建系统、入口、测试与 CI；再用 rg、符号引用、依赖图、调用链和 Git 历史围绕任务建立局部地图。
  • 形成可验证假设：“错误从 A 输入，经 B 转换，在 C 丢失”，按假设加载文件；不要一次读取全仓库。
  • 区分权威信息：代码与测试优先于文档，运行结果优先于模型记忆；文档与实现冲突要呈报并决定修谁。
  • 建立 context manifest，记录已读文件、关键符号、版本、未决问题和为何相关；长任务阶段性压缩，但保留引用可回查。
  • 修改前先找现有模式和相邻测试，避免生成一套与仓库生态不一致的新抽象。
延伸联想

主动说“我的第一步通常不是写代码，而是让 Agent 给出证据化的影响面与验证计划”。

边界与常见误区

我会先做窄范围代码考古，用搜索、调用关系和测试建立局部心智模型；无法确认影响面时不会让 Agent 直接大改。

19如何使用 diff 驱动 Agent 自审，而不陷入“自己审自己”？
为什么重要

关键在于判断是否理解生成与验证需要解耦。

要点
  • 生成后切换到 reviewer 任务：只看需求、原始基线、diff、测试结果和风险清单，避免沿用实现过程中的自我合理化上下文。
  • 审查维度包括需求覆盖、无关改动、边界条件、错误处理、并发/性能、安全、兼容性、可测试性和回滚；大 diff 拆成逻辑单元。
  • 模型审查只能辅助。静态分析、类型、测试、SAST、依赖扫描和人类 owner 提供独立证据；高风险模块可用不同模型/Agent 做第二意见，但不能把共识当真理。
  • 要求每条问题指向具体行和可复现证据，防止泛泛建议；修复后重跑全套相关验证，并检查是否新增无关 diff。
  • 追踪 review yield、误报、遗漏和人工修订时间，持续改进 reviewer rubric。
延伸联想

提出“上下文隔离的双角色 + 确定性工具 + 人类风险 owner”三角审查，而不是简单让同一个会话说“请检查”。

边界与常见误区

模型自审有相关性偏差，所以我只把它当一层；最终结论必须由独立测试、扫描和责任人 review 共同形成。

20TDD 如何与 Coding Agent 结合？测试会不会也被 AI 写错？
为什么重要

关键在于理解测试驱动验证是否真正可信。

要点
  • 先把需求变成可观察行为，新增失败测试并确认红灯原因正确，再做最小实现、跑绿、重构；这能约束 Agent 的搜索空间并防止“实现后编测试迎合”。
  • 测试与实现最好分阶段或分 Agent/上下文，关键验收测试由人或独立来源定义；保留历史回归、契约和生产样本，避免两边犯同一个假设错误。
  • 防止假绿：确认测试确实被执行、失败时能失败、没有过度 mock、没有删除断言、没有 .skip、覆盖关键边界；可用 mutation testing 检查测试敏感度。
  • UI、性能和 Agent 任务需扩展到视觉回归、E2E、benchmark 和轨迹评测，不能只看单测数量。
  • NovelReel（个人项目）具备完整测试集，可作为重视可验证性的证据，但应能解释测试覆盖的核心行为和仍未覆盖的风险，而非只报数字。
延伸联想

强调“红灯证据”比“AI 写了测试”更重要，并实践中说明如何验证一个测试不是空测试。

边界与常见误区

测试同样可能被 AI 写错，所以我会让需求、测试、实现和外部行为相互校验；高风险验收不会只依赖同一次生成。

五、质量、安全与生产力度量（21—25）

21如何防止 AI 生成代码引入安全漏洞？
为什么重要

关键在于确认安全治理是否覆盖从上下文到供应链的全链路。

要点
  • 威胁面包括不安全代码模式、硬编码密钥、越权、注入、依赖投毒、许可证风险、Prompt injection、恶意仓库指令和 Agent 误执行命令。
  • 预防层：安全编码规则、最小工具权限、密钥隔离、依赖 allowlist/lockfile、禁止任意下载执行、高风险模块模板化。
  • 检测层：编译/类型、SAST、secret scan、SCA、IaC/容器扫描、模糊测试和针对认证授权的专项测试；扫描结果进入硬门禁，而不是仅生成报告。
  • 审查层按风险路由给安全/模块 owner；Agent 修复扫描问题时不得自动静默或改规则绕过，例外需有期限、理由和责任人。
  • 运行层采用灰度、最小运行权限、审计、异常监控和快速回滚。安全责任属于提交和审批链，不转嫁给模型供应商。
延伸联想

实践中给出一条从“不可信 issue 文本”到“诱导 Agent 读取密钥并外传”的攻击链，再逐层说明控制点。

边界与常见误区

我不会声称扫描能消灭漏洞；会用权限隔离、自动检测、专家审查和运行时防护做纵深防御，并对高风险变更提高自治门槛。

22AI Coding 的验证闭环应该怎样设计？
为什么重要

关键在于理解是否能把一次任务结果转化为持续改进资产。

要点
  • 闭环是：目标与验收前置→隔离执行→自动验证→独立 review→小流量发布→运行观测→缺陷归因→沉淀回归测试、规则或 Skill。
  • 每次 run 保存任务、基线、工具/模型/Skill 版本、diff、验证证据、人工修改和生产结果，才能判断哪里有效。
  • 失败分类到需求、上下文、模型、工具、实现、测试、环境、权限和审批；不同根因进入不同改进队列，不能全部靠“优化 Prompt”。
  • 把线上缺陷脱敏后加入 benchmark，把高频人工纠正变成 lint、测试、模板或 Skill；定期删除无效规则，避免上下文越来越重。
  • 质量门禁也需测有效性：误报率、绕过率、发现阶段和缺陷逃逸率，防止流程只增加仪式成本。
延伸联想

用“每次人工救火都应留下机器可复用的防线”概括沉淀价值。

边界与常见误区

我会先确保每次变更有证据和可归因数据，再从高频失败建立回归集；没有数据的 Prompt 调优很难形成工程闭环。

23如何衡量 AI Coding 的真实生产力，为什么不能看生成代码行数？
为什么重要

关键在于判断是否具备经营视角和指标反作弊意识。

要点
  • 代码行数是产出体积，不是用户价值；AI 可能生成更多冗余代码，甚至提高 review、维护和缺陷成本。
  • 主指标可用“从任务 ready 到生产验证的合格交付周期”、单位合格任务成本、吞吐量、需求交付率；质量护栏看缺陷逃逸、返工、回滚、变更失败率和 MTTR。
  • 过程诊断看首次验收通过率、人工介入分钟、review wait time、Agent 重试率和验证耗时；满意度只作辅助，不能替代行为数据。
  • 用同类型任务、相近人员和时间窗口做基线；采用分阶段 rollout、配对对比或 difference-in-differences，控制任务复杂度和新鲜感效应。
  • 计算总成本：席位/API、等待、review、返工、安全治理和平台维护。真正提升是质量不降前提下，单位价值的总人机时间和成本下降。
延伸联想

给出北极星指标：“每工程师每月完成并稳定运行 30 天的有效需求数”，同时列质量护栏。

边界与常见误区

我不会用接受率或代码量直接报 ROI；先建立交付周期、人工时间、质量和总成本基线，再用可比任务验证增益。

24如何治理模型、依赖和生成资产的可复现性？
为什么重要

关键在于理解 AI 研发的供应链与版本意识。

要点
  • 记录模型标识、参数、系统规则、Skill/工具版本、仓库 commit、依赖 lockfile、环境镜像、输入摘要与产物哈希；不能只保存一段聊天。
  • 模型服务可能静默升级，因此“完全复现”未必可得；工程目标是证据可追踪、结果可再验证、版本变化可对比。
  • 关键流程使用固定发布通道、回归 benchmark 和 canary；模型/Prompt/Skill 升级视为软件发布，需版本评测和回滚。
  • 依赖安装受 allowlist、锁版本、签名/来源、SBOM 和漏洞扫描约束；Agent 不能为解决编译问题随意升级全局依赖。
  • 生成的代码、图片、文本还需来源与许可证记录，尤其第三方代码片段不能因模型转述就默认无版权风险。
延伸联想

把一次 Agent run 描述成“可寻址的构建”，其输入、执行器、策略、产物和验证都有 provenance。

边界与常见误区

我不会承诺概率模型逐 token 重现，但会确保版本、输入、工具轨迹和验证证据可追踪，结果变化能被回归集及时发现。

25AI Coding 出现线上事故时，怎样复盘而不是简单归咎于 AI？
为什么重要

关键在于判断负责人是否有系统性责任观。

要点
  • 先止损、回滚和保护用户，再保全任务、diff、审批、测试、模型/Skill 版本和部署证据；不把“AI 生成”当根因。
  • 沿控制链进一步讨论：需求为何允许歧义、上下文是否错误、Agent 为何有权限、测试为何未覆盖、review 为何放行、灰度和监控为何未发现。
  • 区分直接错误与系统控制缺失，给 action owner 和期限；修复可能是测试、权限、任务模板、门禁、架构边界或培训，而非只加一句 Prompt。
  • 更新风险分级和 benchmark，回放相似历史变更；观察补丁是否导致审批负担或绕过行为。
  • 复盘强调无责学习但责任明确：工具没有法律和组织责任，提交、审查、发布制度仍由团队承担。
延伸联想

说“AI 是事故链中的组件，不是可以停止进一步讨论的根因标签”。

边界与常见误区

我会按常规工程事故处理：证据化时间线、控制失效分析和可验证整改；是否由 AI 生成只影响调查维度，不改变质量责任。

六、团队规模化与组织治理（26—29）

26如何说服团队和管理层采用 AI Coding？
为什么重要

关键在于理解变革推动能力，而非技术布道热情。

要点
  • 对管理层用业务问题表达：交付周期、积压、质量和人才杠杆；对开发者用具体痛点表达：陌生代码定位、测试补齐、重复迁移、文档和脚手架。
  • 先找自愿 champion 和低风险高频场景，建立无 AI 基线，做 2—4 周小试点；公开成功、失败、成本和适用边界。
  • 不要求所有人同一种用法。提供最低安全规范、推荐路径、办公时间和可复用 Skill，让价值通过真实任务扩散。
  • 管理层承诺 AI 指标不直接用于粗暴裁员或按代码量排名，否则成员会隐藏使用、制造虚假数据并抵制反馈。
  • 实践者的 AI Engineering 课程体系（个人项目、个人时间产出） 包含系统化专题和多份可演讲 HTML 课件，可证明系统化培训与知识产品能力；不能表述为已在公司完成全员培训。
延伸联想

建议用一条团队最痛的交付链路做“前后对照实践中”，比泛讲趋势更有说服力。

边界与常见误区

我不会靠行政命令推广；先用可比任务证明收益和边界，再通过 champion、培训和工具资产降低使用成本。

27团队 AI Coding 使用规范应包含哪些内容？
为什么重要

关键在于判断能否把风险原则落成可执行制度。

要点
  • 数据分级：哪些代码/文档可进入哪些模型，禁止输入密钥、个人信息和受限资料；明确供应商数据留存与训练策略。
  • 权限分级：允许读写范围、联网、依赖安装、外部系统、生产访问和审批要求；禁止 Agent 绕过 CI、关闭安全规则或自行部署高风险变更。
  • 交付规范：提交者负责、必须 review diff、运行指定测试/扫描、披露未验证部分；关键模块需要 owner 审核。
  • 资产规范：Prompt/Skill/MCP 的 owner、版本、测试、发布和退役；第三方 Skill/插件按供应链依赖管理。
  • 事故、例外和审计流程必须简短可执行；规范进入模板、pre-commit、CI 和 Harness policy，不能只放 Wiki。
延伸联想

提出“一页红线 + 自动门禁 + 详细手册”三层设计，让新人能在一分钟知道不能做什么。

边界与常见误区

我会先把数据、权限、提交责任和高风险操作四条底线固化，再结合安全与法务逐步完善，不用一份过长制度阻塞试点。

28如何设计分层培训，让 20 人团队真正形成能力？
为什么重要

关键在于理解培训是否能转化为工作行为。

要点
  • 入门层掌握任务描述、上下文、diff、测试和安全红线；进阶层掌握长任务拆分、调试、TDD、Skill；骨干层掌握 Harness、MCP、评测、权限与平台治理。
  • 培训使用团队真实但脱敏的仓库任务，采取演示→结对练习→独立交付→review 复盘；考试看合格变更与风险识别，不看 Prompt 背诵。
  • 建立 office hours、案例库、失败博物馆、champion 轮值和模板；将高频纠错沉淀为自动规则，减少口口相传。
  • 按角色设计内容：前端视觉验证、后端契约/迁移、QA 测试生成、安全威胁审查、管理者指标与流程。
  • 可用 AI Engineering 课程体系（个人项目）的系统化专题和多份 HTML 课件说明内容建设能力，并坦诚企业落地还需按团队栈和基线裁剪。
延伸联想

提出结业标准：独立完成一个真实任务，交付 diff、验证证据、风险说明和一次复盘沉淀。

边界与常见误区

我不会把看课等同掌握；培训效果要由真实任务首次通过率、人工介入时间和质量护栏验证。

29如何处理团队成员对“AI 替代”的焦虑？
为什么重要

关键在于理解管理同理心、组织诚信与角色重构能力。

要点
  • 不用“AI 不会替代任何人”这种无法兑现的安慰，也不以恐惧推动采用。透明说明哪些任务会自动化、哪些责任会增强、评价标准如何调整。
  • 将角色从代码产量转向问题定义、架构判断、验收、安全、用户价值和资产沉淀；给学习时间、练习任务和导师支持。
  • 明确试点数据不用于简单个人排名，允许员工报告 AI 失败而不受惩罚；否则问题会被隐藏，治理失真。
  • 给不同成熟度的人多条路径：高阶开发者建设 Harness/评测，业务专家沉淀验收知识，初级工程师借 AI 加速学习但仍需解释代码。
  • 管理者以身作则公开自己的失败轨迹，同时守住绩效与人员决策的诚信边界。
延伸联想

把讨论从“是否替代职位”转向“未来一年团队必须新增哪些能力、公司提供什么学习保障”。

边界与常见误区

焦虑不能靠技术论证消除。我会透明沟通任务变化和评价机制，提供实际训练与转岗路径，并用一致的人事政策建立信任。

七、系统设计题（30—31）

30系统设计：为 20 人研发团队设计一套 AI Coding 工作流与质量门禁。
为什么重要

综合考察工具链、权限、流程、度量和分阶段落地能力。

要点
  • 需求与假设：先确认语言栈、代码敏感级别、现有 Git/CI、是否允许云模型、发布频率和高风险模块。目标不是全自动，而是在质量不降前提下缩短合格交付周期。
  • 入口层：支持 IDE 与 CLI 两类入口，统一身份、仓库规则、任务模板和 Skill catalog；工具选择可多样，策略底线统一。
  • 执行层：每个任务创建隔离 branch/worktree/container；Harness 管理 run/step、上下文、预算、工具权限和检查点。默认无生产凭据，网络 allowlist，敏感数据脱敏。
  • 流程：任务卡明确范围/非目标/验收→Agent 先调查和计划→人确认高风险方案→Agent 小步提交→本地 verifier→独立 diff review→PR/CI→owner 审核→灰度发布→线上观测。
  • 门禁：编译、lint、类型、单元/集成、SAST、secret、SCA、许可证为基础层；认证、支付、医疗、迁移等高风险目录追加 CODEOWNERS、专项测试与人工审批。禁止 Agent 修改门禁配置来通过门禁。
  • 平台能力：策略中心、MCP gateway、Skill registry、模型网关、审计事件、artifact store、评测集和 dashboard；凭据短期化、调用按人/项目/工具归因。
  • 指标：合格交付周期、首次通过率、人工介入、缺陷逃逸、回滚率、变更失败率、单位合格任务成本；不采用 LOC 或简单采纳率作为北极星指标。
  • 容量与组织：20 人先配 2—3 名 champion 和一个平台 owner；限制并发 WIP，避免 Agent 生成速度压垮 review。培训分层，office hours 收集失败案例。
  • 落地节奏：0—2 周基线和红线；3—6 周在低风险仓库试点；7—12 周接 Skill/MCP 和分级门禁；数据达标再扩大。每阶段都有停止条件与回滚方案。
  • 风险：供应商锁定、上下文泄漏、Prompt injection、成本失控、审批疲劳、Skill 供应链和指标游戏化；用抽象适配、最小权限、预算、抽样审计和定期治理缓解。
延伸联想

白板先画“开发者入口→Harness/策略→隔离执行→PR/CI 门禁→发布观测→评测沉淀”，然后主动给出 90 天路线和成功阈值，体现负责人不仅会画终局架构。

边界与常见误区

具体 CI 和云模型选择要结合当前团队约束，但我会先守住隔离、最小权限、验收前置、独立 review 和可度量闭环，再从低风险黄金路径渐进扩展。

31系统设计：把个人 Agent Harness 经验产品化为团队研发基础设施，你怎么规划？
为什么重要

关键在于理解从个人原型到多租户平台的架构、产品和运营升级能力。

要点
  • 真实性起点：mini-harness、跨工具 Skill、NovelReel 均是个人项目、个人时间产出，证明机制与端到端实践；产品化必须承认原型在权限、SLA、租户、运维和合规上的差距。
  • 先选产品楔子：访谈团队并找一条高频、高成本、可验证流程，例如 issue→修复→测试→PR；不一开始做万能 Agent 平台。定义使用者、购买者、管理员和安全角色。
  • 控制面：租户/项目、身份 RBAC/ABAC、策略、模型与工具 registry、Skill catalog、预算、审批、审计、版本和评测发布。
  • 执行面：隔离 runner、任务队列、context builder、tool/MCP gateway、checkpoint、artifact store、verifier、取消/超时/重试；runner 使用短期凭据和最小网络权限。
  • 核心数据模型：Task、Run、Step、ToolCall、Artifact、Checkpoint、PolicyDecision、Evaluation、Approval；事件可回放，副作用幂等，状态可恢复。
  • 扩展机制：工具中立的 Skill spec + Claude Code/Codex 等薄适配；MCP 负责标准接入，Harness 负责编排与治理。插件签名、权限声明、兼容矩阵和契约测试防供应链风险。
  • 验证体系：离线任务 benchmark、shadow run、canary、版本对比和生产失败回流；模型、Prompt、Skill、policy 任一升级均有评测与回滚。
  • 非功能要求：SLO、并发隔离、成本配额、数据留存、加密、灾备、可观测和管理员审计；明确不存储不必要的原始代码/Prompt。
  • 路线图：P0 单团队黄金路径；P1 多项目身份与审计；P2 Skill/MCP 生态和评测中心；P3 自助接入与跨团队运营。每阶段以活跃合格任务、质量和总成本设退出标准。
  • 商业与组织判断：持续维护模型/工具兼容成本很高，应复用现成 SDK 与沙箱；核心壁垒放在企业上下文、验证资产、失败数据和组织工作流，而不是再造聊天界面。
延伸联想

主动做 gap analysis：“个人可用”到“团队可信”缺的是身份、隔离、审计、SLO、兼容和运营，然后说明先补哪三项、为什么。

边界与常见误区

我不会把个人原型直接称为平台。我的做法是先验证一个团队级黄金路径，再围绕身份、隔离、状态、验收和观测逐步补齐企业能力，用数据决定是否平台化。

八、负责人级综合判断（32）

32结合 2026 年 Harness 工程角色趋势，你的差异化能力和短板分别是什么？
为什么重要

看实践者能否把市场需求、真实证据、负责人能力与边界诚实地连起来。

要点
  • 市场证据可引用开头 JD：AI 编程工具熟练、稳定 Prompt、高质量 coding、实际交付，以及通过 Harness 提升构建效率、可验证性与可复用性，已成为明确角色要求。
  • 第一层差异化是“使用深度”：Claude Code、Codex、Cursor 不停留在补全，而是用于真实前端/全栈项目的调查、实现、测试、审查和交付。
  • 第二层是“机制与资产”：mini-harness（个人项目）、AI Engineering 课程体系（个人项目，包含系统化专题和多份 HTML 课件）、跨工具 Skill/MCP 自动化（个人项目）、NovelReel（个人项目，三层编排、降级、持久化、断点续跑、完整测试集），形成从实践到抽象再到教学的证据链。
  • 第三层是“企业场景”：公司的 AI 医疗助手产品有 Dify 工作流编排经验，覆盖多类医疗场景智能体；要准确说明自己的职责、团队协作与平台边界。
  • 第四层是“负责人能力”：具备十余年研发和多年管理经验，能把工具个人增益转成选型、规范、质量门禁、培训、指标和组织变革，而不是只展示个人效率。
  • 短板要坦诚：若没有 1 万+ star 开源项目参与就明确没有；个人 Harness 尚不等于经历过大规模多租户生产验证。补强计划应是公开可验证的 benchmark/文档、真实团队试点、MCP 服务端作品、SLO 与安全治理数据。
  • 推荐回答结构：市场为什么需要→自己有什么直接证据→企业经验如何迁移→哪些尚未被证明→入职 90 天如何验证，而非罗列工具名。
延伸联想

最后结合当前环境确认：“当前团队现在更缺会使用 AI Coding 交付的人，还是能把个人能力产品化、治理化的人？如果是后者，我可以继续展开 90 天落地方案。”

边界与常见误区

我不会用热点词包装未验证经历。我的优势是工具实战、个人 Harness/Skill 资产、Agent 项目和管理经验能形成闭环；规模化生产数据和大体量开源影响力若尚不足，我会明确边界，并用可衡量的试点快速补证。

## 笔记说明

  • 整理顺序优先采用：判断框架→核心机制→真实案例→边界/风险→可量化结果。
  • 个人资产每次首次提及时明确说“这是我的个人项目、个人时间产出”，后续可以简称，但不要结合当前环境误解为公司成果。
  • 公司 AI 医疗助手产品的 Dify 经验可以讲业务复杂度和编排判断；不虚构没有亲自实现的底层模型、框架或基础设施细节。
  • 不把“会用 Claude Code/Codex/Cursor”讲成工具熟练度竞赛，要落到验收、状态、权限、失败恢复、Skill 沉淀、质量和组织推广。
  • 涉及未验证规模时，记录清楚边界与验证方案；负责人可信度来自判断与证据，不来自把所有经历说成生产级。
